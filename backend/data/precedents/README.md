# backend/data/precedents/ — 판례 데이터 안내 (정민재 편집 대상)

> 판례 매칭 화면의 재료가 되는 폴더입니다. **`seed_cases.json`만 직접 편집하면 됩니다.**
> (기존 `backend/data/cases.json`은 구 방식(수기 전체 입력)이고, 이 폴더가 신 방식입니다 —
> E-3에서 화면이 이 데이터로 전환되면 cases.json은 정리 예정. docs/cleanup-tracker.md 참고.)

## 폴더 구성

| 경로 | 내용 | 편집 |
|---|---|---|
| `seed_cases.json` | **판례 큐레이션** — 쉬운 요약·결과·조언·위험 태그 | ✅ 정민재 |
| `eval_set.json` | 검색 정확도 평가 기대 쌍 ("이 위험이면 이 판례가 나와야 함") | 개발자와 함께 |
| `raw/` | 법제처 API로 받아온 판례 원문 (자동 생성) | ❌ 손대지 않기 |
| `index/` | 검색용 벡터 인덱스 (자동 생성, git 미추적) | ❌ 손대지 않기 |

## seed_cases.json 편집법

기존 항목을 복사해 내용만 바꾸는 방식이 안전합니다 (JSON 문법 규칙은 `backend/data/README.md`와 동일).

한 항목의 칸:

| 칸 | 뜻 | 필수 |
|---|---|---|
| `case_no` | 사건번호 (판결문 표기 그대로, 예: `"2019다300095"`) | ✅ |
| `court` | 법원명 (예: `"대법원"`) | ✅ |
| `decided` | 선고일 `"2022-02-17"` | |
| `risk_tags` | 위험 태그 (아래 고정 어휘에서만) | ✅ |
| `summary_easy` | 사건 쉬운 요약 한두 문장 (해요체) | ✅ |
| `outcome` | 임차인이 어떻게 됐는지 한 줄 | ✅ |
| `advice` | **"이런 피해를 피하려면"** — 카드에 그대로 실림 | ✅ |
| `source_urls` | 확인한 출처 링크 목록 (최소 1개) | ✅ |
| `holding` | 판결 요지 — **법제처 원문이 있으면 비워 둠**(자동으로 채워짐) | 원문 없을 때만 |
| `verified` | 출처 확인 완료 여부 — `false`면 **앱에 절대 노출 안 됨** | ✅ |
| `curated_by` / `date` | 정리한 사람 / 날짜 | ✅ |

**위험 태그 고정 어휘 (8종)**: `"전세가율"` `"선순위 채권"` `"신탁등기"` `"압류·가압류"`
`"경매"` `"임차권등기"` `"보증보험"` `"대항력"`

## 지켜야 할 것 (기존 원칙 그대로)

1. **지어내기 금지** — 사건번호·요지는 실제 확인된 것만. 못 찾은 판례는 넣지 않는다.
2. **출처 필수** — 판결문 원문(law.go.kr, casenote 등)이나 판결 인용 기사. 블로그 단독 금지.
3. **확신 없으면 `verified: false`** — 넣어 두되 노출은 자동 차단된다. 개발자·팀 검수 후
   `true`로 올리면 그때부터 노출된다. **대량 수집분(raw/)을 검수해 승격할 때는 자동으로
   붙은 위험 태그가 맞는지도 함께 재검토**한다(키워드 규칙이라 과잉 태깅 소지 —
   rule-auditor 권고).
4. 조언(`advice`)에 "안전합니다" 같은 단정 표현 금지 — "~확인하세요/~검토하세요"로.

## 편집 후 반영 절차 (개발자 실행)

```bash
cd backend
.venv/Scripts/python.exe scripts/ingest_precedents.py   # 재적재
.venv/Scripts/python.exe scripts/eval_retrieval.py      # 검색 품질 확인
```

새 위험 유형의 판례를 추가했다면 `eval_set.json`에 기대 쌍도 함께 추가해 달라고
개발자에게 알려 주세요 (검색 품질 측정이 그 판례를 포함하도록).
