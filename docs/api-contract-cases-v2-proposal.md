# api-contract.md 갱신안 — 판례 섹션 v2 (제안서 · 미승인)

> **상태: 제안(초안).** 2026-07-22 야간 자율 작업 산출물. 판례 RAG 모듈이 만들 수 있는
> 응답을 기준으로 `docs/api-contract.md` §2.3·§3.5의 갱신안을 정리한다.
> **api-contract.md 본문은 건드리지 않았다** — E-3 게이트에서 이 제안을 승인·반영할 때
> 본문을 갱신한다(계약 변경은 앱 작업과 한 몸이라 단독 확정 금지).

## 1. 변경 요약

| 항목 | 현행 (§2.3 CaseMatch) | 제안 (v2) | 호환성 |
|---|---|---|---|
| `riskPattern` | 고정 어휘 4종 | 어휘 확장(8종) | ⚠ 앱 칩 표시 확인 필요 |
| `caseNo` | 유지 | 유지 (+ `decided` 추가) | additive |
| `summary`·`result`·`commonPoint` | 유지 | 유지 (의미 동일) | 무변경 |
| (신규) `advice` | — | 카드별 맞춤 조언 (큐레이션) | additive — 피드백 A5 |
| (신규) `sourceUrl` | — | 판례 출처 링크 | additive |
| (신규) `matchedTags` | — | 매칭 태그 목록 (개수 정렬·뱃지) | additive — 피드백 A6 |
| (신규) `explanationSource` | — | 섹션 단위 "AI 생성"/"자동 생성" 라벨 | additive |
| (신규) 폴백 | 빈 배열 | 빈 배열 + `fallbackText` | 응답 형태 변경 → 아래 §3 |

## 2. 제안 데이터 모델

### 2.1 `CaseMatchV2`

```
CaseMatchV2 {
  riskPattern: string,     // [메타] 대표 위험 태그 1개 (칩 표시용)
  matchedTags: string[],   // [메타] 이 매물 판정과 겹친 태그 전체 (뱃지 + 개수 정렬 — A6)
  caseNo:      string,     // [메타] "대법원 2019다300095" — 검색된 문서에서 복사 (LLM 불개입)
  decided:     string|null,// [메타] 선고일 "2022-02-17"
  sourceUrl:   string,     // [메타] 판례 원문·확인 링크 (인용 필수 요소)
  summary:     string,     // [설명] 사건 쉬운 요약 (LLM 생성 슬롯 — 실패 시 큐레이션 폴백)
  commonPoint: string,     // [설명] 우리 매물 판정과의 공통점 (동상)
  result:      string,     // [판정 아님·사실] 임차인 관점 결과 — 큐레이션 값 그대로
  advice:      string|null // [큐레이션] "이런 피해를 피하려면" — LLM 불가침 (A5, decisions.md 2026-07-09)
}
```

- **출처 태그 원칙(§0) 그대로**: `[설명]` 두 필드만 LLM 슬롯이고, 나머지는 서버가
  검색된 문서에서 복사한다. LLM 출력 스키마(`PrecedentExplanation`)는 `extra="forbid"`이며
  등급·점수·사건번호·advice 필드가 **존재하지 않는다** — E-2 가드레일과 동일.
- 카드 표시 순서 제안(피드백 A4): **공통점(commonPoint) → 결과(result)** 순서로 앱이 배치.

### 2.2 응답 래퍼 (§3.5 갱신안)

```
GET /api/reports/{id}/cases → 200
{
  "cases": CaseMatchV2[],          // 최대 4건, 매칭 태그 수 → 유사도 순 정렬
  "fallbackText": string|null,     // cases가 빈 배열일 때만 — 정직한 폴백 문구
  "explanationSource": string      // "AI 생성" | "AI 생성(일부 폴백)" | "자동 생성"
}
```

- **폴백 문구는 서버 결정적 템플릿** (예: "…판례를 아직 찾지 못했어요. 판례가 없다는
  뜻이 위험이 없다는 뜻은 아니에요…") — "판례 없음 = 안전" 오독 차단(보수적 편향).
- `explanationSource`는 E-2 라벨 결정(2026-07-09 "자동 생성")과 동일 원칙 — 폴백을
  "AI 생성"으로 표기하지 않는 정직성 장치.

### 2.3 `riskPattern` 어휘 확장

현행 4종(신탁등기·선순위 채권·전세가율·보증보험)에 **임차권등기·압류·가압류·경매·대항력**을
추가한다. 판정 근거(ownership 카드의 압류 신호 등)와 판례를 더 정밀하게 잇기 위함.
⚠ 확인 필요: 앱 판례 화면 칩이 미지의 라벨 문자열을 그대로 표시하는지(E-3에서 확인 —
프론트 구현 금지 범위라 이번에 확인하지 않음).

## 3. 왜 래퍼 객체인가 (현행은 배열 반환)

현행 §3.5는 `CaseMatch[]` 배열을 반환하고 "빈 배열 허용(앱이 빈 상태 문구 표시)"이다.
- 배열 유지안: 호환성 최고, 그러나 폴백 문구·설명 출처 라벨을 실을 곳이 없다
  (앱 하드코딩 문구는 서버 결정적 문구 원칙과 어긋남 — E-3 홈 카드 사례와 동일 논리).
- **래퍼 채택 권고**: 앱 수정이 어차피 필요한 화면(A4·A5·A6 반영)이므로, 같은 E-3
  작업 묶음에서 응답 형태를 한 번에 바꾸는 것이 재작업이 가장 적다.

## 4. 태그 저장 권고 (additive)

저장된 리포트 재열람 시 판례 매칭 정밀도를 위해, analyze 시점에 파생된 위험 태그를
리포트에 저장하는 것을 권고한다:

```
Report { ..., riskTags?: string[] }   // [판정] 규칙 엔진 파생 — LLM 불개입, additive
```

- 없으면 서버가 detailText 문구로 태그를 재파생하는 폴백(`tags_from_report`)을 쓴다 —
  동작은 하지만 판정 facts 기반보다 거칠다 (docs/precedent-rag.md §4-1).

## 5. 미결·확인 필요

1. 앱 칩의 미지 라벨 표시 방식 (§2.3) — E-3에서 확인.
2. Solar 판례 설명을 **분석 시점에 미리 생성·저장**할지, **판례 화면 진입 시 생성**할지
   (지연 vs 크레딧·이력 일관성) — E-3 설계 결정.
3. `advice` 없는 판례(대량 수집분)의 카드 표시 — "조언 준비 중" 문구 vs 필드 숨김.
