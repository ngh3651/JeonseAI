# 앱 ↔ 서버 JSON 계약서 (api-contract.md)

> **Phase D-1 산출물.** 앱(Flutter)과 서버(FastAPI)가 주고받을 데이터 형식을 확정한 문서입니다.
> 이 계약은 D-2(서버 더미 응답 구현)와 D-3(앱 연결)의 설계도이며, 나중에 실제 분석(Phase E)으로
> 교체될 때 **앱을 바꾸지 않고 서버 속만 바꾸기 위한** 기준점입니다(Repository 패턴).
>
> - 이 문서는 **"무엇을 주고받는가"만** 정의합니다. "어떻게 만드는가"(추출·판정 로직)는 담지 않습니다.
> - 모든 필드는 **Phase C 화면 코드에서 실제로 쓰는 데이터**를 역추출한 것입니다. 화면에 없는 필드는 넣지 않았습니다.
> - plan.md·CLAUDE.md가 말하는 `docs/data-contract.md`가 바로 이 문서입니다(파일명은 api-contract.md로 확정).

## 0. 핵심 원칙 (계약에 반영된 가드레일)

1. **판정과 설명의 분리** — 위험 판정(등급·수치)은 규칙 엔진이, 설명 문장은 LLM이 만든다.
   그래서 응답의 각 필드에 **출처 태그**를 붙였다:
   - `[판정]` = 규칙 엔진이 만드는 값(등급·수치·상태). LLM이 못 바꾼다.
   - `[설명]` = LLM(Solar Pro)이 생성하는 문장. 판정을 바꾸지 않고 문장만.
   - `[메타]` = 식별·시각용 값(id·주소·시간·게이지 진행률 등).
   - `[UI]` = 앱이 그대로 노출하는 고정 라벨.
2. **보수적 편향** — 등급은 `위험 | 확인 필요 | 양호` 3단계이며, 데이터가 불충분하면
   `양호`로 단정하지 않고 항목 상태를 `확인 필요`로 표현한다(2번 §2, 근거 카드 `statusLabel`).
3. **Repository 교체** — 앱은 이 계약(무엇을)만 알고 서버 내부(어떻게)는 모른다.

## 1. 공통 규약

### 1.1 기본 주소
- Base URL: `http://127.0.0.1:8000` (실기기 `adb reverse tcp:8000 tcp:8000` 고정)

### 1.2 인증 (확정된 규칙)
- **인증이 필요한 API는 두 개**다: `POST /api/analyze`(분석 실행)와 `DELETE /api/reports/{id}`(이력 삭제).
  삭제는 분석과 한 몸이다 — 로그인해서 분석한 사람만 자기 리포트를 지운다(§3.4). 그 외 조회성 API는 **비회원도 허용**한다.
- 인증이 필요한 요청은 헤더에 토큰을 싣는다: `Authorization: Bearer <token>`
- **개발 모드(현재)**: 아직 진짜 로그인 시스템(Supabase 등)이 없어, 인증을 실제로 걸면 우리 스스로
  분석을 테스트할 수 없다. 그래서 **서버는 지금 토큰을 실제로 검사하지 않고 항상 통과**시킨다
  (토큰이 없어도 200). 단, 나중에 진짜 인증을 켜기 쉽도록 **인증 검사를 한 곳(의존성 함수
  `get_current_user`)에 몰아두고 "항상 통과"만 반환**하게 한다 — 이 함수 하나만 바꾸면 실인증이 켜진다.
- **앱 쪽 기획 의도는 유지**: 화면상 비회원이 분석하려 하면 로그인 유도가 뜬다(D-3 앱 작업). 서버는 관여하지 않는다.
- 로그인/회원가입 서버 엔드포인트는 이번 D에 만들지 않는다(계약 범위 밖 유지).

### 1.3 에러 형식 (일관)
모든 에러는 HTTP 상태 코드 + 아래 JSON으로 반환한다(현행 백엔드 `/api/upload`와 동일 형식).

```json
{ "detail": "사용자에게 보여줄 한국어 메시지" }
```

| 상태 | 의미 |
|---|---|
| 400 | 잘못된 요청(형식 오류 등) |
| 401 | 인증 필요/실패 (분석·삭제 API. **개발 모드에서는 발생하지 않음** — §1.2) |
| 403 | 금지된 동작 (예: 예시 리포트 삭제 시도 — §3.4) |
| 404 | 리소스 없음(리포트 id 없음, 용어 조회 실패=범위 밖) |
| 413 | 업로드 용량 초과 |
| 5xx | 서버 오류 (앱은 "잠깐 문제가 생겼어요"로 표시) |

### 1.4 값 표기
- **금액**: 정수, 단위는 **원**(예: `120000000` = 1억 2천만원). 앱이 "만원" 입력을 원으로 변환해 보낸다.
- **날짜/시간**: ISO 8601 문자열(예: `"2026-06-27T09:00:00+09:00"`). 앱이 "2026.06.27"·"7일 전"으로 표시.
- **등급 문자열**(`grade`): `"위험"` | `"확인 필요"` | `"양호"` (공백 포함, 앱 enum 라벨과 동일).
  - 등급별 **색·의사결정 문구는 앱이 grade로부터 파생**한다(아래 표). 서버는 `grade`만 보내면 된다.

  | grade | 의사결정 문구(앱 파생) | 색(앱 파생) |
  |---|---|---|
  | 위험 | 계약을 피하는 것을 권해요 | 빨강 |
  | 확인 필요 | 보류하고 아래 항목을 먼저 확인하세요 | 주황 |
  | 양호 | 진행을 검토할 수 있어요 — 단, 직접 확인은 꼭 필요해요 | 초록 |

## 2. 공통 데이터 모델

여러 엔드포인트에서 재사용하는 객체들이다.

### 2.1 `Report` — 안전도 리포트 (핵심)
홈 카드·리포트 화면·시뮬레이터가 공유한다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 리포트 식별자 (예: `"analysis-1720000000000"`) |
| `alias` | string | [메타] | 매물 별칭. 미입력 시 `address`가 기본값 |
| `address` | string | [메타] | 표제부 소재지 주소 |
| `analyzedAt` | string(ISO8601) | [메타] | 분석 시각 |
| `grade` | string | [판정] | 위험도 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `gaugeProgress` | number | [메타] | 게이지 시각 진행률 0.0~1.0 (점수 체계는 E-1에서 확정) |
| `headline` | string | [설명] | 결론 한 줄 (예: "보증금을 지키기 어려운 신호가 보여요") |
| `nextAction` | string | [설명] | "지금 해야 할 일" 한 문장 |
| `topRiskSummary` | string | [설명] | 최대 위험 요인 한 줄 — 홈/마이 이력 카드 3번째 줄 |
| `deposit` | integer | [판정] | 예정 보증금(원) — 사용자 입력 |
| `marketPrice` | integer \| null | [판정] | 매매 시세(원). null이면 전세가율 근거는 "확인 필요" |
| `marketPriceSource` | string \| null | [표시] | 시세 출처 — §2.8 (2026-08-03 추가, 선택) |
| `marketPriceAsOf` | string \| null | [표시] | 기준일(`"2025-01-01"`) 또는 조회기간(`"2026-02~2026-07"`) |
| `marketPriceSampleCount` | integer \| null | [표시] | 실거래가일 때 표본 수 |
| `marketPriceGapPct` | integer \| null | [표시] | 실거래가가 공시 기준보다 몇 % 높은지. **판정에 쓰지 않는다** |
| `marketPriceAlternatives` | `MarketPriceAlternative[]` | [표시] | 채택되지 않은 시세 후보들 (기본 `[]`) |
| `seniorDebtAmount` | integer | [판정] | 선순위 채권 합계(원) — 손실 시뮬레이터 입력 |
| `evidences` | `Evidence[]` | — | 근거 카드 목록(§2.2) |
| `highlights` | `Highlight[]` | [표시] | 원본 사진 위 표시 — §9 (기본 `[]`) |
| `highlightNotice` | string \| null | [표시] | 사진 묶음 안내 한 줄 — §9 |
| `checkedNotes` | string[] | [표시] | "무엇을 찾아봤나" 요약 — §9 (기본 `[]`) |
| `registryViewedAt` | string \| null | [표시] | 등기부 열람일시 `YYYY.MM.DD` — §9 |
| `comparable` | boolean | [메타] | 이 분석을 **다음 등기부와 견줄 기준으로 쓸 수 있는가** — §2.9 (기본 `false`) |

- **홈/마이 이력 카드**가 쓰는 필드: `id, alias, address, analyzedAt, grade, deposit, topRiskSummary`.
- **손실 시뮬레이터**가 쓰는 필드: `alias, deposit, marketPrice, seniorDebtAmount` + `evidences`에서 `insurance` 항목의 `grade`(보증보험 가입 미확인 경고 판단). **슬라이더·보험 토글 계산은 앱에서 로컬 수행**(서버 호출 없음). 계산식은 E-4에서 서버 이관 검토.
- **파생 값(전송 안 함)**: 등급별 `decisionLabel`·색은 앱이 `grade`로 파생. `riskLabels`(위험 패턴 목록)는 `evidences`에서 파생(§2.2 note).

### 2.2 `Evidence` — 근거 카드 한 항목
리포트 화면의 접힘/펼침 카드. `evidences` 배열의 원소.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 항목 식별자: `jeonse_ratio` \| `senior_debt` \| `ownership` \| `insurance` \| `blacklist` |
| `title` | string | [설명] | 쉬운 질문형 제목 (예: "나보다 먼저 돈 받아갈 빚이 있나요?") |
| `termSubtitle` | string | [UI] | 전문용어 부제 (예: "선순위 채권 · 근저당권") |
| `grade` | string | [판정] | 이 항목의 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `statusLabel` | string \| null | [판정] | 등급 대신 표시할 상태 (예: "확인 필요", "페이지 누락"). null이면 grade 라벨 사용 |
| `easyExplanation` | string | [설명] | 펼침 1단: 쉬운 설명 (LLM 생성 슬롯 — 판정 변경 금지) |
| `detailText` | string \| null | [판정] | 펼침 2단: 상세 수치를 사람이 읽게 포맷한 문자열 (예: "채권최고액 1억 8,000만원 · 근저당권 2건") |
| `sourceText` | string \| null | [판정] | 판정 출처 (예: "HUG 공식 기준 등 확정 예정" — E-1에서 실제 출처로 교체) |
| `actionLabel` | string \| null | [UI] | 다음 행동 버튼 라벨 (예: "중개사에게 물어볼 질문 보기", "시세 입력하기"). null이면 버튼 없음 |
| `termGlossary` | object(map) | [설명] | `easyExplanation` 속 용어→툴팁 설명. 키=용어, 값=설명 문장 (예: `{"근저당권":"집주인이 …"}`) |
| `explanationSource` | string? | [설명] | **이 카드의 설명 문장을 누가 썼는가** (2026-08-14 D26 추가 · additive). LLM이 쓴 문장이면 **실제 호출된 모델 문자열**(예: `"solar-pro2"`), 검증에 걸려 미리 준비한 문장이 나갔으면 `"준비된 문구"`. 없으면(옛 리포트) 앱이 종전 라벨 `자동 생성`을 쓴다 |

- ⚠ `explanationSource`는 **판정 출처가 아니다.** 판정은 언제나 규칙 엔진이고 그 출처는 `sourceText`다.
  설명 계층에만 해당하며, **카드마다 다를 수 있다** — 설명 폴백이 필드 단위라 한 리포트 안에서
  어떤 카드는 모델 문장, 어떤 카드는 준비된 문구가 된다.
- ⚠ 한 카드 안에서 경로가 섞이면 **`"준비된 문구"`로 내린다**(과대 표기 금지 · 보수 편향).

- **위험 패턴 파생(중요)**: 판례·질문 엔드포인트가 쓰는 "위험 패턴"은 `evidences` 중 `grade ≠ 양호`인
  항목의 `id`를 아래로 매핑해 만든다. **앱은 이 파생을 하지 않아도 되며(서버가 리포트 id로 계산)**,
  파생 규칙만 계약에 남긴다:
  `senior_debt→선순위 채권`, `ownership→신탁등기`, `jeonse_ratio→전세가율`, `insurance→보증보험`.

### 2.3 `CaseMatch` — 판례 (판례 매칭 화면)
| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `riskPattern` | string | [메타] | 매칭된 위험 패턴명 (예: "신탁등기", "선순위 채권"). 앱이 칩에서 쉬운 말로 치환해 표시 |
| `caseNo` | string | [메타] | 사건번호 (예: "대법원 2022다123456") |
| `summary` | string | [설명] | 사건 한 줄 요약 |
| `result` | string | [설명] | 결과 (예: "보증금 대부분 손실") |
| `commonPoint` | string | [설명] | 우리 매물과의 공통점 |

**E-3 추가 (2026-08-07) — additive only.** 기존 5개 필드의 의미는 그대로다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `sourceUrl` | string? | [메타] | 판결문 원문 링크. 지어내지 않았음을 사용자가 직접 검증하는 통로 |
| `decided` | string? | [메타] | 선고일 |
| `matchedTags` | string[] | [메타] | 이 판례가 우리 매물의 어떤 위험과 겹쳤는지. 서버 정렬 1순위 키 |
| `advice` | string? | [큐레이션] | "이런 피해를 피하려면". **LLM이 만들거나 고치지 않는다** |
| `curated` | bool | [메타] | 사람이 문구까지 검수했는지. 출처 확인(`source_verified`)과는 다른 축 |

**읽기 보조 추가 (2026-08-14 D20·D23) — additive only.** 옛 앱은 두 필드를 무시해도 그대로 동작한다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `termGlossary` | `{string: string}` | [큐레이션] | 본문에 등장한 어려운 말 → 쉬운 설명. **§2.2 `EvidenceItem.termGlossary`와 같은 구조·같은 규칙** |
| `emphasis` | `{string: string[]}` | [설명] | `{필드명: [굵게 그릴 부분 문자열]}`. 필드명은 이 모델 이름 그대로 — `result` · `commonPoint` · `advice` |

- `termGlossary`의 키는 **본문에 글자 그대로 있어야** 한다. 앱이 `indexOf`로 찾아 점선 밑줄을
  붙이기 때문이다(근거 카드와 동일 전제). 서버는 검수된 용어(`terms.json` `verified=true`)만 내린다.
- `emphasis`의 각 문자열도 **해당 필드 본문의 정확한 부분 문자열**이다. Solar가 고르고
  서버가 검증한다(부분 문자열 일치 · 필드당 2개 이하 · 항목당 30자 이하 · 굵은 글자 합이 본문의 30% 이하).
  하나라도 어기면 그 필드는 통째로 버리고 **금액·비율·기간 정규식 폴백**으로 내려간다.
- ⚠ **두 필드 모두 본문을 바꾸지 않는다.** "어디를 어떻게 그릴지"만 가리키므로,
  문구 변경이 금지된 `advice`에도 안전하게 붙는다. 못 찾으면 표시만 안 붙고 끝난다.
- ⚠ 마크다운(`**굵게**`)을 본문에 심는 방식은 **쓰지 않는다** — 그러면 검수한 문장과
  화면에 나가는 문장이 달라진다.

### 2.4 `QuestionGroup` / `QuestionItem` — 질문 생성기 화면
```
QuestionGroup {

### 2.5 `GlossaryTerm` / `GlossaryAnswer` — 용어 챗봇 화면 (S-12)

**`GlossaryTerm`** — 추천 칩 목록(`GET /api/glossary`)의 원소.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `term` | string | [메타] | 용어 (예: "신탁등기") |
| `description` | string | [설명] | 쉬운 설명 |

**`GlossaryAnswer`** — 챗봇 답 하나(`GET /api/glossary/lookup`). 2026-08-14 추가.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `answer` | string | [설명] | 화면에 그대로 그릴 문장. **거절 문구도 여기 들어온다** |
| `outOfScope` | bool | [메타] | true면 앱이 유도 버튼(리포트/분석)을 붙인다 |
| `source` | string | [메타] | 이 문장을 누가 썼나 — `"검수된 용어 사전"` \| 실제 모델명 \| `"준비된 문구"` |
| `termGlossary` | `{용어: 설명}` | [설명] | 답변에 등장한 어려운 말 (근거 카드와 **같은 메커니즘**) |
| `term` | string \| null | [메타] | 사전 직격일 때만 그 용어명. 자연어 답변·거절이면 null |
| `description` | string | [설명] | `answer`의 거울 — **옛 앱 호환용**(옛 앱은 `{term, description}`을 기대) |

- **거절도 답이다.** 예전에는 404가 나가고 앱이 거절 문구를 하드코딩했다. 이제 사전 답·LLM 답·거절이 **같은 모양**으로 나가고, 화면 문구는 전부 서버가 정한다.
- `source`는 **뭉뚱그리지 않는다** — 'AI 생성' 같은 말 대신 실제 모델 문자열을 쓴다(2026-08-14 D26과 같은 원칙). 앱은 이 값을 답변 아래 회색 한 줄로 그대로 보여준다.

### 2.6 `JourneyStage` / `JourneyItem` — 계약 여정 화면 (S-11)
```
JourneyStage {
  title:    string,         // [UI] 단계명 (예: "잔금 보내는 날")
  subtitle: string,         // [UI] 부제 (예: "가장 큰 돈이 나가는 날")
  items:    JourneyItem[],
  // ── 2026-08-14 S-11 재설계로 더해진 칸. 전부 선택이며 옛 앱은 무시해도 동작한다. ──
  kind:     string,         // [UI] "analysis" | "action" | "later"  (기본 "action")
  compare:  boolean,        // [UI] 이 단계에 [다시 떼서 대조하기]를 붙일지 (기본 false)
  askDates: boolean,        // [UI] 이 단계에서 계약 일정 입력을 권할지 (기본 false)

  why:  string              // [설명] "왜 해야 하나요?" 펼침 설명

- 여정 데이터는 **정적**(모든 사용자 동일)이고 정본은 `backend/data/journey_stages.json`이다(비개발 팀원이 직접 편집).

### 2.9 `CompareResult` — 등기부 대조 (2026-08-14 추가 · S-11)

**왜 있나**: 등기부는 뗀 시점의 스냅샷이라, 계약 직전에 새로 잡힌 근저당은 이전 서류에
없다(실제 전세사기 수법). 그래서 잔금 전에 **다시 떼어 기준 서류와 맞춰보는** 기능이다.

**무엇이 아닌가**: 새 판정이 아니다. 두 리포트의 등급은 각자 규칙 엔진이 이미 낸 것이고,
대조는 **그 둘과 추출 항목을 나란히 놓기만** 한다. LLM은 이 경로에 개입하지 않는다.

```
CompareResult {
  result:        string,        // "changed" | "partial" | "no_baseline" | "different_property"
  headline:      string,        // [규칙] 결론 한 줄
  subline:       string | null, // [규칙] 몇 가지를 맞춰봤는지 등
  baseline:      CompareDoc,    // 기준이 된 서류
  current:       CompareDoc,    // 이번에 뗀 서류 (다른 집이면 날짜만 채워진다)
  daysBetween:   integer | null,// 두 서류를 뗀 날의 차이. 한쪽이라도 못 읽으면 null
  comparedCount: integer,       // 맞춰본 항목 수
  totalCount:    integer,       // 맞춰보려던 항목 수 (집주인·빚·압류·안전도 = 4)
  rows:          CompareRow[],
  notices:       string[],      // 대조 자체에 대한 고지 (같은 집인지 확인 못 함 등)
  identityBasis: string | null, // 같은 집인지 무엇으로 확인했나 — "고유번호" | "소재지" | null
  newReportId:   string | null  // 이번 서류로 만들어진 리포트 id. **다른 집이면 null**
}
CompareDoc { reportId, alias, address, viewedAt, analyzedAt, grade, pageCount }  // 전부 nullable
CompareRow {
  kind:        string,        // added|removed|changed|same|unknown|grade
  tone:        string,        // danger|caution|neutral (색은 앱이 토큰으로 매핑)
  marker:      string,        // 카드 왼쪽 원 안 글자: + − ≠ = ? !
  title:       string,
  subtitle:    string | null,
  detail:      string | null, // 회색 상세 박스(줄바꿈으로 여러 줄). 첫 줄 = 건수·금액
  receiptDate: string | null, // 새로 생긴 항목의 접수일 YYYY-MM-DD (앱이 계약 일정과 견줌)
  gradeBefore: string | null,
  gradeAfter:  string | null,
  action:      string | null, // "recapture" | "analyze"
  actionLabel: string | null
}
```

네 갈래가 각각 언제 나오나 (**보수적 편향**이 이 표에 그대로 들어 있다):

| result | 조건 | 화면이 하는 일 |
|---|---|---|
| `changed` | 같은 집 + 모든 항목을 맞춰봄 | 변한 것과 **안 변한 것을 모두** 보여준다 |
| `partial` | 못 읽은 항목이 있거나 같은 집인지 확인 못 함 | 못 본 것을 `unknown`으로 말하고 "달라진 게 없다는 뜻이 아니에요" + 행동 버튼 |
| `no_baseline` | 기준 리포트에 추출 스냅샷이 없음(이 기능 이전 이력) | 비난이 아니라 초대 톤. **사진을 받기 전에** 나온다 |
| `different_property` | 고유번호(없으면 소재지·전용면적)가 다름 | **수치를 아예 렌더하지 않는다.** 이번 분석은 이력에서도 지운다 |

- 못 읽은 항목은 `same`이 아니라 **`unknown`**이다. 침묵이 "이상 없음"으로 읽히는 것이 이 화면의 가장 나쁜 실패다.
- 스냅샷에 **소유자 실명을 저장하지 않는다.** 비교는 프로세스마다 새로 만드는 소금을 섞은 해시로 하고, 화면에는 `김○○`만 나간다.

### 2.8 시세 출처 (2026-08-03 추가 — **additive only**)

기존 필드의 의미는 **하나도 바뀌지 않았다.** `marketPrice`는 여전히 "판정에 들어가는
집값 하나"이고, 달라진 것은 그 값이 사용자 입력 말고 **자동 조회**에서도 올 수 있다는 점뿐이다.
아래 필드는 전부 선택이며, 앱이 통째로 무시해도 예전과 똑같이 동작한다.

**왜 추가하나**: 숫자만 보여 주면 사용자는 그 값을 믿을지 판단할 수 없다.
"결론은 크게, 근거는 항상 공개"라는 원칙을 시세에도 적용한다.

`marketPriceSource` 값 (고정 어휘):

| 값 | 뜻 | 화면 문구(안) |
|---|---|---|
| `manual` | 사용자가 직접 넣은 값 | "직접 입력하신 값" |
| `actual_trade` | 국토부 실거래가 | "자동 조회 · 국토부 실거래가 (2026.2~7 · 5건)" |
| `official_price` | 공동주택 공시가격 × 140% | "자동 조회 · 공시가격 기준 (2025.1.1)" |
| `tax_base` | 국세청 오피스텔 기준시가 | "자동 조회 · 국세청 기준시가 (2026.1.1)" |
| `null` | 시세를 못 구함 | "자동 조회가 안 됐어요 · 직접 넣으면 더 정확해요" |

```
MarketPriceAlternative {
  source:      string,          // 위 고정 어휘
  sourceName:  string,          // 사람이 읽는 출처명
  price:       integer,         // 원
  asOf:        string | null,   // 기준일 또는 조회기간
  sampleCount: integer | null,
  detail:      string | null    // 매칭 방법 등
}
```

**채택 규칙 (서버)**: 후보가 여럿이면 **낮은 값**을 쓴다. 평균이 아니다.
시세를 높게 잡으면 전세가율이 낮게 나와 위험한 집을 안전하다고 말하게 된다(미탐).

**괴리(`marketPriceGapPct`)**: 실거래가와 공시 기준이 둘 다 있을 때만 온다.
실거래가는 조작할 수 있지만 공시가격은 정부가 매기므로, 실거래가만 유난히 높으면
신축 빌라 자전거래(시세 부풀리기)를 의심할 수 있다.
⚠ **판정 룰이 아니다** — 임계값의 권위 있는 출처가 없어 정보 계층에만 둔다.

**단독·다가구**: 이 유형은 `marketPrice`가 있어도 전세가율 근거 카드가 `"확인 필요"`로
고정된다(`statusLabel = "이 집 유형에는 쓸 수 없어요"`). 등기부가 건물 1개에 1부라
앞순위 세입자들의 보증금 합계를 알 수 없어, 낮은 전세가율이 안전 신호가 아니기 때문이다.

## 3. 엔드포인트 목록

### 3.1 `POST /api/analyze` — 등기부 분석 실행 · **인증 필요**
- **목적**: 등기부 사진 + 입력값으로 분석해 리포트를 만들어 반환한다(＋버튼 → 로딩 → 리포트).
- **인증**: 필요 (`Authorization: Bearer <token>`). 없으면 401.
- **요청** (`multipart/form-data`):

  | 파트 | 타입 | 필수 | 설명 |
  |---|---|---|---|
  | `files` | file[] (image/jpeg) | ✅ | 등기부 페이지 이미지 여러 장 (앱이 항상 JPEG로 변환해 전송) |
  | `deposit` | integer | ✅ | 예정 보증금(원) |
  | `marketPrice` | integer | ✖ | 매매 시세(원). 없으면 전세가율 근거가 "확인 필요"로 |
  | `alias` | string | ✖ | 매물 별칭. 없으면 서버가 표제부 주소를 별칭으로 |

- **응답 200**: `Report`(§2.1, `evidences` 포함) 하나.
- **참고**: 현행 검증 자산 `POST /api/upload`(이미지 1장 수신·메타데이터 반환)는 통신 파이프 검증용이며,
  이 계약에서는 `/api/analyze`가 그 역할을 대체·확장한다(부록 §8).

### 3.2 `GET /api/reports` — 분석 이력 목록 · **비회원 허용**
- **목적**: 홈 대시보드·마이의 최근 분석 이력.
- **인증**: 불필요. (비회원도 예시 리포트 2건을 봄 — "홈 둘러보기")
- **요청**: 없음.
- **응답 200**: `Report[]` (최신순). 홈은 앞의 3건 + 전체 보기, 마이는 전체.
  - 목록에서 홈/마이 카드가 실제 쓰는 필드는 §2.1 note 참고. (경량화를 위한 요약 응답은 향후 최적화 여지 — D-1은 앱 현행대로 전체 `Report` 반환.)

### 3.3 `GET /api/reports/{id}` — 리포트 단건 · **비회원 허용**
- **목적**: 안전도 리포트 화면(재열람 포함) + 손실 시뮬레이터의 데이터원.
- **인증**: 불필요. (예시 리포트 열람 허용)
- **응답 200**: `Report` 하나. **404**: 해당 id 없음 → 앱은 "이 리포트를 불러올 수 없어요".

### 3.4 `DELETE /api/reports/{id}` — 이력 삭제 · **인증 필요**
- **목적**: 마이 화면에서 이력 삭제.
- **인증**: 필요(개발 모드에서는 `get_current_user`가 항상 통과 — §1.2). 삭제는 분석과 한 몸이라
  로그인해서 분석한 사람만 자기 것을 지운다.
- **응답 204**: 성공(본문 없음). **404**: 없는 id. **403**: 예시 리포트(`dummy-danger`·`dummy-caution`) 삭제 시도.
- **참고**: 비회원이 보는 **예시 리포트는 조회만 허용**이며 삭제 대상이 아니다(홈 둘러보기 의도).

### 3.5 `GET /api/reports/{id}/cases` — 판례 매칭 · **비회원 허용**
- **목적**: 리포트의 위험 패턴에 매칭되는 판례 목록.
- **인증**: 불필요.
- **응답 200**: `CaseMatch[]`. **빈 배열 허용**(매칭 판례 없음 → 앱이 빈 상태 문구 표시). **404**: 없는 리포트 id.
- **참고**: 서버가 리포트의 `evidences`에서 위험 패턴을 파생(§2.2 note)해 매칭한다. 앱은 위험 패턴을 계산·전송하지 않는다.

### 3.6 `GET /api/reports/{id}/questions` — 중개사 질문 생성 · **비회원 허용**
- **목적**: 리포트의 위험 요소별 질문 그룹.
- **인증**: 불필요.
- **응답 200**: `QuestionGroup[]`. 위험 요소가 없어도 "어떤 집이든 꼭" 기본 그룹을 포함(빈 배열 아님). **404**: 없는 리포트 id.
- **참고**: 실단계 E-2에서 분석 결과 기반 LLM 생성으로 교체(판정 변경 금지). 위험 패턴 파생은 §2.2 note.

### 3.7 `GET /api/journey-stages` — 계약 여정 단계 · **비회원 허용**
- **목적**: 계약 여정의 정적 단계 목록(9단계).
- **인증**: 불필요.
- **응답 200**: `JourneyStage[]` (모든 사용자 동일). **날짜·진행 상태는 응답에 없다** — 일정은 기기에만 저장한다(§2.6).
- **데이터 정본**: `backend/data/journey_stages.json` (로더 `app/services/journey.py`). 파일이 깨지면 한국어 로그 + 최소 단계로 응답한다 — 여정 탭이 빈 화면이 되지 않게.

### 3.10 `POST /api/reports/{id}/compare` — 등기부 대조 · **인증 필요**
- **목적**: 기준 리포트의 등기부와 **이번에 뗀 등기부**를 맞춰본다 (S-11 화면 6).
- **인증**: 개발 모드 통과(§1.2).
- **요청**: `multipart/form-data`, 필드 `files`(이미지 여러 장). **사진 없이도 호출할 수 있다.**
- **처리**: 새 사진을 그대로 분석 파이프라인에 태워(**기준과 같은 보증금·시세**) 새 리포트를 만들고, 그 추출 스냅샷을 기준 스냅샷과 견준다. 등급 변화를 말할 수 있는 이유가 이것이다 — 두 등급 모두 규칙 엔진 산출물이다.
- **응답 200**: `CompareResult`(§2.9).
  - 기준 스냅샷이 없으면 **사진을 읽지 않고** `no_baseline`으로 답한다(찍게 해 놓고 마지막에 못 한다고 말하지 않기 위해 — 앱은 `Report.comparable`로 미리 안다).
  - `different_property`면 이번 분석을 **이력에서 지운다**. 기준 매물의 보증금으로 계산된 등급이라 그 집의 판정으로 쓸 수 없다.
- **에러**: **400** 기준은 있는데 사진이 없음 / **404** 없는 리포트 / **413** 파일 초과 / **402·429** Upstage 크레딧·한도(분석과 동일) / **503** 이번 서류의 스냅샷을 남기지 못함.
- **비용**: 대조 1회 = 분석 1회(IE + OCR). 그래서 기준이 없을 때는 호출 전에 걸러진다.

### 3.8 `GET /api/glossary` — 용어 목록(추천 칩) · **비회원 허용**
- **목적**: 용어 챗봇 진입 시 추천 질문 칩.
- **인증**: 불필요.
- **응답 200**: `GlossaryTerm[]`.

### 3.9 `GET /api/glossary/lookup?q={query}` — 챗봇 질문 · **비회원 허용**
- **목적**: 질문 하나에 답 하나. 용어·제도 설명만 하고, 판정·조언은 **거절**한다(가드레일).
- **인증**: 불필요.
- **요청**: 쿼리스트링 `q` = 사용자 입력 문자열.
- **응답 200**: `GlossaryAnswer`(§2.5). **404**: `q`가 비어 있을 때만(클라이언트 오류).
  - 2026-08-14 변경: **범위 밖도 404가 아니라 200 + `outOfScope=true`**로 나간다.
    앱이 거절 문구를 하드코딩하던 것을 없애기 위해서다(화면 문구는 서버가 정한다).
    옛 앱 호환을 위해 404 처리 경로는 앱·서버 양쪽에 남겨 두었다.

**통과 순서 (구현: `app/services/chat.py`)** — 이 순서가 설계의 전부다.

| 층 | 무엇 | LLM 호출 | 결과 |
|---|---|---|---|
| **L1** | 판정·조언·법률 요구 차단 (정규식) | **0회** | 거절 (`준비된 문구`) |
| **L2** | 검수된 용어 사전 직격 | **0회** | 사전 문장 **그대로** (`검수된 용어 사전`) |
| **L3** | 도메인 게이트 (terms.json에서 생성한 키워드) | **0회** | 부동산 얘기가 아니면 거절 |
| **L4** | Solar 설명 생성 + 검증 | 1회 | 통과분만 (`source`=모델명) |
| **L5** | 용어 툴팁 부착 (`termGlossary`) | — | 세 경로가 **합류한 뒤 한 곳에서** |

- **L1이 맨 앞인 이유**: "근저당 잡힌 이 집, 계약해도 돼요?"는 사전에도 걸리고 도메인 키워드도 있다. 판정 요구 게이트가 뒤에 있으면 그대로 새 나간다. **거절을 LLM에게 맡기지 않는다** — 프롬프트는 언젠가 뚫리지만 정규식은 안 뚫린다.
- **L4 검증** (`text_guard.check_chat`): 금지 표현·등급 단어(리포트와 **같은 패턴**) + 챗봇 전용 3개 —
  ⑴ **숫자 전면 금지**(챗봇에는 대조할 재료가 없어 화이트리스트를 만들 수 없다. 지어낸 `80%`가 판정 계층과 충돌하는 것을 구조로 막는다) ⑵ 200자 상한(넘으면 **자르지 않고 버린다**) ⑶ `out_of_scope=true`인데 answer가 있으면 answer를 버린다.
- **출력 스키마에 등급·점수·확률·금액 필드가 없다**(`extra="forbid"`). 리포트와 같은 경계다.
- **스위치**: `.env`의 `CHATBOT_LLM=off`면 L4를 통째로 건너뛴다 = AI 연결 이전과 완전히 같은 동작(사전 + 거절). 키 없음·타임아웃·JSON 깨짐·검증 실패도 전부 같은 자리로 떨어진다.
- **모델**: `LLM_CHAT_PROVIDER`(없으면 `LLM_EXPLAIN_PROVIDER` 상속, 기본 `upstage`) · temperature **0.3**(설명 생성 0.6보다 낮다 — 재료가 없어 창작 여지를 줄인다) · max_tokens 400.

## 9. 추가분 — 원본 사진 하이라이트 좌표 (2026-07-27, **채택 미확정**)

> **이 절은 기존 계약을 바꾸지 않는다.** `Report`에 **선택적 필드 1개**를 더할 뿐이며,
> 앱이 이 필드를 통째로 무시하면 지금과 **완전히 똑같이** 동작한다(기본값 빈 목록).
> 검증 기록은 `docs/ocr-highlight-findings.md`. 채택 여부는 아직 정해지지 않았다.

### 9.1 왜 추가하나

사용자가 **손에 든 등기부 종이와 앱 화면을 대조**할 수 있게 하려는 것이다. 은행원이
색연필로 동그라미 치듯, 사진 위에 확인해야 할 항목의 위치를 표시한다.

Information Extract는 필드를 구조화해주지만 **좌표를 주지 않는다.** 그래서 Document OCR을
함께 부르고, 두 결과를 매칭해 좌표를 만든다.

### 9.2 `Report`에 더해지는 필드

| 필드 | 타입 | 설명 |
|---|---|---|
| `highlights` | `Highlight[]` | **선택**. 사진 위 표시 목록. 좌표를 못 구하면 `[]` |
| `highlightNotice` | string? | 사진 묶음 안내 한 줄 (다른 등기부 섞임·쪽 누락·같은 쪽 중복). 없으면 `null` |
| `checkedNotes` | string[] | **"무엇을 찾아봤고 무엇을 왜 표시하지 않았는지"**. 9.7 참고 |
| `registryViewedAt` | string? | 등기부에 인쇄된 **열람일** `YYYY.MM.DD`. 못 읽으면 `null` — **앱은 분석일로 대체하지 않는다** |

기존 필드는 **하나도 바뀌지 않는다.**

### 9.3 `Highlight`

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | `owner-0`, `mortgage-1` 등 |
| `page` | int | **업로드한 사진 순서(0부터)**. 앱이 몇 번째 사진에 그릴지 |
| `kind` | string | **15종** (아래 9.3-a). ⚠ **앱은 모르는 값을 위험 톤으로 떨어뜨린다** |
| `badge` | int | 화면 뱃지 번호(1부터). 색만으로 정보를 전달하지 않기 위함(접근성) |
| `box` | `HighlightBox` | 정규화 좌표 |
| `title` | string | 시트 제목 (예: `소유자 이름 · 김○○`) |
| `body` | string | 사용자가 지금 할 행동 |
| `caution` | string? | 추가 주의 (예: 공동명의 전원 동의) |
| `source` | string? | 이 문장이 어디서 왔는지 (예: `등기부 갑구 — 이 앱이 사진에서 직접 찾은 위치`). 없으면 "앱이 그냥 하는 말"로 읽힌다 |

#### 9.3-a `kind` 목록 (2026-07-28 · 3종 → 15종)

**정본은 `backend/app/services/highlight.py`의 `_SPECS`다.** 여기는 계약 사본이다.
나열 순서 = **등기부를 읽는 순서**이고, 서버는 그 순서로 `badge`를 매긴다.

| kind | 톤 | 무엇 | 앵커 |
|---|---|---|---|
| `address` | 대조 | 소재지·동호수 | 표제부 주소 줄 (문서당 1곳) |
| `area` | 대조 | 전용면적 | IE 면적 ↔ ㎡ 있는 줄 |
| `separate_land` | 따져봄 | 토지 별도등기 | OCR 텍스트 (문서당 1곳) |
| `doc_title` | 대조 | 말소사항 포함 여부 | 표지 제목 줄 |
| `owner` | 대조 | 집주인 이름 | 등록번호 앞 word 1개 |
| `provisional_seizure` | 따져봄 | 가압류 | 3앵커 (순위+등기목적+청구금액) |
| `seizure` | 따져봄 | 압류 | **2앵커** (순위+등기목적) |
| `auction` | 따져봄 | 경매개시결정 | **2앵커** |
| `trust` | 따져봄 | 신탁등기 | **2앵커** |
| `mortgage` | 따져봄 | 근저당권 | 3앵커 (+채권최고액) |
| `jeonse` | 따져봄 | 전세권 | 3앵커 (+전세금) |
| `lease_registration` | 따져봄 | 임차권등기 | 3앵커 (+보증금) |
| `joint_collateral` | 따져봄 | 공동담보 | OCR 텍스트 (문서당 1곳) |
| `pending_application` | 따져봄 | 신청사건 처리중 | OCR 텍스트 (문서당 1곳) |
| `viewed_at` | 대조 | 서류를 뗀 날 | 꼬리말 열람일시 줄 |

**앱이 모르는 `kind`를 받으면**: **위험 톤(따져볼 곳)으로 취급한다.**
서버가 앱보다 먼저 새 종류를 내보낼 수 있는데, 모르는 것을 초록(대조할 곳)으로 칠하면
"확인만 하면 되는 것"으로 읽혀 경고를 놓친다. 미탐이 오탐보다 치명적이라는 보수적 편향
(risk-scoring 3절)을 여기에도 적용한다. 구현: `MarkKind.unknown`.

#### 9.3-b 표시 상한 — 종류당 5건

같은 `kind`가 5건을 넘으면 **서버가 상위 5건만 내보낸다**(금액 내림차순 → 금액이 없으면
순위번호 오름차순). 종류가 15개로 늘면서 압류 8건짜리 등기부는 갑구가 통째로 가로 띠가
되기 때문이다.

⚠ **표시 상한이지 판정 상한이 아니다.** 잘린 항목도 리포트 근거 카드에는 전부 있고,
**잘렸다는 사실을 `checkedNotes`로 반드시 알린다**(9.7).

### 9.4 `HighlightBox` — 정규화 좌표 (0~1)

| 필드 | 타입 | 설명 |
|---|---|---|
| `x`, `y` | float | 왼쪽 위 모서리 ÷ 원본 크기 |
| `w`, `h` | float | 폭·높이 ÷ 원본 크기 |

**왜 픽셀이 아니라 0~1인가**: 앱의 표시 크기는 기기·회전·줌에 따라 달라진다. 픽셀을 그대로
보내면 앱이 원본 크기를 따로 알아야 하고, 하나라도 어긋나면 좌표가 전부 밀린다.
서버는 **Pillow로 직접 읽은 원본 크기**로 나눈다(OCR 응답의 페이지 크기를 믿지 않는다).

앱은 `표시 좌표 = 정규화값 × 화면에 그린 이미지 크기` 로 되돌린다.
⚠ 앱이 화면에 띄우는 이미지는 **서버로 보낸 그 JPEG**여야 한다. 갤러리 원본을 띄우면
해상도가 달라 좌표가 전부 어긋난다.

### 9.5 좌표를 주지 않는 경우 (보수적 편향)

**틀린 위치에 칠하는 것보다 안 칠하는 것이 낫다.** 아래는 전부 "좌표 없음"으로 처리한다.

- **말소된 항목** — 사용자가 "이미 없어진 빚"을 현재 위험으로 오해하는 것이 최악의 오류다
- 앵커(순위번호 + 등기목적 + 금액)가 **같은 줄에 전부 있지 않을 때** (부분 매칭 금지)
- IE의 금액과 사진에서 읽은 금액이 다를 때
- 순위번호가 없을 때 (같은 금액이 여러 곳에 나와 항목을 지목할 수 없다)
- IE의 `current_owners`에 없는 이름 (지분을 넘긴 옛 소유자를 칠하면 임대인으로 오인한다)
- OCR 호출 실패 / 원본 크기를 못 읽음

### 9.6 판정과의 관계 — **완전 분리**

`highlights`는 **표시 전용**이다. 등급·점수·근거 카드에 어떤 영향도 주지 않는다.
IE ↔ OCR이 어긋나도 **판정은 바뀌지 않고 표시만 보류**된다.
(IE↔OCR 교차검증으로 등급을 바꾸는 것은 별도 승인 사항이며 구현돼 있지 않다.)

### 9.7 `checkedNotes` — "무엇을 찾아봤고 무엇을 왜 표시하지 않았는지"

**왜 있나**: 리포트에는 근저당이 4건인데 사진에는 3개만 표시되는 일이 흔하다(1건이 말소면
빠진다). 이 줄이 없으면 **개수가 안 맞는 이유를 화면 어디에서도 찾을 수 없다.**
2026-07-27 페르소나 2인의 공통 지적이 이것이었다 — **침묵이 신뢰를 깎는다.**

서버가 문장을 만들고 앱은 고르기만 한다. 지금 나가는 문장 종류:

| 상황 | 문장 예 |
|---|---|
| 말소로 제외 | `집에 잡힌 빚(근저당) 2건은 모두 말소된 것으로 확인해 표시하지 않았어요` |
| 위치 못 찾음 | `집주인 이름 1명은 리포트에 반영됐지만, 사진에서 위치를 찾지 못했어요` |
| **상한으로 생략** | `빚은 7건 중 큰 것부터 5건만 사진에 표시했어요. 나머지 2건은 화면이 가려져서 표시하지 않았어요` |
| **사진 순서 자동 정렬** | `사진 순서가 등기부 쪽수와 달라 자동으로 맞췄어요 — 다시 올리지 않으셔도 돼요` |
| **교차검증 일치** | `서류 내용을 2가지 방법으로 교차 확인했어요 — 빚(근저당) 3건 일치` |
| **교차검증 불일치** | `압류는 AI가 서로 다른 두 방법으로 읽었더니 개수가 달랐어요(3건 / 1건). 위험 계산은 더 많이 잡은 3건 기준으로 했어요.` |
| **두 번째 확인 실패** | `이번엔 한 가지 방법으로만 읽었어요 — 두 번째 확인은 하지 못했어요` |
| **못 본 쪽이 있음** | `못 본 쪽이 있어서 빚(근저당)이 없다고는 말할 수 없어요` |

⚠ **알려진 부채 (2026-07-28)**: 앱은 이 목록을 **문자열 포함 검사**로 고른다
(`kUnmarkedNoteMarkers`). 서버가 문구를 바꾸면 **조용히 화면에서 사라진다** — 실제로
오늘 만든 고지 3종이 전부 그렇게 탈락하고 있었고, 리뷰어 3인이 각각 찾아냈다.
**근본 해결은 서버가 분류 태그를 함께 보내는 것**(`{kind: "omitted"|"warn"|"ok", text}`)이고,
그건 이 계약을 바꾸는 일이라 **승인 후** 반영한다. 지금은 마커 목록을 늘려 막아 두었다.
