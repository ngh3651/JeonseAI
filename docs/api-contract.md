# 앱 ↔ 서버 JSON 계약서 (api-contract.md)

> **Phase D-1 산출물.** 앱(Flutter)과 서버(FastAPI)가 주고받을 데이터 형식을 확정한 문서입니다.
> 이 계약은 D-2(서버 더미 응답 구현)와 D-3(앱 연결)의 설계도이며, 나중에 실제 분석(Phase E)으로
> 교체될 때 **앱을 바꾸지 않고 서버 속만 바꾸기 위한** 기준점입니다(Repository 패턴).
>
> - 이 문서는 **"무엇을 주고받는가"만** 정의합니다. "어떻게 만드는가"(추출·판정 로직)는 담지 않습니다.
> - 모든 필드는 **Phase C 화면 코드에서 실제로 쓰는 데이터**를 역추출한 것입니다. 화면에 없는 필드는 넣지 않았습니다.
> - 옛 문서가 말하던 `docs/data-contract.md`가 바로 이 문서입니다(파일명은 api-contract.md로 확정).
>   이 계약과 코드가 다르면 **코드가 맞다** — 서버 `backend/app/schemas/contract.py`·`routers/`, 현재 상태는 `docs/NOW.md`.

## 0. 핵심 원칙 (계약에 반영된 가드레일)

1. **판정과 설명의 분리** — 위험 판정(등급·수치)은 규칙 엔진이, 설명 문장은 LLM이 만든다.
   그래서 응답의 각 필드에 **출처 태그**를 붙였다:
   - `[판정]` = 규칙 엔진이 만드는 값(등급·수치·상태). LLM이 못 바꾼다.
   - `[설명]` = LLM(Solar Pro)이 생성하는 문장. 판정을 바꾸지 않고 문장만.
   - `[메타]` = 식별·시각용 값(id·주소·시간·게이지 진행률 등).
   - `[UI]` = 앱이 그대로 노출하는 고정 라벨.
2. **보수적 편향** — 등급은 `위험 | 확인 필요 | 양호` 3단계이며, 데이터가 불충분하면
   `양호`로 단정하지 않고 항목 상태를 `확인 필요`로 표현한다(2번 §2, 근거 카드 `statusLabel`).
3. **Repository 교체** — 앱은 이 계약(무엇을)만 알고 서버 내부(어떻게)는 모른다.

## 1. 공통 규약

### 1.1 기본 주소
- Base URL: `http://127.0.0.1:8000` (실기기 `adb reverse tcp:8000 tcp:8000` 고정)
  - 클라우드(Railway) 배포 뒤에는 Railway가 만든 `https://…` 주소 (2026-10-21 서버 준비 완료 — `docs/NOW.md` 배포 방법).
  - **2026-10-22 앱**: 주소를 코드에 박지 않고 **빌드 때** 넣는다 — `flutter build apk --dart-define=API_BASE_URL=https://<주소>`
    (`frontend/lib/app/config.dart`). 안 넣으면 위 기본값. CI 'APK 빌드'는 저장소 변수 `API_BASE_URL`을 넣는다.

### 1.1-1 요청 헤더 (2026-10-21 추가 — 서버 1단계)

| 헤더 | 언제 | 값 | 없거나 틀리면 |
|---|---|---|---|
| `X-Device-Id` | 모든 `/api/*` (권장) | 앱이 처음 실행될 때 만들어 폰에 저장하는 id. `[A-Za-z0-9-]{8,64}` (예: UUID). `legacy-device`라는 값과 **`acct-`로 시작하는 값**(계정 주인 사칭, 대소문자 무시)은 직접 보낼 수 없다 | 형식이 틀리면 **400**. 없으면 공용 id `legacy-device`로 처리(옛 앱 호환 — **헤더 없는 앱은 전부 이 칸 하나를 함께 쓴다**: 서로의 기록이 보이고 속도 제한도 함께 쓴다) — 서버에 `REQUIRE_DEVICE_ID=1`이면 **400**. 새 앱이 나오면 바로 1로 켠다 |
| `X-App-Key` | 서버에 `APP_KEY`가 설정돼 있을 때 모든 `/api/*` | 서버의 `APP_KEY`와 같은 값(빌드 때 앱에 넣는다) | **401** (업로드를 읽기 전에 막는다 — 크레딧 0원) |
| `Authorization` | 카카오로 로그인했을 때 모든 `/api/*` (2026-10-22) | `Bearer <sessionToken>` (§3.15가 준 값) — 살아 있으면 기록의 주인 = **계정**(`acct-…`) | 틀리거나 만료·로그아웃·탈퇴된 세션이면 **401** `로그인이 끝났어요. 다시 로그인해 주세요` + 응답 헤더 `WWW-Authenticate: Bearer error="invalid_token"`. 빈 값이면 없는 것과 같다(둘러보기) |

- **앱이 보내는 방식 (2026-10-22, 앱 1단계)** — `frontend/lib/services/api_client.dart`의 `commonHeaders()` **한 곳**에서 붙인다:
  - `X-Device-Id`: **모든** `/api/*` 요청(JSON GET·DELETE·멀티파트 POST — 분석·대조·이력·삭제·판례·질문·용어·여정)에 싣는다.
    값 = 처음 실행 때 한 번 만든 **UUID v4**(소문자 36자), 폰의 SharedPreferences `device_id_v1`에 둔다(`services/device_id.dart`).
    앱을 지우면 새 id → 예전 기록과 끊긴다. 저장소를 못 쓰면 그 실행 동안만 같은 임시 id를 보낸다.
  - `X-App-Key`: 빌드 때 `--dart-define=APP_KEY=…`로 넣은 값이 **있을 때만** 싣는다(빈 값이면 헤더 자체를 안 보낸다).
  - `Authorization: Bearer <세션>`: 카카오로 로그인했을 때만(2026-10-22). 세션은 폰의 보안 저장소(`flutter_secure_storage`)에 둔다.
    로그인해도 `X-Device-Id`는 늘 싣는다(로그인하는 순간 이 기기의 기록을 계정으로 옮길 때 쓴다).
- `GET /`(헬스체크)는 두 헤더 없이도 열려 있다. `/docs`·`/openapi.json`도 헤더 없이 열리지만, 서버에 `DISABLE_DOCS=1`이면 **404**(공개 배포에서 끈다).
- **기기별 기록**: 리포트·대조 기준·판례 캐시는 그 리포트를 만든 **주인의 것**이다 — 로그인했으면 계정, 아니면 기기 id. 목록·단건·삭제·대조·판례·질문은
  호출한 주인의 기록만 보며, **다른 주인의 리포트 id는 404**다(있다/없다를 구분해 주지 않는다).
  예시 리포트 `dummy-example`만 모든 기기에 보이고, 삭제는 403.
- 헤더 이름은 대소문자를 가리지 않는다(HTTP 규칙).

### 1.2 인증 (확정된 규칙)
- **지금 서버가 실제로 하는 일 (2026-10-22 카카오 로그인)**: 모든 `/api/*`가 ⑴ `X-App-Key`(서버에 `APP_KEY`가 있을 때, 틀리면 401)
  ⑵ `Authorization: Bearer <세션>`(있으면 검사 — 살아 있으면 주인 = 계정, 틀리면 401) ⑶ `X-Device-Id`(세션이 없을 때의 주인)를 본다.
  주인은 `get_current_user`(`backend/app/dependencies.py`) **한 곳**이 정하고, 라우터는 그 반환값으로만 "누구의 기록인가"를 판단한다.
- **로그인 없이 둘러보기**(세션 없음 = 기기 id)도 모든 기능이 된다 — 분석·대조 포함. 부스에서 카카오가 막혀도 분석은 돼야 한다.
- 카카오에서는 **회원번호만** 받는다(서버가 토큰 정보 API로 확인). 회원번호 원문은 DB·로그·응답 어디에도 남기지 않는다 —
  계정 키 = HMAC-SHA256(`ACCOUNT_HASH_SECRET`, `"kakao:"+회원번호`), 주인 = `acct-` + 계정 키 앞 32자리.
- 예전의 `DEV_MODE_AUTH` 상수(인증 우회 + 실명 원응답 저장을 함께 켜던 스위치)는 없어졌다 — 원응답 저장은 서버 환경변수
  `SAVE_RAW_RESPONSES`(기본 꺼짐)로 분리됐다.
- **앱 쪽 기획 의도는 유지**: 화면상 둘러보는 사람이 분석하려 하면 로그인 유도가 뜬다 — 단 [로그인 없이 분석하기]로 그대로 갈 수 있다
  (카카오 키가 없는 빌드는 유도 없이 바로). 서버는 관여하지 않는다.
- 로그인 엔드포인트: §3.15~§3.18 (2026-10-22). 따로 회원가입은 없다 — 처음 카카오로 로그인하면 계정이 생긴다.

### 1.3 에러 형식 (일관)
모든 에러는 HTTP 상태 코드 + 아래 JSON으로 반환한다(FastAPI 기본 `HTTPException` 형식).

```json
{ "detail": "사용자에게 보여줄 한국어 메시지" }
```

| 상태 | 의미 |
|---|---|
| 400 | 잘못된 요청(형식 오류 등). `X-Device-Id` 형식 오류 → `기기 정보 형식이 올바르지 않아요` / 필수인데 없음 → `기기 정보가 없어요. 앱을 최신 버전으로 업데이트해 주세요` |
| 400 | 사진이 20장을 넘음(분석·대조) → `사진이 너무 많아요. 한 번에 20장까지 올릴 수 있어요` (내용을 읽기 전에 거절 — OCR 호출 0회) |
| 401 | 앱 키(`X-App-Key`)가 없거나 틀림 → `앱 인증 정보가 맞지 않아요. 앱을 최신 버전으로 업데이트해 주세요` (§1.1-1) |
| 401 | **세션**이 틀리거나 만료·로그아웃·탈퇴됨 → `로그인이 끝났어요. 다시 로그인해 주세요` + `WWW-Authenticate: Bearer error="invalid_token"` (앱은 이 헤더로 앱 키 401과 가른다 → 세션을 지우고 로그인 안내) |
| 401 | 카카오 토큰이 우리 앱의 것이 아니거나 만료(§3.15) → `카카오 로그인을 확인하지 못했어요. 다시 로그인해 주세요` / 로그인 없이 탈퇴(§3.18) → `로그인한 뒤에 탈퇴할 수 있어요` |
| 502 | 카카오에 닿지 못함(§3.15) → `카카오에 연결하지 못했어요. 잠시 후 다시 시도해 주세요` |
| 503 | 서버에 `KAKAO_APP_ID`·`ACCOUNT_HASH_SECRET`(32자 이상)이 없음(§3.15) → `카카오 로그인이 아직 준비되지 않았어요` (둘러보기는 그대로) |
| 403 | 금지된 동작 (예: 예시 리포트 삭제 시도 — §3.4) |
| 404 | 리소스 없음(리포트 id 없음, 용어 질문이 빈 문자열). 범위 밖 질문은 404가 아니라 200 + `outOfScope` (§3.9) |
| 413 | 업로드 용량 초과 |
| 429 | 분석·대조를 너무 자주 함 — 최근 1시간 **세 겹 상한**을 모두 통과해야 한다: 기기 id × IP(`RATE_LIMIT_ANALYZE_PER_HOUR`, 기본 30) · IP 하나(`RATE_LIMIT_IP_PER_HOUR`, 기본 60) · 서버 전체(`RATE_LIMIT_GLOBAL_PER_HOUR`, 기본 300) → `분석을 너무 자주 했어요. 한 시간쯤 뒤에 다시 시도해 주세요`. 여기에 **서버 전체 하루(최근 24시간) 상한**(`RATE_LIMIT_GLOBAL_PER_DAY`, 기본 500, 2026-10-22)이 한 겹 더 있다 → `오늘은 서버의 하루 분석 횟수를 다 썼어요. 내일 다시 시도해 주세요`. 입력 검사에서 거절된 요청(400·404·413·422)과 '기준 없음' 대조는 세지 않는다. (Upstage 크레딧·한도 문제의 429도 같은 코드로 나간다) |
| 5xx | 서버 오류 (앱은 "잠깐 문제가 생겼어요"로 표시) |

- **앱이 보여 주는 말 (2026-10-22)** — `api_client.dart`의 `apiExceptionFor`. 사용자가 **할 수 있는 일**로 끝나게 바꾼다:
  - **401** → `앱 인증에 실패했어요. 최신 앱을 설치해 주세요` · **400 중 `기기 정보…`** → `기기 정보에 문제가 있어 서버가 요청을 받지 않았어요. 최신 앱을 설치해 주세요`.
    둘 다 다시 시도·사진 교체로 풀리지 않으므로 분석·대조 실패 화면에서 '다시 시도'·'사진 다시 고르기'를 감춘다.
  - **세션 401**(`invalid_token`, 2026-10-22) → 세션을 지우고 `로그인이 끝났어요. 다시 로그인해 주세요` + 화면 아래 [로그인] 한 줄.
    그 밖의 401(카카오 토큰 거절 등)은 서버 `detail` 그대로.
  - **429 중 `너무 자주`(우리 서버의 횟수 제한)** → `잠시 후 다시 시도해 주세요. 분석은 1시간에 정해진 횟수까지만 할 수 있어요`.
  - 그 밖의 400(요약본 거부 등)·Upstage 쪽 429는 서버 `detail` 그대로(이미 정확한 행동을 말한다).

### 1.4 값 표기
- **금액**: 정수, 단위는 **원**(예: `120000000` = 1억 2천만원). 앱이 "만원" 입력을 원으로 변환해 보낸다.
- **날짜/시간**: ISO 8601 문자열(예: `"2026-06-27T09:00:00+09:00"`). 앱이 "2026.06.27"·"7일 전"으로 표시.
- **등급 문자열**(`grade`): `"위험"` | `"확인 필요"` | `"양호"` (공백 포함, 앱 enum 라벨과 동일).
  - 등급별 **색·의사결정 문구는 앱이 grade로부터 파생**한다(아래 표). 서버는 `grade`만 보내면 된다.

  | grade | 의사결정 문구(앱 파생) | 색(앱 파생) |
  |---|---|---|
  | 위험 | 계약을 피하는 것을 권해요 | 빨강 |
  | 확인 필요 | 보류하고 아래 항목을 먼저 확인하세요 | 주황 |
  | 양호 | 진행을 검토할 수 있어요 — 단, 직접 확인은 꼭 필요해요 | 초록 |

## 2. 공통 데이터 모델

여러 엔드포인트에서 재사용하는 객체들이다.

### 2.1 `Report` — 안전도 리포트 (핵심)
홈 카드·리포트 화면·시뮬레이터가 공유한다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 리포트 식별자 (예: `"analysis-1720000000000"`) |
| `alias` | string | [메타] | 매물 별칭. 미입력 시 `address`가 기본값 |
| `address` | string | [메타] | 표제부 소재지 주소 |
| `analyzedAt` | string(ISO8601) | [메타] | 분석 시각 |
| `grade` | string | [판정] | 위험도 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `gaugeProgress` | number | [메타] | 게이지 시각 진행률 0.0~1.0 (점수 체계는 E-1에서 확정) |
| `headline` | string | [설명] | 결론 한 줄 (예: "보증금을 지키기 어려운 신호가 보여요") |
| `nextAction` | string | [설명] | "지금 해야 할 일" 한 문장 |
| `topRiskSummary` | string | [설명] | 최대 위험 요인 한 줄 — 홈/마이 이력 카드 3번째 줄 |
| `deposit` | integer | [판정] | 예정 보증금(원) — 사용자 입력 |
| `marketPrice` | integer \| null | [판정] | 매매 시세(원). null이면 전세가율 근거는 "확인 필요" |
| `marketPriceSource` | string \| null | [표시] | 시세 출처 — §2.8 (2026-08-03 추가, 선택) |
| `marketPriceAsOf` | string \| null | [표시] | 기준일(`"2025-01-01"`) 또는 조회기간(`"2026-02~2026-07"`) |
| `marketPriceSampleCount` | integer \| null | [표시] | 실거래가일 때 표본 수 |
| `marketPriceGapPct` | integer \| null | [표시] | 실거래가가 공시 기준보다 몇 % 높은지. **판정에 쓰지 않는다** |
| `marketPriceAlternatives` | `MarketPriceAlternative[]` | [표시] | 채택되지 않은 시세 후보들 (기본 `[]`) |
| `seniorDebtAmount` | integer | [판정] | 선순위 채권 합계(원) — 손실 시뮬레이터 입력 |
| `evidences` | `Evidence[]` | — | 근거 카드 목록(§2.2) |
| `highlights` | `Highlight[]` | [표시] | 원본 사진 위 표시 — §9 (기본 `[]`) |
| `highlightNotice` | string \| null | [표시] | 사진 묶음 안내 한 줄 — §9 |
| `checkedNotes` | string[] | [표시] | "무엇을 찾아봤나" 요약 — §9 (기본 `[]`) |
| `registryViewedAt` | string \| null | [표시] | 등기부 열람일시 `YYYY.MM.DD` — §9 |
| `propertyId` | string \| null | [메타] | 부동산고유번호 **숫자만**(10자리 이상, 못 읽으면 `null`) — 같은 집 묶기의 첫 기준(둘 다 있으면 이것만, 아니면 도로명 병기를 뗀 주소). 화면에 안 보임 (2026-10-27) |
| `comparable` | boolean | [메타] | 이 분석을 **다음 등기부와 견줄 기준으로 쓸 수 있는가** — §2.9 (기본 `false`) |

- **파생 값(전송 안 함)**: 등급별 `decisionLabel`·색은 앱이 `grade`로 파생. `riskLabels`(위험 패턴 목록)는 `evidences`에서 파생(§2.2 note).

### 2.2 `Evidence` — 근거 카드 한 항목
리포트 화면의 접힘/펼침 카드. `evidences` 배열의 원소.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 항목 식별자: `jeonse_ratio` \| `senior_debt` \| `ownership` \| `insurance` \| `blacklist` |
| `title` | string | [설명] | 쉬운 질문형 제목 (예: "나보다 먼저 돈 받아갈 빚이 있나요?") |
| `termSubtitle` | string | [UI] | 전문용어 부제 (예: "선순위 채권 · 근저당권") |
| `grade` | string | [판정] | 이 항목의 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `statusLabel` | string \| null | [판정] | 등급 대신 표시할 상태 (예: "확인 필요", "페이지 누락"). null이면 grade 라벨 사용 |
| `easyExplanation` | string | [설명] | 펼침 1단: 쉬운 설명 (LLM 생성 슬롯 — 판정 변경 금지) |
| `detailText` | string \| null | [판정] | 펼침 2단: 상세 수치를 사람이 읽게 포맷한 문자열 (예: "채권최고액 1억 8,000만원 · 근저당권 2건") |
| `sourceText` | string \| null | [판정] | 판정 출처 (예: "HUG 공식 기준 등 확정 예정" — E-1에서 실제 출처로 교체) |
| `actionLabel` | string \| null | [UI] | 다음 행동 버튼 라벨 (예: "중개사에게 물어볼 질문 보기", "시세 입력하기"). null이면 버튼 없음 |
| `termGlossary` | object(map) | [설명] | `easyExplanation` 속 용어→툴팁 설명. 키=용어, 값=설명 문장 (예: `{"근저당권":"집주인이 …"}`) |
| `explanationSource` | string? | [설명] | **이 카드의 설명 문장을 누가 썼는가** (2026-08-14 D26 추가 · additive). LLM이 쓴 문장이면 **실제 호출된 모델 문자열**(예: `"solar-pro2"`), 검증에 걸려 미리 준비한 문장이 나갔으면 `"준비된 문구"`. 없으면(옛 리포트) 앱이 종전 라벨 `자동 생성`을 쓴다 |

- ⚠ `explanationSource`는 **판정 출처가 아니다.** 판정은 언제나 규칙 엔진이고 그 출처는 `sourceText`다.
  설명 계층에만 해당하며, **카드마다 다를 수 있다** — 설명 폴백이 필드 단위라 한 리포트 안에서
  어떤 카드는 모델 문장, 어떤 카드는 준비된 문구가 된다.
- ⚠ 한 카드 안에서 경로가 섞이면 **`"준비된 문구"`로 내린다**(과대 표기 금지 · 보수 편향).

- **위험 패턴 파생(중요)**: 판례·질문 엔드포인트가 쓰는 "위험 패턴"은 `evidences` 중 `grade ≠ 양호`인
  항목의 `id`를 아래로 매핑해 만든다. **앱은 이 파생을 하지 않아도 되며(서버가 리포트 id로 계산)**,
  파생 규칙만 계약에 남긴다:
  `senior_debt→선순위 채권`, `ownership→신탁등기`, `jeonse_ratio→전세가율`, `insurance→보증보험`.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|

| `advice` | string? | [큐레이션] | "이런 피해를 피하려면". **LLM이 만들거나 고치지 않는다** |
| `curated` | bool | [메타] | 사람이 문구까지 검수했는지. 출처 확인(`source_verified`)과는 다른 축 |

**읽기 보조 추가 (2026-08-14 D20·D23) — additive only.** 옛 앱은 두 필드를 무시해도 그대로 동작한다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `termGlossary` | `{string: string}` | [큐레이션] | 본문에 등장한 어려운 말 → 쉬운 설명. **§2.2 `EvidenceItem.termGlossary`와 같은 구조·같은 규칙** |
| `emphasis` | `{string: string[]}` | [설명] | `{필드명: [굵게 그릴 부분 문자열]}`. 필드명은 이 모델 이름 그대로 — `result` · `commonPoint` · `advice` |

- `termGlossary`의 키는 **본문에 글자 그대로 있어야** 한다. 앱이 `indexOf`로 찾아 점선 밑줄을
  붙이기 때문이다(근거 카드와 동일 전제). 서버는 검수된 용어(`terms.json` `verified=true`)만 내린다.
- `emphasis`의 각 문자열도 **해당 필드 본문의 정확한 부분 문자열**이다. Solar가 고르고
  서버가 검증한다(부분 문자열 일치 · 필드당 2개 이하 · 항목당 30자 이하 · 굵은 글자 합이 본문의 30% 이하).
  하나라도 어기면 그 필드는 통째로 버리고 **금액·비율·기간 정규식 폴백**으로 내려간다.
- ⚠ **두 필드 모두 본문을 바꾸지 않는다.** "어디를 어떻게 그릴지"만 가리키므로,
  문구 변경이 금지된 `advice`에도 안전하게 붙는다. 못 찾으면 표시만 안 붙고 끝난다.
- ⚠ 마크다운(`**굵게**`)을 본문에 심는 방식은 **쓰지 않는다** — 그러면 검수한 문장과
  화면에 나가는 문장이 달라진다.

### 2.9 `CompareResult` — 등기부 대조 (2026-08-14 추가 · S-11)

**왜 있나**: 등기부는 뗀 시점의 스냅샷이라, 계약 직전에 새로 잡힌 근저당은 이전 서류에
없다(실제 전세사기 수법). 그래서 잔금 전에 **다시 떼어 기준 서류와 맞춰보는** 기능이다.

**무엇이 아닌가**: 새 판정이 아니다. 두 리포트의 등급은 각자 규칙 엔진이 이미 낸 것이고,
대조는 **그 둘과 추출 항목을 나란히 놓기만** 한다. LLM은 이 경로에 개입하지 않는다.

```
CompareResult {
  result:        string,        // "changed" | "partial" | "no_baseline" | "different_property"
  headline:      string,        // [규칙] 결론 한 줄
  subline:       string | null, // [규칙] 몇 가지를 맞춰봤는지 등
  baseline:      CompareDoc,    // 기준이 된 서류
  current:       CompareDoc,    // 이번에 뗀 서류 (다른 집이면 날짜만 채워진다)
  daysBetween:   integer | null,// 두 서류를 뗀 날의 차이. 한쪽이라도 못 읽으면 null
  comparedCount: integer,       // 맞춰본 항목 수
  totalCount:    integer,       // 맞춰보려던 항목 수 (집주인·빚·압류·안전도 = 4)
  rows:          CompareRow[],
  notices:       string[],      // 대조 자체에 대한 고지 (같은 집인지 확인 못 함 등)
  identityBasis: string | null, // 같은 집인지 무엇으로 확인했나 — "고유번호" | "소재지" | null
  newReportId:   string | null  // 이번 서류로 만들어진 리포트 id. **다른 집이면 null**
}
CompareDoc { reportId, alias, address, viewedAt, analyzedAt, grade, pageCount, propertyId }  // 전부 nullable
CompareRow {
  kind:        string,        // added|removed|changed|same|unknown|grade
  tone:        string,        // danger|caution|neutral (색은 앱이 토큰으로 매핑)
  marker:      string,        // 카드 왼쪽 원 안 글자: + − ≠ = ? !
  title:       string,
  subtitle:    string | null,
  detail:      string | null, // 회색 상세 박스(줄바꿈으로 여러 줄). 첫 줄 = 건수·금액
  receiptDate: string | null, // 새로 생긴 항목의 접수일 YYYY-MM-DD (앱이 계약 일정과 견줌)
  gradeBefore: string | null,
  gradeAfter:  string | null,
  action:      string | null, // "recapture" | "analyze"
  actionLabel: string | null,
  group: string | null       // owner(갑구 소유자) | seizure(갑구 압류·가압류) | debt(을구 빚) | grade(안전도) — 앱이 두 줄로 묶는다(2026-10-26)
}
```

네 갈래가 각각 언제 나오나 (**보수적 편향**이 이 표에 그대로 들어 있다):

| result | 조건 | 화면이 하는 일 |
|---|---|---|
| `changed` | 같은 집 + 모든 항목을 맞춰봄 | 변한 것과 **안 변한 것을 모두** 보여준다 |
| `partial` | 못 읽은 항목이 있거나 같은 집인지 확인 못 함 | 못 본 것을 `unknown`으로 말하고 "달라진 게 없다는 뜻이 아니에요" + 행동 버튼 |
| `no_baseline` | 기준 리포트에 추출 스냅샷이 없음(이 기능 이전 이력) | 비난이 아니라 초대 톤. **사진을 받기 전에** 나온다 |
| `different_property` | 고유번호(없으면 소재지·전용면적)가 다름 | **수치를 아예 렌더하지 않는다.** 이번 분석은 이력에서도 지운다 |

- 못 읽은 항목은 `same`이 아니라 **`unknown`**이다. 침묵이 "이상 없음"으로 읽히는 것이 이 화면의 가장 나쁜 실패다.
- 스냅샷에 **소유자 실명을 저장하지 않는다.** 비교는 프로세스마다 새로 만드는 소금을 섞은 해시로 하고, 화면에는 `김○○`만 나간다.
- `action: "recapture"`(2026-10-23) = **빠진 쪽만 더 찍기**. 서버는 이전 요청의 사진을 갖고 있지 않으므로(원본 사진을 저장하지 않는다)
  앱이 **먼저 올린 사진 + 새 사진을 합쳐** 같은 주소(`POST /api/reports/{id}/compare`)로 다시 보낸다 — 계약은 그대로다.
  순서는 서버가 쪽 번호(N/M)로 다시 맞춘다. 라벨은 `"빠진 쪽만 더 찍기"`(앱은 이 버튼 라벨을 화면 전체에서 하나로 맞춘다).
  사진을 통째로 바꾸는 것은 `different_property`의 '사진 다시 고르기'뿐이다.

### 2.8 시세 출처 (2026-08-03 추가 — **additive only**)

기존 필드의 의미는 **하나도 바뀌지 않았다.** `marketPrice`는 여전히 "판정에 들어가는
집값 하나"이고, 달라진 것은 그 값이 사용자 입력 말고 **자동 조회**에서도 올 수 있다는 점뿐이다.
아래 필드는 전부 선택이며, 앱이 통째로 무시해도 예전과 똑같이 동작한다.

**왜 추가하나**: 숫자만 보여 주면 사용자는 그 값을 믿을지 판단할 수 없다.
"결론은 크게, 근거는 항상 공개"라는 원칙을 시세에도 적용한다.

`marketPriceSource` 값 (고정 어휘):

| 값 | 뜻 | 화면 문구(안) |
|---|---|---|
| `manual` | 사용자가 직접 넣은 값 | "직접 입력하신 값" |
| `actual_trade` | 국토부 실거래가 | "자동 조회 · 국토부 실거래가 (2026.2~7 · 5건)" |
| `official_price` | 공동주택 공시가격 × 140% | "자동 조회 · 공시가격 기준 (2025.1.1)" |
| `tax_base` | 국세청 오피스텔 기준시가 | "자동 조회 · 국세청 기준시가 (2026.1.1)" |
| `null` | 시세를 못 구함 | "자동 조회가 안 됐어요 · 직접 넣으면 더 정확해요" |

```
MarketPriceAlternative {
  source:      string,          // 위 고정 어휘
  sourceName:  string,          // 사람이 읽는 출처명
  price:       integer,         // 원
  asOf:        string | null,   // 기준일 또는 조회기간
  sampleCount: integer | null,
  detail:      string | null    // 매칭 방법 등
}
```

**채택 규칙 (서버)**: 후보가 여럿이면 **낮은 값**을 쓴다. 평균이 아니다.
시세를 높게 잡으면 전세가율이 낮게 나와 위험한 집을 안전하다고 말하게 된다(미탐).

**괴리(`marketPriceGapPct`)**: 실거래가와 공시 기준이 둘 다 있을 때만 온다.
실거래가는 조작할 수 있지만 공시가격은 정부가 매기므로, 실거래가만 유난히 높으면
신축 빌라 자전거래(시세 부풀리기)를 의심할 수 있다.
⚠ **판정 룰이 아니다** — 임계값의 권위 있는 출처가 없어 정보 계층에만 둔다.

**단독·다가구**: 이 유형은 `marketPrice`가 있어도 전세가율 근거 카드가 `"확인 필요"`로
고정된다(`statusLabel = "이 집 유형에는 쓸 수 없어요"`). 등기부가 건물 1개에 1부라
앞순위 세입자들의 보증금 합계를 알 수 없어, 낮은 전세가율이 안전 신호가 아니기 때문이다.

## 3. 엔드포인트 목록

### 3.1 `POST /api/analyze` — 등기부 분석 실행 · **인증 필요**
- **목적**: 등기부 사진 + 입력값으로 분석해 리포트를 만들어 반환한다(＋버튼 → 로딩 → 리포트).
- **인증**: 주인이 있으면 된다(§1.2) — 로그인했으면 `Authorization: Bearer <세션>`(계정), 아니면 `X-Device-Id`(둘러보기). `X-App-Key`(설정 시).
  주인(계정 또는 기기)×IP별 1시간 상한을 넘으면 **429**(§1.3).
- **요청** (`multipart/form-data`):

  | 파트 | 타입 | 필수 | 설명 |
  |---|---|---|---|
  | `files` | file[] (image/jpeg) | ✅ | 등기부 페이지 이미지 여러 장 (앱이 항상 JPEG로 변환해 전송) |
  | `deposit` | integer | ✅ | 예정 보증금(원) |
  | `marketPrice` | integer | ✖ | 매매 시세(원). 없으면 전세가율 근거가 "확인 필요"로 |
  | `alias` | string | ✖ | 매물 별칭. 없으면 서버가 표제부 주소를 별칭으로 |

- **응답 200**: `Report`(§2.1, `evidences` 포함) 하나.
- **참고**: 옛 통신 검증용 `POST /api/upload`는 2026-10-26에 지웠다 — `/api/analyze`가 그 역할을 대체했다.

### 3.2 `GET /api/reports` — 분석 이력 목록 · **비회원 허용**
- **목적**: 홈 대시보드·마이의 최근 분석 이력.
- **인증**: 불필요. (비회원도 예시 리포트 `dummy-example` 1건을 봄 — "홈 둘러보기")
- **요청**: 없음. 헤더 `X-Device-Id`(§1.1-1).
- **응답 200**: `Report[]` — **이 기기의 기록**(최신순) + 맨 끝에 예시 리포트. 다른 기기의 기록은 섞이지 않는다. 홈은 앞의 3건 + 전체 보기, 마이는 전체.
  - 목록에서 홈/마이 카드가 실제 쓰는 필드는 §2.1 note 참고. (경량화를 위한 요약 응답은 향후 최적화 여지 — D-1은 앱 현행대로 전체 `Report` 반환.)

### 3.3 `GET /api/reports/{id}` — 리포트 단건 · **비회원 허용**
- **목적**: 안전도 리포트 화면(재열람 포함) + 손실 시뮬레이터의 데이터원.
- **인증**: 불필요. (예시 리포트 열람 허용) 헤더 `X-Device-Id`(§1.1-1).
- **응답 200**: `Report` 하나(이 기기의 것 또는 예시). **404**: 해당 id 없음 **또는 다른 기기의 리포트** → 앱은 "이 리포트를 불러올 수 없어요".

### 3.4 `DELETE /api/reports/{id}` — 이력 삭제 · **인증 필요**
- **목적**: 마이 화면에서 이력 삭제.
- **인증**: **그 리포트의 주인만** 지울 수 있다(§1.2 — 로그인했으면 계정, 아니면 `X-Device-Id` 기기) —
  다른 주인의 리포트 id는 **404**(있는지조차 알려 주지 않는다). 헤더 없는 옛 앱끼리는 `legacy-device` 칸을 함께 쓰므로 서로 지울 수 있다.
- **응답 204**: 성공(본문 없음). **404**: 없는 id 또는 다른 주인의 리포트. **403**: 예시 리포트(`dummy-example`) 삭제 시도.
- **참고**: 비회원이 보는 **예시 리포트는 조회만 허용**이며 삭제 대상이 아니다(홈 둘러보기 의도).

### 3.5 `GET /api/reports/{id}/cases` — 판례 매칭 · **비회원 허용**
- **목적**: 리포트의 위험 패턴에 매칭되는 판례 목록.
- **인증**: 불필요.
- **응답 200**: `CaseMatch[]`. **빈 배열 허용**(매칭 판례 없음 → 앱이 빈 상태 문구 표시). **404**: 없는 리포트 id.
- **참고**: 서버가 리포트의 `evidences`에서 위험 패턴을 파생(§2.2 note)해 매칭한다. 앱은 위험 패턴을 계산·전송하지 않는다.

### 3.6 `GET /api/reports/{id}/questions` — 중개사 질문 생성 · **비회원 허용**
- **목적**: 리포트의 위험 요소별 질문 그룹.
- **인증**: 불필요.
- **응답 200**: `QuestionGroup[]`. 위험 요소가 없어도 "어떤 집이든 꼭" 기본 그룹을 포함(빈 배열 아님). **404**: 없는 리포트 id.
- **참고**: 실단계 E-2에서 분석 결과 기반 LLM 생성으로 교체(판정 변경 금지). 위험 패턴 파생은 §2.2 note.

### 3.7 `GET /api/journey-stages` — 계약 여정 단계 · **비회원 허용**
- **목적**: 계약 여정의 정적 단계 목록(9단계).
- **인증**: 불필요.
- **응답 200**: `JourneyStage[]` (모든 사용자 동일). **날짜·진행 상태는 응답에 없다** — 일정은 기기에만 저장한다(§2.6).
- **데이터 정본**: `backend/data/journey_stages.json` (로더 `app/services/journey.py`). 파일이 깨지면 한국어 로그 + 최소 단계로 응답한다 — 여정 탭이 빈 화면이 되지 않게.

### 3.10 `POST /api/reports/{id}/compare` — 등기부 대조 · **인증 필요**
- **목적**: 기준 리포트의 등기부와 **이번에 뗀 등기부**를 맞춰본다 (S-11 화면 6).
- **인증**: 개발 모드 통과(§1.2).
- **요청**: `multipart/form-data`, 필드 `files`(이미지 여러 장). **사진 없이도 호출할 수 있다.**
- **처리**: 새 사진을 그대로 분석 파이프라인에 태워(**기준과 같은 보증금·시세**) 새 리포트를 만들고, 그 추출 스냅샷을 기준 스냅샷과 견준다. 등급 변화를 말할 수 있는 이유가 이것이다 — 두 등급 모두 규칙 엔진 산출물이다.
- **응답 200**: `CompareResult`(§2.9).
  - 기준 스냅샷이 없으면 **사진을 읽지 않고** `no_baseline`으로 답한다(찍게 해 놓고 마지막에 못 한다고 말하지 않기 위해 — 앱은 `Report.comparable`로 미리 안다).
  - `different_property`면 이번 분석을 **이력에서 지운다**. 기준 매물의 보증금으로 계산된 등급이라 그 집의 판정으로 쓸 수 없다.
- **에러**: **400** 기준은 있는데 사진이 없음 / **404** 없는 리포트 / **413** 파일 초과 / **402·429** Upstage 크레딧·한도(분석과 동일) / **503** 이번 서류의 스냅샷을 남기지 못함.
- **비용**: 대조 1회 = 분석 1회(IE + OCR). 그래서 기준이 없을 때는 호출 전에 걸러진다.

### 3.8 `GET /api/glossary` — 용어 목록(추천 칩) · **비회원 허용**
- **목적**: 용어 챗봇 진입 시 추천 질문 칩.
- **인증**: 불필요.
- **응답 200**: `GlossaryTerm[]`.

### 3.9 `GET /api/glossary/lookup?q={query}` — 챗봇 질문 · **비회원 허용** · ⚠ 2026-10-24부터 **옛 앱 전용**

> **2026-10-24**: 새 앱은 §3.21 `POST /api/chat`을 쓴다. 이 주소는 옛 APK가 깨지지 않게 남겨 두고, 안에서 새 챗봇 엔진(`chat.reply`)에 질문 하나만 넣는다 — `answer`·`description`은 굵게 표시를 뺀 글, `outOfScope`는 늘 false, `source`는 모델명(기본 문장이면 ""), `termGlossary`는 빈 값. 아래 L1~L5 표는 **옛 설계 기록**이다.
- **목적**: 질문 하나에 답 하나. 용어·제도 설명만 하고, 판정·조언은 **거절**한다(가드레일).
- **인증**: 불필요.
- **요청**: 쿼리스트링 `q` = 사용자 입력 문자열.
- **응답 200**: `GlossaryAnswer`(§2.5). **404**: `q`가 비어 있을 때만(클라이언트 오류).
  - 2026-08-14 변경: **범위 밖도 404가 아니라 200 + `outOfScope=true`**로 나간다.
    앱이 거절 문구를 하드코딩하던 것을 없애기 위해서다(화면 문구는 서버가 정한다).
    옛 앱 호환을 위해 404 처리 경로는 앱·서버 양쪽에 남겨 두었다.

**통과 순서 (구현: `app/services/chat.py`)** — 이 순서가 설계의 전부다.

| 층 | 무엇 | LLM 호출 | 결과 |
|---|---|---|---|
| **L1** | 판정·조언·법률 요구 차단 (정규식) | **0회** | 거절 (`준비된 문구`) |
| **L2** | 검수된 용어 사전 직격 | **0회** | 사전 문장 **그대로** (`검수된 용어 사전`) |
| **L3** | 도메인 게이트 (terms.json에서 생성한 키워드) | **0회** | 부동산 얘기가 아니면 거절 |
| **L4** | Solar 설명 생성 + 검증 | 1회 | 통과분만 (`source`=모델명) |
| **L5** | 용어 툴팁 부착 (`termGlossary`) | — | 세 경로가 **합류한 뒤 한 곳에서** |

- **L1이 맨 앞인 이유**: "근저당 잡힌 이 집, 계약해도 돼요?"는 사전에도 걸리고 도메인 키워드도 있다. 판정 요구 게이트가 뒤에 있으면 그대로 새 나간다. **거절을 LLM에게 맡기지 않는다** — 프롬프트는 언젠가 뚫리지만 정규식은 안 뚫린다.
- **L4 검증** (`text_guard.check_chat`): 금지 표현·등급 단어(리포트와 **같은 패턴**) + 챗봇 전용 3개 —
  ⑴ **숫자 전면 금지**(챗봇에는 대조할 재료가 없어 화이트리스트를 만들 수 없다. 지어낸 `80%`가 판정 계층과 충돌하는 것을 구조로 막는다) ⑵ 200자 상한(넘으면 **자르지 않고 버린다**) ⑶ `out_of_scope=true`인데 answer가 있으면 answer를 버린다.
- **출력 스키마에 등급·점수·확률·금액 필드가 없다**(`extra="forbid"`). 리포트와 같은 경계다.
- **스위치**: `.env`의 `CHATBOT_LLM=off`면 L4를 통째로 건너뛴다 = AI 연결 이전과 완전히 같은 동작(사전 + 거절). 키 없음·타임아웃·JSON 깨짐·검증 실패도 전부 같은 자리로 떨어진다.
- **모델**: `LLM_CHAT_PROVIDER`(없으면 `LLM_EXPLAIN_PROVIDER` 상속, 기본 `upstage`) · temperature **0.3**(설명 생성 0.6보다 낮다 — 재료가 없어 창작 여지를 줄인다) · max_tokens 400.

### 3.12 `GET /api/pricing` — 요금제 · **비회원 허용** (2026-10-22 추가 · P2-1)
- **목적**: 요금제 화면. 정본 `backend/data/pricing.json`.
- **응답 200**: `Pricing` = `{label, currency, testMode, testNotice, plans: PricingPlan[]}`
  - `label` = `"예시 가격(확정 전)"`(2026-10-23 — 예전 `"예시 (팀 확정 전)"`, 내부 말을 뺐다) — 결제 화면 가격 밑에 붙인다. 요금제 화면은 맨 위 안내가 "예시예요"라고 하므로 돈을 받는 요금제 가격 밑에 짧게 `예시 가격`만(0원에는 없음 — '예시'는 한 번씩만). 가격은 팀이 확정하기 전까지 예시 — NOW.md 6절 #5.
  - `testMode: true` · `testNotice: "테스트 결제 — 실제 청구 없음"` — 결제 화면·영수증 어디에나 붙인다.
  - `PricingPlan` = `{id, name, tagline, price: int|null, priceText, period: string|null, purchasable, contact, features: string[]}`.
    `id`: `free`(무료 — 분석) · `guardian_pass`(계약 지킴이 패스 — 알림·재대조) · `institution`(기관용 — `price: null`, `priceText: "문의"`, `contact: true`).
    `purchasable: false`면 결제 버튼을 붙이지 않는다.

### 3.13 `POST /api/payments/confirm` — 테스트 결제 승인 · **기기 id 필요** (2026-10-22 추가 · P2-1)
- **목적**: 토스페이먼츠 결제위젯이 성공으로 돌려준 값을 서버가 **승인**한다(토스 `POST /v1/payments/confirm`).
- **요청** `application/json`: `{planId, orderId, paymentKey, amount}` — `orderId`는 `[A-Za-z0-9_-]{6,64}`(토스 규칙, 어긋나면 **422**).
- **금액은 서버가 정한다**: `amount`가 `pricing.json`의 그 요금제 `price`와 다르면 토스를 부르지 않고 **400**. 토스에는 앱 금액이 아니라 **요금제 가격**을 보낸다.
- **키**: 서버 변수 `TOSS_SECRET_KEY`(비우면 토스 문서 공개 **테스트** 키). `test_`로 시작하지 않으면(실제 키 `live_…`) **503** — 결선은 테스트 결제만.
- **응답 200**: `{testMode: true, notice: "테스트 결제 — 실제 청구 없음", pass: GuardianPass}`
  - `GuardianPass` = `{planId, planName, orderId, amount, method: string|null, approvedAt: string|null, testMode}` — 카드 번호·영수증 주소는 **없다**(서버가 버린다).
- **같은 주문 재전송**: 이미 승인해 둔 `orderId`면 토스를 다시 부르지 않고 같은 `pass`(앱의 [다시 확인하기]가 안전한 이유). 남의 주문번호면 **409**.
  토스가 "이미 처리된 결제"라고 하면 결제를 조회해 같은 주문·금액일 때만 패스를 되살린다.
- **에러**: **400** 결제할 수 없는 요금제 · 금액 불일치 · 토스 거절(토스의 한국어 문구 그대로 `detail`) / **409** 남의 주문 / **502** 토스에 닿지 못함·응답 불일치("잠시 후 다시") / **503** 실제 키.
- **주인 키**: 서버는 `dependencies.get_pass_owner` **한 곳**에서 정한다(모양은 `accounts.pass_owner_key`) — 로그인했으면 `account:acct-…`, 아니면 `device:<X-Device-Id>`.
  로그인하는 순간 그 기기의 패스는 계정으로 옮겨진다(§3.15). 앱의 토스 `customerKey`는 로그인했으면 서버가 준 `customerKey`(§3.15·§3.17), 아니면 기기 id 해시.

### 3.14 `GET /api/me/pass` — 내 계약 지킴이 패스 · **기기 id 필요** (2026-10-22 추가 · P2-1)
- **응답 200**: `{active: boolean, testMode: true, notice, pass: GuardianPass|null}` — 이 주인(로그인했으면 계정, 아니면 이 기기)의 가장 최근 패스. 다른 주인의 패스는 안 보인다.
- **앱 규칙**: 패스가 있으면 알림·재대조에 "지킴이 패스" **표시만** 붙인다. 패스가 없어도 알림·재대조는 막지 않는다(시연에서 막히면 안 된다).

### 3.15 `POST /api/auth/kakao` — 카카오로 로그인 · **기기 id 권장** (2026-10-22 추가 · P2-1)
- **요청** `application/json`: `{accessToken}` — 카카오 SDK가 준 **카카오 액세스 토큰**(1~4096자, 비면 **422**). 헤더 `X-Device-Id`(옮길 기기).
- **서버가 하는 일**: 카카오 `GET https://kapi.kakao.com/v1/user/access_token_info`(`Authorization: Bearer <카카오 토큰>`)에 묻는다 →
  응답 `{id: 회원번호, expires_in, app_id}`의 **`app_id`가 서버 변수 `KAKAO_APP_ID`와 같을 때만** 통과(다른 앱의 토큰 거부) →
  계정 키를 만들고(회원번호 원문은 버린다) 세션을 연다 → **이 기기(`X-Device-Id`)의 리포트·대조 기준·판례 캐시·캐시 쪽지·패스를 계정으로 옮긴다**
  (공용 통로 `legacy-device`는 옮기지 않는다. 여러 번 불러도 같다). 사용자 정보 API(`/v2/user/me`)는 부르지 않는다 — 이름·이메일·닉네임·프로필 사진을 받지 않는다.
- **응답 200**: `{sessionToken, expiresAt, customerKey}` — `sessionToken`은 무작위(서버에는 SHA-256만), `expiresAt`은 만료 시각(ISO 8601, UTC — `SESSION_DAYS`, 기본 30일),
  `customerKey`는 토스 결제위젯용 계정 값(`acct_` + 40자, 회원번호와 무관).
- **에러**: **401** 카카오가 토큰을 받지 않음·다른 앱의 토큰·회원번호 없음 / **502** 카카오에 닿지 못함 / **503** 서버 변수 없음(`KAKAO_APP_ID`·`ACCOUNT_HASH_SECRET` 32자 이상) / **400** 기기 id 형식(§1.1-1).

### 3.16 `POST /api/auth/logout` — 로그아웃 (2026-10-22 추가)
- 헤더 `Authorization: Bearer <세션>`의 **그 세션만** 지운다(다른 폰의 로그인은 그대로). 본문 없음 → **204**. 로그인하지 않았거나 이미 끝난 세션이어도 204.

### 3.17 `GET /api/me` — 지금 로그인 상태 (2026-10-22 추가)
- **응답 200**: `{loggedIn: boolean, provider: "kakao"|null, customerKey: string|null}` — 세션이 없으면 `loggedIn: false`(둘러보기).
- 세션이 틀리거나 만료면 **401**(§1.3 세션 401) — 앱은 켤 때 한 번 물어 끝난 세션을 지운다.

### 3.18 `DELETE /api/me` — **회원 탈퇴** (2026-10-22 추가)
- 그 계정의 **리포트·대조 기준·판례 캐시·캐시 쪽지·패스·모든 세션**을 지운다(되돌릴 수 없다) → **204**. 다른 사람·둘러보기 기기의 기록은 그대로.
- 로그인하지 않았으면 **401** `로그인한 뒤에 탈퇴할 수 있어요`. 카카오 연결 끊기(unlink)는 **앱**이 카카오 SDK로 한다(카카오 토큰은 앱에만 있다) — 서버 삭제가 먼저다.

### 3.20 `POST /api/me/name` — 표시 이름 정하기 (2026-10-24 추가)
- 요청 `{"displayName": "동크크 1"}` → 200 `MeResponse`(`displayName` 포함). 앞뒤 공백 정리, **12자까지**(넘으면 400), 빈 값이면 이름을 지운다.
- 로그인했을 때만(아니면 401). 카카오 닉네임은 받지 않는다 — 사용자가 앱에서 **직접 정한** 이름만. 회원 탈퇴 때 함께 지운다.
- `GET /api/me` 응답에도 `displayName`(없으면 null)이 실린다. 앱 홈 인사말 "○○님 안녕하세요".

### 3.19 `GET /api/precedents/status` — 판례 창고 상태 (2026-10-24 추가)

### 3.21 `POST /api/chat` — 챗봇 · **비회원 허용** (2026-10-24 추가)
- **목적**: 최근 대화를 받아 답 하나. 인사·잡담·장난·"더 쉽게" 같은 이어 묻기까지 **AI(Solar)가 직접 읽고 답한다**. 판정은 하지 않는다.
- **요청**: `ChatRequest { messages: ChatMessage[] }` — `ChatMessage { role: "user"|"assistant", content: string }`. 1~20개, **마지막은 이번 질문(user)**. 서버는 최근 8개만 쓰고 **대화를 저장하지 않는다**(앱이 매번 보낸다). 헤더 `X-Device-Id`는 횟수 상한에만 쓴다.
  선택 `reportId`(2026-10-26): 사용자가 보던 리포트 — 서버가 **이 사용자의** 리포트(기록의 이름 가린 사본)를 찾아 AI에게 참고로 준다.
  "왜 위험해?"에 그 리포트의 근거·숫자로 답하고, 리포트에 실제로 나온 등급·퍼센트만 말할 수 있다(다른 등급을 말하면 검사에 걸림).
  "계약해도 돼?" 같은 판정 요구는 여전히 조심 모드 — 리포트 결과를 전할 뿐 해도 된다/하지 마라는 말하지 않는다. 없거나 남의 것이면 리포트 없이 답한다.
  앱은 마지막으로 연 리포트(없으면 가장 최근 리포트)의 id를 보낸다.
- **응답 200**: `ChatResponse { answer, mode, model }`
  - `answer`: 화면에 그릴 글. 줄바꿈(`\n`)과 **`**굵게**` 표시(최대 3곳)**가 들어 있다 — 앱이 굵게 그린다. 용어 밑줄(`termGlossary`)은 없다(챗봇이 곧 풀이라서).
  - `mode`: `normal` AI 답 / `careful` 규칙이 판정 요구를 알아채 '판단 없이' 답함 / `fallback` AI 대신 기본 문장(AI 연결 실패·검사 두 번 실패)
  - `model`: 답을 쓴 모델 문자열(예: `solar-pro2`). 기본 문장이면 `""`.
  - **등급·점수·금액 칸이 없다** — 판정은 리포트(규칙 엔진)만 한다.
- **에러**: **400** 마지막이 질문이 아님·빈 질문·질문 500자 초과 / **422** 모양이 틀림 / **429** 질문 횟수 상한(기기×IP 시간당 `RATE_LIMIT_CHAT_PER_HOUR` 60 · IP 시간당 `RATE_LIMIT_CHAT_IP_PER_HOUR` 300 · 서버 하루 `RATE_LIMIT_CHAT_GLOBAL_PER_DAY` 3000 — 분석과 칸이 따로).
- **흐름 (구현: `app/services/chat.py`)**:

| 단계 | 무엇 | 비고 |
|---|---|---|
| 정리 | 최근 8개 · 주민번호·전화번호 꼴 가리기 · 길이 자르기 | 질문 글은 로그에 안 남김(길이·분류만) |
| 규칙 | 마지막 질문이 판정·금액·법률 판단 요구인가(정규식) | 맞으면 **조심 모드** 지시를 붙인다 — 막지 않는다 |
| Solar | 검수된 용어 풀이 + 판정 기준(`thresholds.py` 상수에서 생성)을 참고 자료로 받아 자기 말로 답 | 해요체 · 2~4문장 · 한 줄 한 문장 · 굵게 1~2곳 |
| 검사 | 금지 표현·등급 단어(리포트와 같은 패턴) · 집/계약/가격 판정 문장 · 근거 없는 숫자(사용자 숫자 + 판정 기준만 허용) · 인터넷 주소 · 450자 | `text_guard.check_chat_reply` |
| 고쳐 쓰기 | 걸리면 이유를 알려 주고 한 번 다시 쓰게 함 | 그래도 걸리면 기본 문장(검수된 용어가 있으면 그 풀이) |

- **스위치**: `CHATBOT_LLM=off`면 AI를 건너뛴다(용어 풀이 + 안내 문장).

## 9. 추가분 — 원본 사진 하이라이트 좌표 (2026-07-27, **채택 미확정**)

> **이 절은 기존 계약을 바꾸지 않는다.** `Report`에 **선택적 필드 1개**를 더할 뿐이며,
> 앱이 이 필드를 통째로 무시하면 지금과 **완전히 똑같이** 동작한다(기본값 빈 목록).
> 검증 기록은 `docs/ocr-highlight-findings.md`. 채택 여부는 아직 정해지지 않았다.

### 9.1 왜 추가하나

사용자가 **손에 든 등기부 종이와 앱 화면을 대조**할 수 있게 하려는 것이다. 은행원이
색연필로 동그라미 치듯, 사진 위에 확인해야 할 항목의 위치를 표시한다.

Information Extract는 필드를 구조화해주지만 **좌표를 주지 않는다.** 그래서 Document OCR을
함께 부르고, 두 결과를 매칭해 좌표를 만든다.

### 9.2 `Report`에 더해지는 필드

| 필드 | 타입 | 설명 |
|---|---|---|
| `highlights` | `Highlight[]` | **선택**. 사진 위 표시 목록. 좌표를 못 구하면 `[]` |
| `highlightNotice` | string? | 사진 묶음 안내 한 줄 (다른 등기부 섞임·쪽 누락·같은 쪽 중복). 없으면 `null` |
| `checkedNotes` | string[] | **"무엇을 찾아봤고 무엇을 왜 표시하지 않았는지"**. 9.7 참고 |
| `registryViewedAt` | string? | 등기부에 인쇄된 **열람일** `YYYY.MM.DD`. 못 읽으면 `null` — **앱은 분석일로 대체하지 않는다** |

기존 필드는 **하나도 바뀌지 않는다.**

### 9.3 `Highlight`

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | `owner-0`, `mortgage-1` 등 |
| `page` | int | **업로드한 사진 순서(0부터)**. 앱이 몇 번째 사진에 그릴지 |
| `kind` | string | **15종** (아래 9.3-a). ⚠ **앱은 모르는 값을 위험 톤으로 떨어뜨린다** |
| `badge` | int | 화면 뱃지 번호(1부터). 색만으로 정보를 전달하지 않기 위함(접근성) |
| `box` | `HighlightBox` | 정규화 좌표 |
| `title` | string | 시트 제목 (예: `소유자 이름 · 김○○`) |
| `body` | string | 사용자가 지금 할 행동 |
| `caution` | string? | 추가 주의 (예: 공동명의 전원 동의) |
| `source` | string? | 이 문장이 어디서 왔는지 (예: `등기부 갑구 — 이 앱이 사진에서 직접 찾은 위치`). 없으면 "앱이 그냥 하는 말"로 읽힌다 |

#### 9.3-a `kind` 목록 (2026-07-28 · 3종 → 15종)

**정본은 `backend/app/services/highlight.py`의 `_SPECS`다.** 여기는 계약 사본이다.
나열 순서 = **등기부를 읽는 순서**이고, 서버는 그 순서로 `badge`를 매긴다.

| kind | 톤 | 무엇 | 앵커 |
|---|---|---|---|
| `address` | 대조 | 소재지·동호수 | 표제부 주소 줄 (문서당 1곳) |
| `area` | 대조 | 전용면적 | IE 면적 ↔ ㎡ 있는 줄 |
| `separate_land` | 따져봄 | 토지 별도등기 | OCR 텍스트 (문서당 1곳) |
| `doc_title` | 대조 | 말소사항 포함 여부 | 표지 제목 줄 |
| `owner` | 대조 | 집주인 이름 | 등록번호 앞 word 1개 |
| `provisional_seizure` | 따져봄 | 가압류 | 3앵커 (순위+등기목적+청구금액) |
| `seizure` | 따져봄 | 압류 | **2앵커** (순위+등기목적) |
| `auction` | 따져봄 | 경매개시결정 | **2앵커** |
| `trust` | 따져봄 | 신탁등기 | **2앵커** |
| `mortgage` | 따져봄 | 근저당권 | 3앵커 (+채권최고액) |
| `jeonse` | 따져봄 | 전세권 | 3앵커 (+전세금) |
| `lease_registration` | 따져봄 | 임차권등기 | 3앵커 (+보증금) |
| `joint_collateral` | 따져봄 | 공동담보 | OCR 텍스트 (문서당 1곳) |
| `pending_application` | 따져봄 | 신청사건 처리중 | OCR 텍스트 (문서당 1곳) |
| `viewed_at` | 대조 | 서류를 뗀 날 | 꼬리말 열람일시 줄 |

**앱이 모르는 `kind`를 받으면**: **위험 톤(따져볼 곳)으로 취급한다.**
서버가 앱보다 먼저 새 종류를 내보낼 수 있는데, 모르는 것을 초록(대조할 곳)으로 칠하면
"확인만 하면 되는 것"으로 읽혀 경고를 놓친다. 미탐이 오탐보다 치명적이라는 보수적 편향
(risk-scoring 3절)을 여기에도 적용한다. 구현: `MarkKind.unknown`.

#### 9.3-b 표시 상한 — 종류당 5건

같은 `kind`가 5건을 넘으면 **서버가 상위 5건만 내보낸다**(금액 내림차순 → 금액이 없으면
순위번호 오름차순). 종류가 15개로 늘면서 압류 8건짜리 등기부는 갑구가 통째로 가로 띠가
되기 때문이다.

⚠ **표시 상한이지 판정 상한이 아니다.** 잘린 항목도 리포트 근거 카드에는 전부 있고,
**잘렸다는 사실을 `checkedNotes`로 반드시 알린다**(9.7).

### 9.4 `HighlightBox` — 정규화 좌표 (0~1)

| 필드 | 타입 | 설명 |
|---|---|---|
| `x`, `y` | float | 왼쪽 위 모서리 ÷ 원본 크기 |
| `w`, `h` | float | 폭·높이 ÷ 원본 크기 |

**왜 픽셀이 아니라 0~1인가**: 앱의 표시 크기는 기기·회전·줌에 따라 달라진다. 픽셀을 그대로
보내면 앱이 원본 크기를 따로 알아야 하고, 하나라도 어긋나면 좌표가 전부 밀린다.
서버는 **Pillow로 직접 읽은 원본 크기**로 나눈다(OCR 응답의 페이지 크기를 믿지 않는다).

앱은 `표시 좌표 = 정규화값 × 화면에 그린 이미지 크기` 로 되돌린다.
⚠ 앱이 화면에 띄우는 이미지는 **서버로 보낸 그 JPEG**여야 한다. 갤러리 원본을 띄우면
해상도가 달라 좌표가 전부 어긋난다.

### 9.5 좌표를 주지 않는 경우 (보수적 편향)

**틀린 위치에 칠하는 것보다 안 칠하는 것이 낫다.** 아래는 전부 "좌표 없음"으로 처리한다.

- **말소된 항목** — 사용자가 "이미 없어진 빚"을 현재 위험으로 오해하는 것이 최악의 오류다
- 앵커(순위번호 + 등기목적 + 금액)가 **같은 줄에 전부 있지 않을 때** (부분 매칭 금지)
- IE의 금액과 사진에서 읽은 금액이 다를 때
- 순위번호가 없을 때 (같은 금액이 여러 곳에 나와 항목을 지목할 수 없다)
- IE의 `current_owners`에 없는 이름 (지분을 넘긴 옛 소유자를 칠하면 임대인으로 오인한다)
- OCR 호출 실패 / 원본 크기를 못 읽음

### 9.6 판정과의 관계 — **완전 분리**

`highlights`는 **표시 전용**이다. 등급·점수·근거 카드에 어떤 영향도 주지 않는다.
IE ↔ OCR이 어긋나도 **판정은 바뀌지 않고 표시만 보류**된다.
(IE↔OCR 교차검증으로 등급을 바꾸는 것은 별도 승인 사항이며 구현돼 있지 않다.)

### 9.7 `checkedNotes` — "무엇을 찾아봤고 무엇을 왜 표시하지 않았는지"

**왜 있나**: 리포트에는 근저당이 4건인데 사진에는 3개만 표시되는 일이 흔하다(1건이 말소면
빠진다). 이 줄이 없으면 **개수가 안 맞는 이유를 화면 어디에서도 찾을 수 없다.**
2026-07-27 페르소나 2인의 공통 지적이 이것이었다 — **침묵이 신뢰를 깎는다.**

서버가 문장을 만들고 앱은 고르기만 한다. 지금 나가는 문장 종류:

| 상황 | 문장 예 |
|---|---|
| 말소로 제외 | `집에 잡힌 빚(근저당) 2건은 모두 말소된 것으로 확인해 표시하지 않았어요` |
| 위치 못 찾음 | `집주인 이름 1명은 리포트에 반영됐지만, 사진에서 위치를 찾지 못했어요` |
| **상한으로 생략** | `빚은 7건 중 큰 것부터 5건만 사진에 표시했어요. 나머지 2건은 화면이 가려져서 표시하지 않았어요` |
| **사진 순서 자동 정렬** | `사진 순서가 등기부 쪽수와 달라 자동으로 맞췄어요 — 다시 올리지 않으셔도 돼요` |
| **교차검증 일치** | `서류 내용을 2가지 방법으로 교차 확인했어요 — 빚(근저당) 3건 일치` |
| **교차검증 불일치** | `압류는 AI가 서로 다른 두 방법으로 읽었더니 개수가 달랐어요(3건 / 1건). 위험 계산은 더 많이 잡은 3건 기준으로 했어요.` |
| **두 번째 확인 실패** | `이번엔 한 가지 방법으로만 읽었어요 — 두 번째 확인은 하지 못했어요` |
| **못 본 쪽이 있음** | `못 본 쪽이 있어서 빚(근저당)이 없다고는 말할 수 없어요` |

⚠ **알려진 부채 (2026-07-28)**: 앱은 이 목록을 **문자열 포함 검사**로 고른다
(`kUnmarkedNoteMarkers`). 서버가 문구를 바꾸면 **조용히 화면에서 사라진다** — 실제로
오늘 만든 고지 3종이 전부 그렇게 탈락하고 있었고, 리뷰어 3인이 각각 찾아냈다.
**근본 해결은 서버가 분류 태그를 함께 보내는 것**(`{kind: "omitted"|"warn"|"ok", text}`)이고,
그건 이 계약을 바꾸는 일이라 **승인 후** 반영한다. 지금은 마커 목록을 늘려 막아 두었다.

### 9.8 `privacyMasks` — 사진 속 실명·주민번호 **자리** (2026-10-22 추가, 선택 · P0-2b)

**왜 있나**: 앱의 '사진 속 이름 가리기'(PR #4)는 **집주인 이름 하이라이트 칸만** 덮었다. 사진에는
채무자·이전 소유자·전세권자·개인 근저당권자·개인 채권자의 이름과 주민번호 앞자리가 그대로 보인다.
그 위치를 아는 것은 OCR을 돌린 서버뿐이라 서버가 **좌표만** 모아 보낸다. 판정과 무관하다(표시 전용).

| `Report` 필드 | 타입 | 설명 |
|---|---|---|
| `privacyMasks` | `PrivacyMask[]` | 가릴 자리 목록 (기본 `[]`). **글자는 없다 — 위치만** |
| `privacyMasksReady` | boolean | 위 목록을 **실제로 만들었는가** (기본 `false`). `false` = 이 기능 전 기록이거나 만들다 실패 |

`PrivacyMask` = `{page, x, y, w, h}` — `page`는 **업로드한 사진 순서(0부터)**, 나머지는 0~1 정규화(§9.4와 같은 방식).

- **무엇을 덮나**: 등록번호 모양(`900101-*******`·`110111-0015671`, 줄표가 빠지거나 낱말이 쪼개져도) + 그 앞 이름 칸,
  역할어(`소유자`·`공유자`·`채무자`·`채권자`·`근저당권자`·`전세권자`·`임차권자`·`권리자` 등) 뒤 이름 칸,
  IE가 읽은 사람 이름(소유자·권리자·채무자·근저당권자·채권자)이 사진 글자에 나오는 자리. **말소된 줄도 덮는다.**
- **덮지 않는 것**: 기관 이름(은행·회사·조합 등 `formatting.INSTITUTION_MARKERS` + 세무서·구청 같은 관공서), 금액·순위번호·날짜·주소 줄.
  애매하면 덮는다(놓치는 쪽이 더 나쁘다).
- **못 찾아본 쪽** (OCR 실패·글자 0개·원본 크기 모름) → 그 쪽 **전체**를 `{x:0, y:0, w:1, h:1}` 상자 하나로 보낸다.
- 사진 묶음 점검(§9.5 다른 등기부 섞임 등)으로 하이라이트를 보류해도 **가림 상자는 그대로** 나간다.
- **앱 규칙**: 가리기가 켜져 있으면 `privacyMasks` 전부 + 집주인 이름 하이라이트를 불투명 상자로 덮는다.
  `privacyMasksReady=false`인데 사진이 있으면(옛 기록) 사진을 **통째로** 덮는다 — 어디에 이름이 있는지 모르기 때문이다.
- 개인정보: 가림 상자에는 이름 글자를 싣지 않는다 — 위치만(로그는 개수만 — `[가리기] …`). 정본 코드: `backend/app/services/privacy_masks.py`.
  (리포트 글자 속 이름은 §9.11 — 2026-10-22부터 분석 응답은 실명, 서버 기록은 가린 사본.)

### 9.9 `captureCheck` — 촬영 품질 검사 (2026-10-22 추가, 선택 · P1-1)

**판정이 아니라 사진 품질**이다. 등급·근거 카드·하이라이트를 바꾸지 않는다. 기준값의 근거: decisions.md [2026-10-22] 촬영 품질 검사.

`CaptureCheck` = `{ok: boolean, pages: CapturePageIssue[]}` — 문제가 없는 장은 `pages`에 넣지 않는다.
`CapturePageIssue` = `{index, issues: string[], severe: boolean, tip: string}`

| 필드 | 설명 |
|---|---|
| `index` | 업로드한 사진 순서(0부터). 화면에는 `index+1`쪽 |
| `issues` | `blurry`(흐림) · `too_dark`(어두움) · `too_bright`(빛 번짐·반사) · `low_contrast`(글자가 흐릿) · `no_text`(글자 없음) · `low_resolution`(너무 작음) · `cut_off`(맨 아래 쪽 번호가 안 보임 — OCR 뒤) |
| `severe` | `true` = 분석하지 않고 거절한 장 |
| `tip` | 이유 + 다시 찍는 법, 쉬운 말 두 문장 (예: `글자 테두리가 번져 있어요. 휴대폰을 종이와 나란히 들고 …`) |

- **분석 전 거절** (`POST /api/analyze`·`POST /api/reports/{id}/compare`): 심한 장(`severe`)이 하나라도 있으면 IE·OCR을 부르지 않고(크레딧 0원)
  **400** — 본문은 일관 에러 형식에 `captureCheck`를 덧붙인 것이다:
  `{"detail": "2쪽이 흐려요 — 다시 찍어 주세요 (글자 테두리가 번져 있어요)", "captureCheck": {"ok": false, "pages": [...]}}`.
  옛 앱은 `detail`만 읽어도 된다. 분석 횟수(§1.3 429)는 1회 센다(검사도 서버 계산).
- **가벼운 문제**는 분석하고 `Report.captureCheck`에 싣는다(기본 `null` = 검사 안 한 옛 기록 또는 서버에서 끔). OCR 뒤 발견(`cut_off`, 글자 0개)도 여기 더한다.
- 서버 변수 `CAPTURE_CHECK`: `on`(기본) · `warn`(거절 없이 알리기만 — 심한 장도 `severe:true`로 리포트에 실린다) · `off`(검사 안 함, `captureCheck: null`).
- **앱 규칙**: 400에 `captureCheck`가 있으면 "그 장만 다시 찍기" 화면으로 간다. 리포트의 `captureCheck`에 문제가 있으면 그 장에 "확인 필요"를 붙이고 다시 찍기를 권한다.

### 9.10 같은 사진 = 같은 결과 — 분석 캐시 (2026-10-22 추가 · P1-1)

`POST /api/analyze`는 **같은 기기**가 **같은 JPEG 묶음(순서 포함) + 같은 `deposit`·`marketPrice`**로 다시 부르면 IE·OCR을 다시 부르지 않고
(크레딧 0원) **같은 `Report`(같은 `id`)**를 돌려준다. 응답 모양은 그대로다 — 앱은 따로 할 일이 없다.

- 기간: 서버 변수 `ANALYSIS_CACHE_HOURS`(기본 24, `0`이면 끔). `alias`만 다르면 같은 리포트에 새 별칭을 붙여 돌려준다(기록도 새 별칭으로).
- 리포트를 지웠으면 빗나가 처음부터 분석한다. 읽지 못한 쪽이 있는 결과(OCR 실패 — §9.8의 쪽 전체 가림)는 캐시하지 않는다.
- **서버를 새로 배포하면 빗나간다** — 키에 서버 코드 버전(Railway 배포 커밋 `RAILWAY_GIT_COMMIT_SHA`, 없으면 고정 문자열)이 들어간다.
  규칙을 고쳐 배포했는데 같은 사진에 옛 판정을 돌려주지 않게.
- **시세 DB가 뜨면 빗나간다** — 키에 시세 DB 준비 여부(헬스체크 `priceDb`와 같은 판단)도 들어간다. 배포 직후 DB를 내려받는
  몇 분 동안 만든 '시세 없음' 리포트가 DB가 뜬 뒤에도 나가지 않게. DB를 끝내 안 올린 서버에서도 캐시는 그대로 돈다.
- 분석 횟수(§1.3 429)는 캐시 적중도 1회로 센다. `/api/reports/{id}/compare`에는 쓰지 않는다(대조는 늘 새로 읽는다).

### 9.11 `personNames` — 화면엔 실명, 서버 기록엔 가린 사본 (2026-10-22 추가 · "폰엔 원본, 서버엔 가린 사본")

**왜 바뀌었나**: PR #3(2026-10-21)은 서버가 화면 문장을 **만들 때부터** 이름을 가렸다(`집주인 이름 · 홍○○`).
사용자 폰에도 실명이 안 보여 실제로 만난 계약자와 이름을 맞춰 보기 어려웠다. 이제 **응답은 실명, 서버가 남기는 것은 가린 사본**이다.

| 어디 | 사람 이름 |
|---|---|
| `POST /api/analyze` **새 분석 응답** | **실명** — 예: 집주인 하이라이트 제목 `집주인 이름 · 홍길동`. 회사·은행·관공서 이름은 원래부터 그대로 |
| 서버 기록 사본 — `GET /api/reports`·`GET /api/reports/{id}`, **같은 사진 캐시 적중**(§9.10), 대조(§3.10) | **가린 이름** `홍○○`(첫 글자 + 나머지 ○). `personNames`도 가린 꼴이다 |
| 설명(Solar) 입력 · 서버 로그 | 가린 이름 그대로(바뀌지 않음) |

- `Report.personNames` = 이 등기부의 **사람 이름** 목록(이름 칸 글자 그대로 — 현재·이전 소유자, 근저당권자·채무자, 전세권자·임차권자,
  가압류·가처분·압류 채권자, 수탁자 중 **사람**. 기관은 넣지 않는다). 기본 `[]`(옛 서버·옛 기록 — 그때는 서버가 이미 가렸다).
- 서버 저장: 리포트를 기록 DB에 쓰는 길은 하나뿐이고(`store.add`), 그 안에서 `name_privacy.mask_report_for_storage`가
  모든 글자 칸의 `personNames`를 가린 **깊은 사본**만 쓴다. **`address`·`grade` 칸은 바꾸지 않는다**(주소는 이름 칸이 아니고, 등급은 정해진 말).
- **앱 규칙**:
  - 새 분석 응답(원본)을 이 폰에 리포트 id별로 보관한다(사진과 함께 최근 5건). 리포트를 다시 열 때(기록 목록·캐시 적중 포함)
    **폰 원본을 먼저** 쓰고, 없을 때만 서버 사본을 쓴다. 캐시 적중이면 원본 + 응답의 새 `alias`. 기록을 지우면 폰 사본도 지운다.
  - '사진 속 이름 가리기'가 켜져 있으면 리포트 JSON을 모델로 바꾸는 **한 곳**에서 `personNames`의 각 이름을 서버와 같은 규칙
    (첫 글자 + 나머지 ○, 긴 이름부터)으로 **모든 글자 칸**에서 바꾼다 — `address`·`grade`는 그대로. 사진의 상자는 §9.8.
- ⚠ 대조 결과(§2.9·§3.10)의 이름은 늘 가린 꼴이다 — 이전 등기부의 실명이 서버에 없기 때문이다(스냅샷은 이름 해시뿐).

### 9.12 `pageOrder`·`pageRotations` — 1쪽부터 정렬 · 글자가 바로 서게 (2026-10-26 추가, 선택)

**왜**: 5장을 1·4·2·5·3이나 5·4·3·2·1로 올려도, 가로·거꾸로 찍어도 '내 등기부등본 보기'가 **종이와 같은 순서·같은 방향**이어야 대조할 수 있다.

- `Report.pageOrder: int[]` — **문서 순서의 업로드 인덱스**(0부터). `[3, 2, 1, 0, 4]` = 4번째로 올린 사진이 1쪽.
  서버가 꼬리말 쪽 번호(`N/M`)를 **전부** 읽어 믿고 세울 수 있을 때만 채운다(§사진 묶음 점검과 같은 조건). 빈 목록 = 올린 순서 그대로.
  하이라이트·가림 상자·촬영 검사의 `page`/`index`는 **여전히 업로드 인덱스**다.
- `Report.pageRotations: int[]` — 업로드 순서별 **시계 방향 회전 각도**(0·90·180·270). 서버가 OCR 결과 모양(표지 낱말·가로 상자·왼→오)으로
  바로 선 방향을 찾아 그 방향 사진으로 읽은 각도다(`orientation.py`, AI 판단 없음). 빈 목록 = 전부 0(옛 기록).
  **하이라이트·가림 상자 좌표는 돌린 사진 기준** 정규화 값이다.
- 돌려 세운 장이 있으면 서버는 IE도 바로 선 사진으로 한 번 더 읽는다(판정 재료가 누운 글자를 잘못 읽은 채로 남지 않게). 끄기: `AUTO_ROTATE=off`.
- **앱 규칙**: 폰에 남긴 사진(보낸 그 JPEG)을 `pageRotations[i]`만큼 돌려 그리고(90·270이면 가로세로를 바꿔 잰다),
  뷰어는 `pageOrder` 순서로 쪽을 늘어놓는다. 사진 파일 자체는 바꾸지 않는다(다시 분석할 때 서버가 다시 찾는다).
