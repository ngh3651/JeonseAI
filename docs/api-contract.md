# 앱 ↔ 서버 JSON 계약서 (api-contract.md)

> **Phase D-1 산출물.** 앱(Flutter)과 서버(FastAPI)가 주고받을 데이터 형식을 확정한 문서입니다.
> 이 계약은 D-2(서버 더미 응답 구현)와 D-3(앱 연결)의 설계도이며, 나중에 실제 분석(Phase E)으로
> 교체될 때 **앱을 바꾸지 않고 서버 속만 바꾸기 위한** 기준점입니다(Repository 패턴).
>
> - 이 문서는 **"무엇을 주고받는가"만** 정의합니다. "어떻게 만드는가"(추출·판정 로직)는 담지 않습니다.
> - 모든 필드는 **Phase C 화면 코드에서 실제로 쓰는 데이터**를 역추출한 것입니다. 화면에 없는 필드는 넣지 않았습니다.
> - plan.md·CLAUDE.md가 말하는 `docs/data-contract.md`가 바로 이 문서입니다(파일명은 api-contract.md로 확정).

## 0. 핵심 원칙 (계약에 반영된 가드레일)

1. **판정과 설명의 분리** — 위험 판정(등급·수치)은 규칙 엔진이, 설명 문장은 LLM이 만든다.
   그래서 응답의 각 필드에 **출처 태그**를 붙였다:
   - `[판정]` = 규칙 엔진이 만드는 값(등급·수치·상태). LLM이 못 바꾼다.
   - `[설명]` = LLM(Solar Pro)이 생성하는 문장. 판정을 바꾸지 않고 문장만.
   - `[메타]` = 식별·시각용 값(id·주소·시간·게이지 진행률 등).
   - `[UI]` = 앱이 그대로 노출하는 고정 라벨.
2. **보수적 편향** — 등급은 `위험 | 확인 필요 | 양호` 3단계이며, 데이터가 불충분하면
   `양호`로 단정하지 않고 항목 상태를 `확인 필요`로 표현한다(2번 §2, 근거 카드 `statusLabel`).
3. **Repository 교체** — 앱은 이 계약(무엇을)만 알고 서버 내부(어떻게)는 모른다.

## 1. 공통 규약

### 1.1 기본 주소
- Base URL: `http://127.0.0.1:8000` (실기기 `adb reverse tcp:8000 tcp:8000` 고정)

### 1.2 인증 (확정된 규칙)
- **인증이 필요한 API는 두 개**다: `POST /api/analyze`(분석 실행)와 `DELETE /api/reports/{id}`(이력 삭제).
  삭제는 분석과 한 몸이다 — 로그인해서 분석한 사람만 자기 리포트를 지운다(§3.4). 그 외 조회성 API는 **비회원도 허용**한다.
- 인증이 필요한 요청은 헤더에 토큰을 싣는다: `Authorization: Bearer <token>`
- **개발 모드(현재)**: 아직 진짜 로그인 시스템(Supabase 등)이 없어, 인증을 실제로 걸면 우리 스스로
  분석을 테스트할 수 없다. 그래서 **서버는 지금 토큰을 실제로 검사하지 않고 항상 통과**시킨다
  (토큰이 없어도 200). 단, 나중에 진짜 인증을 켜기 쉽도록 **인증 검사를 한 곳(의존성 함수
  `get_current_user`)에 몰아두고 "항상 통과"만 반환**하게 한다 — 이 함수 하나만 바꾸면 실인증이 켜진다.
- **앱 쪽 기획 의도는 유지**: 화면상 비회원이 분석하려 하면 로그인 유도가 뜬다(D-3 앱 작업). 서버는 관여하지 않는다.
- 로그인/회원가입 서버 엔드포인트는 이번 D에 만들지 않는다(계약 범위 밖 유지).

### 1.3 에러 형식 (일관)
모든 에러는 HTTP 상태 코드 + 아래 JSON으로 반환한다(현행 백엔드 `/api/upload`와 동일 형식).

```json
{ "detail": "사용자에게 보여줄 한국어 메시지" }
```

| 상태 | 의미 |
|---|---|
| 400 | 잘못된 요청(형식 오류 등) |
| 401 | 인증 필요/실패 (분석·삭제 API. **개발 모드에서는 발생하지 않음** — §1.2) |
| 403 | 금지된 동작 (예: 예시 리포트 삭제 시도 — §3.4) |
| 404 | 리소스 없음(리포트 id 없음, 용어 조회 실패=범위 밖) |
| 413 | 업로드 용량 초과 |
| 5xx | 서버 오류 (앱은 "잠깐 문제가 생겼어요"로 표시) |

### 1.4 값 표기
- **금액**: 정수, 단위는 **원**(예: `120000000` = 1억 2천만원). 앱이 "만원" 입력을 원으로 변환해 보낸다.
- **날짜/시간**: ISO 8601 문자열(예: `"2026-06-27T09:00:00+09:00"`). 앱이 "2026.06.27"·"7일 전"으로 표시.
- **등급 문자열**(`grade`): `"위험"` | `"확인 필요"` | `"양호"` (공백 포함, 앱 enum 라벨과 동일).
  - 등급별 **색·의사결정 문구는 앱이 grade로부터 파생**한다(아래 표). 서버는 `grade`만 보내면 된다.

  | grade | 의사결정 문구(앱 파생) | 색(앱 파생) |
  |---|---|---|
  | 위험 | 계약을 피하는 것을 권해요 | 빨강 |
  | 확인 필요 | 보류하고 아래 항목을 먼저 확인하세요 | 주황 |
  | 양호 | 진행을 검토할 수 있어요 — 단, 직접 확인은 꼭 필요해요 | 초록 |

## 2. 공통 데이터 모델

여러 엔드포인트에서 재사용하는 객체들이다.

### 2.1 `Report` — 안전도 리포트 (핵심)
홈 카드·리포트 화면·시뮬레이터가 공유한다.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 리포트 식별자 (예: `"analysis-1720000000000"`) |
| `alias` | string | [메타] | 매물 별칭. 미입력 시 `address`가 기본값 |
| `address` | string | [메타] | 표제부 소재지 주소 |
| `analyzedAt` | string(ISO8601) | [메타] | 분석 시각 |
| `grade` | string | [판정] | 위험도 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `gaugeProgress` | number | [메타] | 게이지 시각 진행률 0.0~1.0 (점수 체계는 E-1에서 확정) |
| `headline` | string | [설명] | 결론 한 줄 (예: "보증금을 지키기 어려운 신호가 보여요") |
| `nextAction` | string | [설명] | "지금 해야 할 일" 한 문장 |
| `topRiskSummary` | string | [설명] | 최대 위험 요인 한 줄 — 홈/마이 이력 카드 3번째 줄 |
| `deposit` | integer | [판정] | 예정 보증금(원) — 사용자 입력 |
| `marketPrice` | integer \| null | [판정] | 매매 시세(원). null이면 전세가율 근거는 "확인 필요" |
| `seniorDebtAmount` | integer | [판정] | 선순위 채권 합계(원) — 손실 시뮬레이터 입력 |
| `evidences` | `Evidence[]` | — | 근거 카드 목록(§2.2) |

- **홈/마이 이력 카드**가 쓰는 필드: `id, alias, address, analyzedAt, grade, deposit, topRiskSummary`.
- **손실 시뮬레이터**가 쓰는 필드: `alias, deposit, marketPrice, seniorDebtAmount` + `evidences`에서 `insurance` 항목의 `grade`(보증보험 가입 미확인 경고 판단). **슬라이더·보험 토글 계산은 앱에서 로컬 수행**(서버 호출 없음). 계산식은 E-4에서 서버 이관 검토.
- **파생 값(전송 안 함)**: 등급별 `decisionLabel`·색은 앱이 `grade`로 파생. `riskLabels`(위험 패턴 목록)는 `evidences`에서 파생(§2.2 note).

### 2.2 `Evidence` — 근거 카드 한 항목
리포트 화면의 접힘/펼침 카드. `evidences` 배열의 원소.

| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `id` | string | [메타] | 항목 식별자: `jeonse_ratio` \| `senior_debt` \| `ownership` \| `insurance` \| `blacklist` |
| `title` | string | [설명] | 쉬운 질문형 제목 (예: "나보다 먼저 돈 받아갈 빚이 있나요?") |
| `termSubtitle` | string | [UI] | 전문용어 부제 (예: "선순위 채권 · 근저당권") |
| `grade` | string | [판정] | 이 항목의 등급 (`"위험"` \| `"확인 필요"` \| `"양호"`) |
| `statusLabel` | string \| null | [판정] | 등급 대신 표시할 상태 (예: "확인 필요", "페이지 누락"). null이면 grade 라벨 사용 |
| `easyExplanation` | string | [설명] | 펼침 1단: 쉬운 설명 (LLM 생성 슬롯 — 판정 변경 금지) |
| `detailText` | string \| null | [판정] | 펼침 2단: 상세 수치를 사람이 읽게 포맷한 문자열 (예: "채권최고액 1억 8,000만원 · 근저당권 2건") |
| `sourceText` | string \| null | [판정] | 판정 출처 (예: "HUG 공식 기준 등 확정 예정" — E-1에서 실제 출처로 교체) |
| `actionLabel` | string \| null | [UI] | 다음 행동 버튼 라벨 (예: "중개사에게 물어볼 질문 보기", "시세 입력하기"). null이면 버튼 없음 |
| `termGlossary` | object(map) | [설명] | `easyExplanation` 속 용어→툴팁 설명. 키=용어, 값=설명 문장 (예: `{"근저당권":"집주인이 …"}`) |

- **위험 패턴 파생(중요)**: 판례·질문 엔드포인트가 쓰는 "위험 패턴"은 `evidences` 중 `grade ≠ 양호`인
  항목의 `id`를 아래로 매핑해 만든다. **앱은 이 파생을 하지 않아도 되며(서버가 리포트 id로 계산)**,
  파생 규칙만 계약에 남긴다:
  `senior_debt→선순위 채권`, `ownership→신탁등기`, `jeonse_ratio→전세가율`, `insurance→보증보험`.

### 2.3 `CaseMatch` — 판례 (판례 매칭 화면)
| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `riskPattern` | string | [메타] | 매칭된 위험 패턴명 (예: "신탁등기", "선순위 채권"). 앱이 칩에서 쉬운 말로 치환해 표시 |
| `caseNo` | string | [메타] | 사건번호 (예: "대법원 2022다123456") |
| `summary` | string | [설명] | 사건 한 줄 요약 |
| `result` | string | [설명] | 결과 (예: "보증금 대부분 손실") |
| `commonPoint` | string | [설명] | 우리 매물과의 공통점 |

### 2.4 `QuestionGroup` / `QuestionItem` — 질문 생성기 화면
```
QuestionGroup {
  riskLabel: string,        // [메타] 위험 요소 그룹명 (예: "신탁등기", "어떤 집이든 꼭")
  items: QuestionItem[]
}
QuestionItem {
  question:   string,       // [설명] 중개사에게 할 질문
  why:        string,       // [설명] 왜 물어봐야 하는지 한 줄
  safeAnswer: string,       // [설명] "이런 답이면 안심"
  riskyAnswer:string        // [설명] "이런 답이면 보류"
}
```

### 2.5 `GlossaryTerm` — 용어 챗봇 화면
| 필드 | 타입 | 출처 | 설명 |
|---|---|---|---|
| `term` | string | [메타] | 용어 (예: "신탁등기") |
| `description` | string | [설명] | 쉬운 설명 |

### 2.6 `JourneyStage` / `JourneyItem` — 계약 여정 체크리스트 화면
```
JourneyStage {
  title:    string,         // [UI] 단계명 (예: "잔금일")
  subtitle: string,         // [UI] 부제 (예: "나머지 보증금을 보내는 날")
  items:    JourneyItem[]
}
JourneyItem {
  text: string,             // [UI] 할 일
  why:  string              // [설명] "왜 해야 하나요?" 펼침 설명
}
```
- 여정 데이터는 **정적**(모든 사용자 동일). **체크 상태는 서버가 아니라 앱 로컬에 저장**한다(계약 대상 아님).

## 3. 엔드포인트 목록

### 3.1 `POST /api/analyze` — 등기부 분석 실행 · **인증 필요**
- **목적**: 등기부 사진 + 입력값으로 분석해 리포트를 만들어 반환한다(＋버튼 → 로딩 → 리포트).
- **인증**: 필요 (`Authorization: Bearer <token>`). 없으면 401.
- **요청** (`multipart/form-data`):

  | 파트 | 타입 | 필수 | 설명 |
  |---|---|---|---|
  | `files` | file[] (image/jpeg) | ✅ | 등기부 페이지 이미지 여러 장 (앱이 항상 JPEG로 변환해 전송) |
  | `deposit` | integer | ✅ | 예정 보증금(원) |
  | `marketPrice` | integer | ✖ | 매매 시세(원). 없으면 전세가율 근거가 "확인 필요"로 |
  | `alias` | string | ✖ | 매물 별칭. 없으면 서버가 표제부 주소를 별칭으로 |

- **응답 200**: `Report`(§2.1, `evidences` 포함) 하나.
- **참고**: 현행 검증 자산 `POST /api/upload`(이미지 1장 수신·메타데이터 반환)는 통신 파이프 검증용이며,
  이 계약에서는 `/api/analyze`가 그 역할을 대체·확장한다(부록 §8).

### 3.2 `GET /api/reports` — 분석 이력 목록 · **비회원 허용**
- **목적**: 홈 대시보드·마이의 최근 분석 이력.
- **인증**: 불필요. (비회원도 예시 리포트 2건을 봄 — "홈 둘러보기")
- **요청**: 없음.
- **응답 200**: `Report[]` (최신순). 홈은 앞의 3건 + 전체 보기, 마이는 전체.
  - 목록에서 홈/마이 카드가 실제 쓰는 필드는 §2.1 note 참고. (경량화를 위한 요약 응답은 향후 최적화 여지 — D-1은 앱 현행대로 전체 `Report` 반환.)

### 3.3 `GET /api/reports/{id}` — 리포트 단건 · **비회원 허용**
- **목적**: 안전도 리포트 화면(재열람 포함) + 손실 시뮬레이터의 데이터원.
- **인증**: 불필요. (예시 리포트 열람 허용)
- **응답 200**: `Report` 하나. **404**: 해당 id 없음 → 앱은 "이 리포트를 불러올 수 없어요".

### 3.4 `DELETE /api/reports/{id}` — 이력 삭제 · **인증 필요**
- **목적**: 마이 화면에서 이력 삭제.
- **인증**: 필요(개발 모드에서는 `get_current_user`가 항상 통과 — §1.2). 삭제는 분석과 한 몸이라
  로그인해서 분석한 사람만 자기 것을 지운다.
- **응답 204**: 성공(본문 없음). **404**: 없는 id. **403**: 예시 리포트(`dummy-danger`·`dummy-caution`) 삭제 시도.
- **참고**: 비회원이 보는 **예시 리포트는 조회만 허용**이며 삭제 대상이 아니다(홈 둘러보기 의도).

### 3.5 `GET /api/reports/{id}/cases` — 판례 매칭 · **비회원 허용**
- **목적**: 리포트의 위험 패턴에 매칭되는 판례 목록.
- **인증**: 불필요.
- **응답 200**: `CaseMatch[]`. **빈 배열 허용**(매칭 판례 없음 → 앱이 빈 상태 문구 표시). **404**: 없는 리포트 id.
- **참고**: 서버가 리포트의 `evidences`에서 위험 패턴을 파생(§2.2 note)해 매칭한다. 앱은 위험 패턴을 계산·전송하지 않는다.

### 3.6 `GET /api/reports/{id}/questions` — 중개사 질문 생성 · **비회원 허용**
- **목적**: 리포트의 위험 요소별 질문 그룹.
- **인증**: 불필요.
- **응답 200**: `QuestionGroup[]`. 위험 요소가 없어도 "어떤 집이든 꼭" 기본 그룹을 포함(빈 배열 아님). **404**: 없는 리포트 id.
- **참고**: 실단계 E-2에서 분석 결과 기반 LLM 생성으로 교체(판정 변경 금지). 위험 패턴 파생은 §2.2 note.

### 3.7 `GET /api/journey-stages` — 계약 여정 단계 · **비회원 허용**
- **목적**: 계약 여정 체크리스트의 정적 단계 목록.
- **인증**: 불필요.
- **응답 200**: `JourneyStage[]` (모든 사용자 동일). 체크 상태는 앱 로컬 저장이라 응답에 없음.

### 3.8 `GET /api/glossary` — 용어 목록(추천 칩) · **비회원 허용**
- **목적**: 용어 챗봇 진입 시 추천 질문 칩.
- **인증**: 불필요.
- **응답 200**: `GlossaryTerm[]`.

### 3.9 `GET /api/glossary/lookup?q={query}` — 용어 조회 · **비회원 허용**
- **목적**: 챗봇에 입력한 질문에서 용어를 찾아 설명 반환. 못 찾으면 "범위 밖"으로 거절(가드레일).
- **인증**: 불필요.
- **요청**: 쿼리스트링 `q` = 사용자 입력 문자열.
- **응답 200**: `GlossaryTerm` 하나(찾음). **404**: 용어 아님 → **범위 밖**. 앱은 "저는 용어를 설명해 드리는 챗봇이에요…" 거절 문구를 띄운다(판정·조언 생성 안 함).

## 7. 열린 질문 — **확정됨 (2026-07-04)**
1. **인증 실체** → **개발 모드로 확정.** 서버는 `POST /api/analyze`·`DELETE`에 인증을 요구하되,
   지금은 `get_current_user`가 토큰을 검사하지 않고 항상 통과시킨다(우리가 분석을 테스트할 수 있도록).
   나중에 이 함수 하나만 바꾸면 실인증이 켜진다. 로그인/회원가입 서버 엔드포인트는 이번 D에 만들지 않는다.
   (§1.2 반영)
2. **`DELETE /api/reports/{id}` 인증** → **인증 필요로 확정.** 삭제는 분석과 한 몸(로그인해서 분석한
   사람만 자기 것을 지움). 개발 모드라 실제로는 항상 통과. 예시 리포트는 삭제 대상 아님. (§3.4 반영)
3. **이력 목록 응답 경량화** → **하지 않기로 확정.** `GET /api/reports`는 전체 `Report`(근거 포함) 반환(현행 유지). (§3.2 반영)
