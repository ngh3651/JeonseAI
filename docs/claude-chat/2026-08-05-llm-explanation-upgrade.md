## 2. 개선 전/후 문구 대조 (5케이스)

### ★ `mortgage_heavy` — `senior_debt` (요청하신 대조)

**개선 전** (감사 §B-2 실측):
> 나보다 먼저 돈을 받아갈 빚(선순위 채권)이 시세의 90%인 1억 8,000만원이에요. 보증금까지 합치면 시세의 150%로 매우 높아요. 등기부등본으로 직접 확인하세요

**개선 후**:
> 선순위 채권 합계를 60% 초과 시 위험으로 봐요. 이 집에는 **1순위 ○○은행 1억 3,000만원, 2순위 ○○캐피탈 5,000만원** 총 1억 8,000만원의 빚이 있어요. 이 빚이 시세의 90%를 차지해요. 보증금+선순위 채권도 시세의 150%로, 90% 초과 시 위험 기준이에요. 이 집에는 나보다 먼저 돈을 받아갈 빚이 많아, 문제가 생길 경우 보증금 회수가 어려울 수 있어요. **중개사에게 이 빚들의 정확한 내용을 물어보세요.**

달라진 것: ⑴ **기준선(60%)이 문장에 들어왔다** ⑵ **근저당이 건별로 특정된다**(순위·채권자·금액) — 이 집에만 해당하는 문장 ⑶ **중개사 질문으로 끝난다**.

### 3-4. 앱의 용어 렌더 방식 (Step 4-13 — 확인 후 보고)

**밑줄이 맞다.** `term_tooltip_sheet.dart`의 `TermText`:
```dart
color: AppColors.primary,
decoration: TextDecoration.underline,
decorationStyle: TextDecorationStyle.dashed,
decorationColor: AppColors.primaryBright,
```
→ **초록색 + 점선(dashed) 밑줄**. 탭하면 바텀시트가 열린다. `termSpan`이 `WidgetSpan`을 베이스라인 정렬로 넣어 문장 흐름을 깨지 않는다.
`report_screen.dart:498`의 "`termGlossary`가 비면 평문 갈래" 문제는 **커버리지가 84%로 올라 대부분 해소**됐다. **앱은 고치지 않았다**(지시대로 보고만).

### 3-5. 폴백 경로 실측 (감사 §9 공백 메움)

| 시나리오 | 결과 |
|---|---|
| ① API 키 없음 | `source='폴백'` · 로그 "호출 생략 → 폴백 (원인: API 키 없음)" |
| ② 응답에 `grade` 키 삽입 | `extra="forbid"` 거부 → 재시도 1회 → `source='폴백'` |
| ③ 단정 + 날조 숫자 혼합 | `source='AI 생성(일부 폴백)'` · 로그 **`headline=금지 표현(안전-단정) \| jeonse_ratio=재료에 없는 수치(99)`** |

**폴백 문구가 LLM 문구보다 어렵지 않은지**: 폴백 52~78자(평균 63자), 용어 0~3개. LLM 문구는 평균 131자에 용어 평균 2.3개. **폴백이 더 짧고 쉽다** — 다만 기준선·건별 상세가 없어 정보량은 적다. 어휘 난도 역전은 없다.

## 4. 용어은행에 **넣지 않은** 용어와 이유

근거가 확실한 것만 넣었다(35개). 아래는 **일부러 뺐다**:

| 용어 | 뺀 이유 |
|---|---|
| **최우선변제 금액·보증금 상한선** | 지역·시기별로 다르고 시행령 개정에 따라 바뀐다. `최우선변제권` 항목은 넣되 **구체 금액은 쓰지 않았다** — 틀린 금액이 툴팁으로 뜨는 것이 없느니만 못하다 |
| **전세권 vs 임차권의 법적 차이 상세** | 정확히 쓰려면 조문 인용이 필요하고, 요약하면 오해를 만든다 |
| **채권최고액 설정 비율** | `110~130% 수준`이라고 **관행으로만** 적었다. 법정 비율이 아니라 금융기관 관행이라 단정하지 않았다 |
| **HUG 보증 가입 요건(전세가율·선순위 한도 등)** | `thresholds.py`의 임계값과 중복되고, 그쪽이 정본이다. 용어은행에서 또 말하면 두 곳이 갈라진다 |
| **대항력 발생 시점의 예외** | "다음 날 0시"는 넣었지만 예외(경매 배당 등)는 뺐다 — 한 문장으로 정확히 쓸 수 없다 |
| **깡통전세의 수치 기준** | 통용되는 정의는 있으나 **권위 있는 수치 기준이 없다**. 뜻만 적고 숫자는 뺐다 |
| **전입신고와 확정일자의 선후 관계 효과** | 실무상 중요하지만 사안별로 갈려 한 줄 설명이 위험하다 |
| **임차권등기명령 신청 요건·절차** | 절차 안내는 용어 설명의 범위를 넘고, 틀리면 사용자가 손해를 본다 |

> ⚠ 위 35개 설명문은 **제가 작성한 것이고 팀 검수를 받지 않았다.** `terms.json` 상단에 편집 규칙을 적어 두었으니, 정민재/최가은 검수 후 문구를 고치는 것이 좋다. 특히 `채권최고액`의 "110~130%"와 `대항력`의 "다음 날 0시"는 사실 확인이 필요하다.

## 5. 확인 불가 목록

| # | 확인 못 한 것 | 이유 |
|---|---|---|
| 1 | **실기기에서 `\n` 문단이 실제로 어떻게 보이는지** | `adb devices`에 기기가 없다. 코드상 `Text`/`Text.rich` 모두 `\n`을 렌더하고 `maxLines` 제한이 없음은 확인했지만(§감사 D-3), 눈으로 못 봤다 |
| 2 | 점선 밑줄이 문단 안에서 줄바꿈될 때의 모양 | 위와 같은 이유. `WidgetSpan` 베이스라인 정렬이라 흐름은 유지된다는 것까지만 코드로 확인 |
| 3 | `temperature=0.6`의 **형식 준수율** | 해요체·용어 괄호 순서는 여전히 검증되지 않는다. 5케이스 관측에서는 눈에 띄는 위반이 없었으나 표본이 작다 |
| 4 | 폴백률 13.3%가 정상 수준인지 | 비교 기준이 없다. 개선 전 감사 실측은 **0%**였는데, 그때는 그물이 성겨서 단정이 통과했기 때문이다 — 폴백률 상승은 **차단이 작동한 결과**로 보이지만 장기 추이를 봐야 한다 |
| 5 | 실물 등기부에서의 동작 | 픽스처 5종만 돌렸다. `real_snapshot` 픽스처는 실명이 있어 제외했다 |
| 6 | 근저당 상세가 **여러 건일 때** 문장이 길어지는 정도 | 최대 2건인 픽스처만 봤다. 근저당 5건 이상이면 600자 상한에 걸릴 수 있다 |
| 7 | `terms.json` 35개 설명문의 **사실 정확성** | 제가 작성했고 팀 검수를 받지 않았다(§4 참고) |
| 8 | 챗봇 화면에서 칩 23개가 어떻게 배치되는지 | 6개 → 23개로 늘었다. 앱 화면을 확인하지 않았다 — **레이아웃이 깨질 수 있다** |
