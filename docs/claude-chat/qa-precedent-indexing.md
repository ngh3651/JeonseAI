## ① Case Collection — 판례 수집

**Q. 어떤 API를 쓰나요? 키가 2개 필요한가요?**

법제처 국가법령정보 공동활용 Open API 하나. 키(OC) 1개로 목록조회(lawSearch)와
본문조회(lawService)를 모두 호출한다. 별도 키 2개가 아니라 같은 키로 2단 호출하는 구조.

**Q. 목록 조회와 본문 조회는 왜 둘 다 필요한가요?**

목록조회는 키 + 검색어(예: 전세보증금)를 보내 판례 리스트와 판례일련번호를 받는 요약 카드
단계(판결요지 없음). 그 번호를 본문조회의 ID에 넣어야 판시사항·판결요지·전문이 온다.
번호가 두 API를 잇는 열쇠.
💡 도서관 검색 결과(제목·청구기호)를 받고 → 청구기호로 실제 책을 꺼내는 2단계.

**Q. 판례 데이터에는 어떤 내용이 있나요? 판결문 전문 통짜인가요?**

전문 통짜가 아니라 구조화된 항목. 메타데이터(사건번호·사건명·선고일자·법원명) +
내용(판시사항·판결요지·참조조문·참조판례·판례내용 전문). 현재 코드는 원본 응답 15개 키
전체를 raw로 저장.

**Q. 메타데이터(사건번호·법원·선고일)는 어디에 쓰이나요?**

검색·랭킹에는 쓰이지 않고 리포트 카드의 출처 표기 전용(예: "대법원 99다59306").
LLM에게 전달되는 통로도 없다.

**Q. 증분 갱신은 어떻게 하나요?**

설계 확정, 구현 대기. 선고일 커서로 최신순 조회하다가 이미 가진 일련번호를 만나면 조기 종료.
💡 효과: 판례가 1,000건 → 1,005건이 되면 새 5건만 수집하면 된다. 전체 재수집 불필요.
⚠️ 현재 코드는 raw 파일이 이미 있으면 건너뛰는 수준이며, 강제 재수집(`--force`)은 미구현.

**Q. 현재 수집 규모와 키 상태는?**

실데이터 26건(시드 6건 공식 원문 조인 + 스트레스 20건). 현재 개발용 키(`OC=test`) 사용 중,
대량 수집은 정식 OC 발급 후.

## ② Chunking → Risk-Tag Tagging — 청킹·위험태그 태깅

**Q. 청킹은 무슨 기준으로 자르나요?**

판결요지는 쟁점 번호(`[1]`, `[2]`) 단위 분리 → 900자 초과 시 문장 경계 분할 → 40자 미만
조각은 앞에 병합. 전문(full text)은 문단 단위(40자 미만 문단 스킵). 큐레이션 요약은 통짜 1청크.
💡 실측: 총 373청크 = 전문 315 / 판결요지 51 / 요약 7. 평균 267자.

**Q. 잘라내면 그 부분은 임베딩에 아예 못 들어가나요?**

청킹 자체는 '버리기'가 아니라 '나누기' — 나뉜 조각은 각각 임베딩되어 모두 DB에 들어간다.
⚠️ 다만 실측 결과 실제 손실 3가지 발견: ⑴ 판시사항 7,098자(판결요지가 있으면 판시사항을
버림) ⑵ 전문의 40자 미만 문단 2,641자 ⑶ 참조조문·참조판례 전량. 원본(raw)에는 남아 있어
재적재로 복구 가능 → 인덱스 재편입이 개선 과제.

**Q. 태그가 중복되는(2개 이상 필요한) 경우는 어떡하나요?**

다중 태그 허용(문서당 0~4개, 리스트 타입). 예: 99다59306 → [선순위 채권, 경매, 대항력].
실제 사기 사례는 원인이 겹치는 경우가 많아 다중이 기본.

**Q. 태깅은 어떤 식으로 진행되나요?**

고정 8종 — 전세가율 · 선순위 채권 · 신탁등기 · 압류·가압류 · 경매 · 임차권등기 · 보증보험 ·
대항력. 이 중 7종은 규칙 엔진 판정 근거와 매핑, 대항력만 판정 비연동 보조 태그. 현재는
키워드 규칙 자동 태깅 + 시드 파일 수동 태그, 향후 국내 LLM(EXAONE/Solar) 자동 분류 예정.
⚠️ 고정 8종이 문서·주석 수준일 뿐 코드로 강제되지 않아, 수동 입력 오타가 통과되면 그 판례가
게이트에서 영구 비노출된다. 코드 검증(enum 강제)이 개선 과제.

**Q. AI(LLM)가 태그를 마음대로 만들 수 있나요?**

아니오 — 객관식 설계. 프롬프트에 "허용 태그 목록 밖 금지"를 명시하고 목록 밖 태그는 검증
실패 처리(하네스 실측: Solar·EXAONE 모두 스키마 3/3 통과). 새 사기 유형(예: 가계약금 먹튀)은
AI가 만들지 않고, 사람이 근거와 함께 목록에 정식 추가한 뒤 AI가 그 태그로 분류한다.
💡 역할 분담: 새 유형의 '인식·승인'은 사람, 정해진 유형으로의 '분류'는 AI.

**Q. 태그만으로 사용자와 가까운 판례(근저당 비율·가격대·지역 등)를 찾을 수 있나요?**

아니오, 역할이 나뉜다. 태그 = 서랍 선택(Branch, 대분류 필터). 세부 유사성 = 하이브리드
검색이 서랍 안에서 임베딩(의미) + BM25(키워드)로 정밀 순위를 매긴다. 비율·가격 같은 구체성은
판례 원문이 임베딩 벡터에 녹아 있어 유사도 검색이 담당 — 청킹·태깅으로 구체성이 사라지지 않는다.

**Q. 검수는 사용자가 등기부를 올릴 때마다 사람이 하나요?**

아니오. 검수는 판례를 DB에 적재하는 시점에만 일어난다. 신규 판례는 `verified=False`로 들어가
검색 시 자동 차단되고 사람 승인 후 공개된다. 사용자의 실시간 요청에는 사람 개입이 0이다.
⚠️ 현재 승인 절차는 시드 파일 수동 편집 방식이며, 검수 큐 시트 출력은 설계만 있고 미구현.

**Q. 이 파이프라인은 지금 앱에서 실제로 돌고 있나요?**

⚠️ 아직 아니다. 판례 모듈은 완성되어 별도로 실동작하지만, 리포트 API는 여전히 더미 데이터를
반환 중 — 실제 연결(배선)은 E-3 라운드의 몫.
