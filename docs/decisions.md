### [2026-07-01] 업로드 이미지 형식: 앱에서 항상 JPEG로 변환해 전송
- **결정**: 업로드 이미지는 **앱(프론트엔드)에서 항상 JPEG로 변환**한 뒤 백엔드로 전송한다. 변환은 `flutter_image_compress`(안드로이드 네이티브 코덱, HEIC/HEIF 디코딩 가능, quality 90)로 하고, 업로드 시 **Content-Type을 `image/jpeg`로 명시**한다.
- **이유**: 갤럭시 기본 카메라가 사진을 HEIC/HEIF로 저장하는데 백엔드 허용 형식(JPEG/PNG/WEBP)에 없어 "지원하지 않는 파일 형식" 에러가 발생했다. 백엔드 허용 목록을 늘리는 대신 어떤 형식이 들어오든 앱 단에서 JPEG로 통일하면 백엔드(향후 OCR 포함)를 단순하게 유지할 수 있다. Content-Type을 명시하지 않으면 `application/octet-stream`으로 전송되어 백엔드가 거부하므로 함께 명시한다.
- **출처**: 팀 내부 결정 (실기기 HEIC 업로드 실패 대응).

- **출처**: Upstage 공식 API 문서(`console.upstage.ai/api/docs` — 요청당 image_url 1개, 파일당 100페이지). (STEP 2-B-1) / [확인 필요] PDF data URL 전송 실제 동작은 실호출로 검증.

### [2026-07-23] 지식 DB 확장 방침: 판례·법령 컬렉션 분리
- **처음 의도**: (신규) 벡터DB는 판례(precedents) 단일 컬렉션으로만 구축됨. 향후 법령 조문(statutes) 등 다른 지식 소스 추가 가능성에 대한 방침 부재.
- **최종 결정**: 판례(precedents)와 법령(statutes)은 **같은 벡터DB의 별도 컬렉션으로 분리**한다. 리포트 판례 매칭은 precedents만 검색하고, 향후 챗봇·가이드 기능이 statutes를 활용한다. **법령 컬렉션 구축은 챗봇 기능 착수 시점으로 보류**(지금 구현하지 않음 — 구조만 확인).
- **근거**: ⑴ 컬렉션을 섞으면 판례 매칭 검색에 법령 조문이 노이즈로 올라와 정밀도·게이트 의미가 흐려짐(현행 3중 게이트는 판례 전용 태그·검증 전제). ⑵ 소스별 메타 스키마·인용 형식(사건번호 vs 조문번호)이 달라 분리가 자연스러움. ⑶ Chroma가 한 DB 폴더에 다중 컬렉션을 지원해 인프라 변경 최소(store.py의 컬렉션명 파라미터화 수준 — 구현 시).
- **수집 재사용**: 법령 수집은 판례와 동일한 국가법령정보 공동활용 Open API에서 target 파라미터만 바꿔(prec→law) 가능하며, 조문·부칙·별표 단위로 제공되어 청킹이 판례보다 단순하다. 따라서 statutes 트랙은 신규 구축이 아니라 기존 수집 파이프라인의 재사용 확장이다.
