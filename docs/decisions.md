### [2026-07-01] 테스트/개발 환경: 안드로이드 전용으로 통일
- **결정**: 테스트·개발 환경을 **안드로이드 전용**으로 통일하고, 웹(크롬) 지원 코드는 제거한다.
- **이유**: 최종 타깃이 안드로이드 앱이고, 핵심 기능(카메라 촬영)이 웹에서 제대로 지원되지 않는다(`Image.file` 미지원 등 플랫폼 차이). 이중 작업 방지를 위해 처음부터 안드로이드 기준으로 통일한다.
- **출처**: 팀 내부 결정.

### [2026-07-01] 업로드 이미지 형식: 앱에서 항상 JPEG로 변환해 전송
- **결정**: 업로드 이미지는 **앱(프론트엔드)에서 항상 JPEG로 변환**한 뒤 백엔드로 전송한다. 변환은 `flutter_image_compress`(안드로이드 네이티브 코덱, HEIC/HEIF 디코딩 가능, quality 90)로 하고, 업로드 시 **Content-Type을 `image/jpeg`로 명시**한다.
- **이유**: 갤럭시 기본 카메라가 사진을 HEIC/HEIF로 저장하는데 백엔드 허용 형식(JPEG/PNG/WEBP)에 없어 "지원하지 않는 파일 형식" 에러가 발생했다. 백엔드 허용 목록을 늘리는 대신 어떤 형식이 들어오든 앱 단에서 JPEG로 통일하면 백엔드(향후 OCR 포함)를 단순하게 유지할 수 있다. Content-Type을 명시하지 않으면 `application/octet-stream`으로 전송되어 백엔드가 거부하므로 함께 명시한다.
- **출처**: 팀 내부 결정 (실기기 HEIC 업로드 실패 대응).

### [2026-07-01] 정보추출 도구: Upstage Information Extract 채택 (스키마 기반 구조화 추출)
- **결정**: 등기부등본에서 필드를 뽑을 때 단순 OCR(텍스트만)이 아니라 **Upstage Information Extract**로 **스키마 기반 구조화 추출**을 한다. 추출 스키마는 `backend/app/schemas/registry_schema.py`에 정의하고, 설명 문서는 `docs/registry-schema.md`에 둔다.
- **이유**: 스키마로 "무엇을 뽑을지"를 직접 정의하면 텍스트 파싱 로직 부담이 크게 줄고, **말소 여부·필드 의미까지 LLM이 해석**해 구조화된 JSON으로 돌려준다. 등기부의 핵심 난점인 "말소사항 구분"을 각 항목의 `is_canceled` 필드로 표현하도록 설계했다.
- **출처**: 팀 내부 결정. (Information Extract 스키마 전달 형식 등 세부는 STEP 2-B에서 Upstage 공식 문서로 검증 예정 — `console.upstage.ai/docs`)

### [2026-07-01] Upstage API 키: 현재는 개발자 개인 발급 키(무료 크레딧) 사용
- **결정**: 현재 사용하는 Upstage API 키는 대회 협업 지원 키가 아니라, 지원 승인 지연으로 **개발자가 개인 명의로 Upstage Console에서 직접 발급한 키(무료 크레딧)**다. 키는 `backend/.env`의 `UPSTAGE_API_KEY`로만 관리한다. **향후 대회 공식 지원 키가 도착하면 `.env` 값만 교체**하며, 코드 구조 변경은 불필요하다.
- **이유**: 지원 키를 기다리며 개발을 멈추지 않기 위해 개인 키로 선진행한다. 키를 `.env`(git 미추적)로 분리해 두면 교체가 값 하나 바꾸는 것으로 끝난다.
- **출처**: 팀 내부 결정 (지원 키 승인 지연 대응).

### [2026-07-01] 추출 스키마 구조: 최상위 평면(flat) 구조로 확정
- **결정**: 등기부 추출 스키마를 표제부/갑구/을구 '객체 그룹'으로 묶지 않고 **최상위 평면 구조**로 둔다(표제부 필드는 최상위 scalar, 갑구·을구 목록은 최상위 array, 각 배열 원소만 object). 어느 구에 속하는지는 필드 설명의 `[표제부]/[갑구]/[을구]` 접두어와 문서로 표시한다.
- **이유**: Upstage Information Extract가 **"최상위 속성은 string/integer/number/array만 허용하고 object는 배열 원소로만 허용한다"**는 제약을 두기 때문(동기 호출 한도 100페이지·100속성). STEP 2-A의 중첩 객체 그룹 구조는 이 제약에 걸려 그대로 쓸 수 없어 평면화했다.
- **출처**: Upstage 공식 API 문서(`console.upstage.ai/api/docs`)에서 확인한 스키마 제약. (STEP 2-B-1)

### [2026-07-01] 멀티 이미지 처리: 여러 장을 하나의 멀티페이지 PDF로 병합해 1회 호출
- **결정**: 등기부는 여러 페이지(표제부/갑구/을구)로 나뉘어 사용자가 여러 장을 촬영한다. 이를 **하나의 멀티페이지 PDF로 병합(각 이미지 = 한 페이지)해 Information Extract에 1회 호출**한다. 병합은 `img2pdf`(JPEG 무손실 임베딩)를 사용한다. 이미지가 1장이면 병합 없이 그대로 전송한다.
- **이유**: Upstage 동기 IE 엔드포인트는 **요청당 image_url을 정확히 1개만** 허용한다(여러 image_url 분할 전송 불가). 대신 **파일 하나에 최대 100페이지**를 지원하므로, 여러 장을 한 문서로 묶어 보내야 페이지에 흩어진 근저당·소유자·압류 등이 하나의 통합 결과로 추출된다.
- **출처**: Upstage 공식 API 문서(`console.upstage.ai/api/docs` — 요청당 image_url 1개, 파일당 100페이지). (STEP 2-B-1) / [확인 필요] PDF data URL 전송 실제 동작은 실호출로 검증.

### [2026-07-03] 개발 방식 재정비: 깡통 프로토타입 우선 + 문서 주도 + 승인 게이트
- **결정**: 기능을 하나씩 덧붙이는 방식을 중단하고, ⑴ **전 화면이 더미 데이터로 처음부터 끝까지 관통하는 깡통 프로토타입을 먼저 완성**한 뒤 화면 단위로 실기능을 교체한다. ⑵ 화면은 Repository 인터페이스에만 의존시켜 `DummyRepository ↔ ApiRepository` 교체로 전환한다(더미 구조 = `docs/data-contract.md` API 계약과 동일 형태 유지). ⑶ Phase A~F 로드맵(`docs/plan.md`)과 **Phase 종료 시 사용자 승인 게이트**로 진행한다. ⑷ 산출물 리뷰에 서브에이전트 6종(gap-checker, persona-jisoo, persona-newlywed, design-reviewer, judge-reviewer, rule-auditor)을 투입한다. ⑸ 위험 판정 파이프라인은 "**규칙 엔진이 판정 → LLM은 판정 JSON을 받아 설명 문장만 생성**" 가드레일 구조를 전제로 한다.
- **이유**: 최종 평가가 영상 심사라 끊김 없는 전체 시연 흐름이 개별 기능 깊이보다 중요하고, 기획이 미확정인 상태에서 기능부터 쌓으면 재작업 위험이 크다. 팀 5명 중 개발자가 2명뿐이라 문서 단위 산출물로 비개발 팀원(판례 큐레이션·출처 조사·데모 시나리오)이 분담할 수 있는 구조가 필요하다.

### [2026-07-03] 기능 스코프 확정: 킵/축소/보류/제외
- **결정**: 브레인스토밍 후보 12개(docs/draft/)를 다음과 같이 확정한다.
  - **킵**: 로그인/시작(로컬 목업, 비회원 포함) · 홈 대시보드(분석 이력 통합) · 등기부 이미지 업로드 검색 · **AI 안전도 리포트(핵심)** · 손실 시뮬레이터 · 중개사 질문 생성기 · **온보딩/발급 가이드(신규 추가)** · 리포트 공유(캡처 수준)
  - **축소 킵**: 판례 매칭 — 임베딩 RAG 대신 **위험 패턴별 큐레이션 판례 라이브러리(10~20건) + 규칙 매칭**으로 시작(법제처 API RAG는 백로그) · 계약 여정 코파일럿 — 알림·스케줄링 제외, **정적 단계 체크리스트**로 · 용어 챗봇 — 자유 대화 대신 **용어·개념 설명으로 범위 제한** · 주소 검색 — **UI만 두고 더미**(CODEF 연동 시 교체, 서비스 레이어로 격리)

  - **제외**: 집주인/다른 집 조회 — 개인별 보유주택 수는 확보 가능한 공개 데이터가 없음(안심전세앱도 임대인 동의 기반). 공개된 악성임대인 명단 대조만 리포트 항목으로 흡수
- **이유**: 판단 기준 = ⑴ 영상 심사 임팩트 ⑵ 개발자 2명 구현 비용 ⑶ 데이터 확보 가능성 ⑷ 틀렸을 때 신뢰 훼손 위험(보수적 편향 원칙). 계약서 교차검증 보류와 두 번째 페르소나(신혼부부·바쁜 직장인)는 사용자가 직접 확정.
- **출처**: 팀 내부 결정 (2026-07-03 재정비 계획 승인).
