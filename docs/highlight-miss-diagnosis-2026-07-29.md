## A. 전용면적 — 두 문서 모두 **규칙 버그** (사진 무관)

### 확인한 것

**오늘** `ocr_page_1.json`:

```
word[124]  text='55.56m2'  confidence=0.9086  box=(823,1449)-(916,1476)
codepoints = ['0x35','0x35','0x2e','0x35','0x36','0x6d','0x32']   ← m + U+0032 (ASCII '2')
L22 display  : 55.56m2      ← 이 word 하나가 줄 전체
```

**어제** `ocr_page_3.json`:

```
word[144]  text='39.52m2'  confidence=0.9617  box=(544,1227)-(622,1246)
codepoints = ['0x33','0x39','0x2e','0x35','0x32','0x6d','0x32']
L29 display  : 39.52m2      ← 이 word 하나가 줄 전체
```

**핵심**: 숫자와 단위가 **한 토큰**이고, 단위가 `㎡`(U+33A1)도 `m²`(m+U+00B2)도 아닌
**ASCII `m2`**다. 지시서가 짚은 "한 토큰인지 두 토큰인지"보다 **단위 문자 자체**가 원인이었다.

### 이게 예외가 아니라 규칙임을 확인

두 문서 전체를 훑었다:

| 문서 | `m2`형 | `㎡`·`m²`형 |
|---|---|---|
| 오늘 `ocr_page_1.json` | **7건** (`278.78m2`, `255.71m2`, `185.58m2`, `192.04m2`, `12.88m2`, `390.9m2`, `55.56m2`) | **0건** |
| 어제 `ocr_page_3.json` | **13건** (`199.52m2`, `17m2`, `44.34m2`, `38.03m2`, `16.66m2`, `9.06m2`, …, `39.52m2`) | **0건** |

**Document OCR은 `㎡`를 한 번도 내보내지 않는다.** 20건 전부 `m2`였다.
따라서 `_AREA_UNIT = r"㎡|m²"` 는 이 OCR 엔진에서는 **영원히 매칭될 수 없는 규칙**이었다.

### 줄 묶기(ocr_layout)는 정상이었다

지시서가 의심한 "전유부분 표제부 칸 인식이 갑구·을구와 달라 깨지는가"는 **아니었다**:

```
L 20 (14w): 표시번호 접 수 건 물 번 호 건 물 내 역 등기원인 및 기타사항
L 21 ( 5w): 1 2022년10월7일 제2층 제○○○호 철근콘크리트구조
L 22 ( 1w): 55.56m2                          ← 건물내역 칸이 두 줄로 접힌 것뿐. 정상.
L 23 ( 4w): ( 대지권의 표시 )
```

건물내역 칸(`철근콘크리트구조` + `55.56m2`)이 두 줄로 접혔을 뿐이고, 면적 word는
온전한 자기 bbox를 갖고 있다. 좌표는 처음부터 멀쩡했다.

### 탈락 조건 (한 줄)

`highlight.py:681` — `if not _AREA_UNIT.search(line.squeezed): continue`
→ `re.search(r"㎡|m²", "55.56m2")` 가 `None` 이라 **줄을 건너뛴다.**
아래의 숫자 대조(`'55.56' in '55.56m2'` → True)에는 **도달조차 못 했다.**

### 조치 — 수정함 ✅

두 문서가 **조명·해상도·촬영일이 다른데도 동일하게 실패**했고, 원인이 사진이 아니라
정규식이므로 규칙 버그로 확정했다.

**① 실패를 재현하는 테스트 먼저** (`tests/test_reading_guide.py`)

- `test_면적_단위가_ASCII_m2로_읽혀도_짚어준다[55.56m2]` / `[39.52m2]` — 실측 두 값 그대로
- `test_면적_단위가_없는_줄의_숫자는_여전히_짚지_않는다` — **완화가 아님을 봉인**
  (단위 없는 `55.56`은 대지권비율·다른 층 면적과 구분 불가 → 계속 표시 안 함)

수정 전: 앞 2건 **FAILED** (`assert 'area' in ['separate_land','doc_title']`), 뒤 1건 통과.

**② 수정** (`highlight.py:404`) — 근거 주석을 함께 남겼다.

```python
_AREA_UNIT = _rx(r"㎡|m²|[mM]2")
```

**단위를 같은 줄에 요구하는 조건 자체는 그대로 두었다** — 2앵커 사고방식(숫자만으로는
대지권 비율과 헷갈린다)은 유지하고, 인정하는 **단위 표기만** 실측에 맞췄다.

**③ 증명**

- 신규 3건 포함 **`338 passed`** (전체)
- 저장된 실데이터 재실행:

## B. 공동담보목록 — **중복 제거**가 원인 (⛔ 수정하지 않음)

### 지시서의 4갈래 중 어느 것인가

| # | 가설 | 판정 |
|---|---|---|
| 1 | `공동담보목록` 문자열을 못 읽었다 | ❌ **아니다.** 아래 참조 |
| 2 | 문서당 1건 중복 제거에 걸렸다 | ✅ **이것이다** |
| 3 | 검색어가 `공동담보`라 `공동담보목록`이 안 걸렸다 | ❌ 아니다 — 부분 문자열이라 정상 매칭된다 |
| 4 | 4-1 행이 항목으로 안 만들어졌다 | ❌ 아니다 — `[을구] 순위='4-1' at p3:L35-41,p4:L7`로 정상 생성. (애초에 이 규칙은 항목을 쓰지 않고 줄 텍스트만 본다) |

### OCR은 완벽하게 읽었다

```
p3 L34 ( 2w): 공동담보목록 제2023-4767호
p3 L35 ( 4w): 4-1  4번근저당권공동담  공동담보목록  제2026-6129호
```

### 실제 매칭 결과 — 히트 4건, 그중 1건만 살아남는다

`_match_text_rule(joint_collateral, pages)` 실행 결과:

| # | 페이지 | 줄 | 내용 | 결과 |
|---|---|---|---|---|
| 1 | p2 | L26 | `공동담보 건물 서울특별시 서초구 서초동` | ✅ **이것만 표시됨** |
| 2 | p3 | L9 | `공동담보 건물 서울특별시 서초구서초동` | ❌ 버려짐 |
| 3 | p3 | L34 | `공동담보목록 제2023-4767호` | ❌ 버려짐 |
| 4 | p3 | L35 | `4-1 4번근저당권공동담 공동담보목록 제2026-6129호` | ❌ 버려짐 |

`highlight.py:934` — `for i, (page_index, box) in enumerate(_match_text_rule(...)[:1]):`

### 왜 이게 설계 결함인지 (지시서 지적이 맞다)

`[:1]`은 2026-07-28에 **"같은 사실 1개가 표시 5개로 부풀어 뱃지 개수가 거짓말이 된다"**는
이유로 들어갔다. 토지 별도등기·신청사건은 실제로 **문서 전체에 대한 사실 하나**라 그 논리가 맞다.
그런데 **공동담보는 근저당마다 따로 붙는 정보**라 같은 논리가 성립하지 않는다.

이 문서에서 실제로 벌어진 일:

- 살아남은 표시 = **을구 순위1(23.6억)**의 공동담보
- 버려진 것 = **을구 순위4(20억)**의 공동담보목록(`제2023-4767호`) **그리고**
  그것이 2026년에 **변경됐다는 부기등기**(`4-1` → `제2026-6129호`)

즉 **20억 근저당이 여러 집에 함께 걸려 있다는 신호가 화면에서 통째로 사라진다.**
지시서의 우려가 실측으로 확인됐다.

### 제안 (승인 필요 — 설계 변경이라 수정하지 않았다)

`[:1]`을 **종류별로 가른다**. `TextRule`에 `per_document: bool` 같은 필드를 두고:

- `separate_land`·`pending_application` → **문서당 1건** (지금 그대로. 문서 전체에 대한 사실)
- `joint_collateral` → **근저당별로 표시** (같은 줄 텍스트가 반복되는 머리말성 중복만 제거)

부풀림 방어는 유지하되, 중복 판정 기준을 "문서당 1건"이 아니라
**"같은 목록번호(`제2026-6129호`)당 1건"**으로 바꾸면 둘 다 만족한다 —
위 4건 중 1·2번은 같은 문구 반복이라 접히고, 3·4번은 서로 다른 목록번호라 살아남는다.
`MAX_MARKS_PER_KIND=5` 상한이 이미 있어 띠가 되는 것도 막힌다.

## C. LLM이 센 4번째 근저당 — **저장된 데이터로는 판별 불가**

### 먼저 밝혀야 할 것: 요청하신 자료가 저장되어 있지 않다

지시서는 "저장된 구조화 결과에서 LLM이 반환한 근저당 4건을 나열하라"고 했지만,
**두 번째 경로(LLM 구조화)의 원응답은 어디에도 저장되지 않는다.**

`artifacts.save_json` 호출부는 세 곳뿐이다:

| 호출부 | 저장 파일 |
|---|---|
| `extraction.py:190` | `ie.json` |
| `ocr.py:137` | `ocr_page_*.json` |
| `document_parse.py:143` | `dp_*.json` |

`llm/structuring.py`에는 저장 호출이 **없다**. `out/llm_compare/*.json`이 있지만
**07-28 01:45~01:47**에 만들어진 옛 비교 하네스 산출물이고, 내용도 **다른 문서**
(신정동 행복아파트, 114.756㎡)라 오늘 14:17 실행과 무관하다.

### 그래서 "IE 2 vs LLM 3"은 **세 가지**와 모두 들어맞는다

`cross_check._active_count()`는 **유효 건수만** 센다(`is_active` 필터). 로그에 남은 것도
유효 건수뿐이라, 총 건수와 말소 건수를 되돌릴 수 없다:

| 시나리오 | LLM 총 건수 | 말소 | 유효 | 로그와 일치? |
|---|---|---|---|---|
| ① 3쪽 고아 행을 별건으로 셈 | 4 | 1 | 3 | ✅ |
| ②a 을구 `1-1` 부기등기를 별건으로 셈 | 4 | 1 | 3 | ✅ |
| ③ **말소를 아예 놓침** (순위2를 유효로 봄) | 3 | **0** | 3 | ✅ |

지시서가 "진단이 완전히 갈리는 지점"이라고 지목한 **말소 건수(0건인가 1건인가)가
바로 저장되지 않은 값**이다. 추측으로 채우지 않고 여기서 멈춘다.

### 구조 증거: **가설 ①이 가장 유력**

가설 ①이 말한 고아 행은 **실제로 존재한다.** 3쪽 상단 원문:

```
p2 L33 ( 6w): 2  근저당권설정  2022년11월21일  2022년11월21일  채권최고액 금600,000,000원
─────────────────────────── 페이지 경계 ───────────────────────────
p3 L 1 ( 9w): 순위번호  등 기 목 적  접        권리자 및 기타사항     ← 표 헤더가 다시 인쇄됨
p3 L 2 ( 5w): 수  등 기 원 인
p3 L 3 ( 5w): 제169586호 | 설정계약 | 채무자 법인B …   ← 순위번호·금액 없음
p3 L 6 ( 3w): 근저당권자 ○○○ ○○○○○○-○******
p3 L 9 ( 4w): 공동담보 건물 서울특별시 서초구서초동
─────
p3 L12 ( 4w): 3  2번근저당권설정등  2023년9월1일  2023년8월23일
p3 L13 ( 3w):    기말소  제131541호  해지                          ← 순위 **2번**을 말소
```

지시서 설명과 정확히 일치한다 — **순위번호도 채권최고액도 없고 `제169586호 / 설정계약 /
근저당권자`만 있다.** 더 나쁜 조건이 하나 더 있다: 페이지가 바뀌면서 **표 헤더가 다시
인쇄**되어(L1~L2), LLM에게 넘어가는 레이아웃 텍스트에서 이 조각은 **헤더 바로 아래 첫 행**으로
보인다. 근저당 행의 본문 3종(`설정계약`·`채무자`·`근저당권자`)을 다 갖췄으니 새 항목으로
읽힐 조건이 완비돼 있다.

그리고 **순위3의 말소 행은 "2번"을 지목**하므로, 순위번호가 없는 이 조각은 어떤 말소와도
연결되지 않는다 → **유효로 남는다.** ①의 예측(4건 / 말소 1 / 유효 3)이 정확히 나온다.

참고로 **우리 파서는 이 함정을 통과했다** — 페이지 경계에서 항목을 닫지 않는 설계 덕분에
조각이 순위2에 이어 붙었고, 말소도 정상 인식됐다:

```
[을구] 순위='2'  at p2:L33-35,p3:L2-11
   canceled=True  evidence=p3:L12-13 의 '2번근저당권설정등기말소'
```

### 가설 ②는 왜 덜 유력한가

이 문서에는 을구 부기등기가 **둘** 있다 — `1-1 1번근저당권이전`(p2 L29)과
`4-1 4번근저당권공동담보변경`(p3 L35). LLM이 `-1` 부기등기를 별건 근저당으로 세는
경향이라면 **둘 다** 셌어야 하고, 그러면 유효 4건이 되어 로그(3건)와 어긋난다.
②가 성립하려면 1-1만 세고 4-1은 안 세는 **비대칭 동작**이 필요하다.

다만 완전히 배제할 수는 없다. 저장된 옛 실행에서 Upstage는 갑구의
`1-1 등기명의인표시변경`을 `ownership_changes`의 **별도 항목으로 반환**했다 —
부기등기를 쪼개는 성향 자체는 실재한다.

### 가설 ③(말소 놓침)도 배제할 수 없다

같은 옛 실행에서 **EXAONE은 근저당 2건을 `is_canceled: false`로 반환**했고,
Upstage는 같은 2건을 `true`로 반환했다. "말소 0건" 실패 모드는 이 저장소에서
**이미 관측된 적이 있는 실제 동작**이다.

### 제안 (수정하지 않음 — 규칙 버그가 아니므로)

`llm/structuring.py`(또는 `report_builder._ocr_then_second_opinion`)에서
검증 통과한 payload를 회차 폴더에 저장한다:

```python
artifacts.save_json(run_id, "llm_structure.json", validated.model_dump())
```

- `run_id`는 이미 그 경로까지 흘러와 있다(`_ocr_then_second_opinion(images, run_id)`).
- `artifacts.py`가 이미 **운영 모드 저장 차단 + 최근 5회분 자동 삭제**를 보장하므로
  개인정보 규율은 그대로 지켜진다.
- **크레딧 0원**이고, 다음 실기기 실행 한 번이면 위 세 시나리오가 **공짜로 판별된다.**

교차검증 불일치를 사용자에게 보여주면서 정작 **우리가 그 불일치를 사후에 진단할 수 없는
상태**라, 이 한 줄은 이번 진단이 남긴 가장 실용적인 숙제다.

## D. 안내 문구의 모순 (수정하지 않음 — 제안만)

### 재현 확인

저장된 오늘 실행을 그대로 돌린 결과, **같은 실행에서 둘 다 나갔다**:

```
[매칭] ✗ 실패: 전용면적 — 전용면적 숫자를 ㎡가 있는 줄에서 찾지 못함 (IE 값 55.56㎡)
[응답] 찾아본 것: 표시가 적다는 건 확인할 게 적다는 뜻이에요. 못 읽었다는 뜻이 아니에요.
```

### 원인 — 방어 조건이 **읽는 장부가 다르다**

`highlight.py:1241`:

```python
if money_allowed and not trimmed and not (unplaced or {}):
    notes.append("표시가 적다는 건 확인할 게 적다는 뜻이에요. 못 읽었다는 뜻이 아니에요.")
```

`unplaced`가 증가하는 곳은 **두 군데뿐**이다:

- `848`·`854` — 소유자 이름 실패
- `900`·`906` — 순위 항목(근저당·압류 등) 실패

**`_document_candidates`(주소·전용면적·서류종류·열람일)는 `failures`에만 적고
`unplaced`는 건드리지 않는다** (`1043`, `1049`).
→ 문서 스칼라 실패는 이 방어에게 **보이지 않는다.**

주석은 "금액 보류·상한 생략·위치 실패가 있는데 이 말을 하면 정확히 거짓말이 된다"고
써 두었는데, **위치 실패의 절반(문서 스칼라)을 세지 않고 있었다.**
어젯밤 잡힌 "코드에 침묵 금지라 써 놓고 화면에서 침묵했다"와 정확히 같은 유형이다 —
**의도는 주석에 있고, 조건은 그 의도를 다 담지 못했다.**

### 제안

**권장안** — 방어가 `failures` 장부를 직접 본다:

```python
if money_allowed and not trimmed and not failures:
```

`failures`는 소유자·순위항목·문서스칼라·정규화 실패를 **모두** 모으는 유일한 장부라
(`unplaced ⊂ failures`), 의미상 정확하다: "한 건이라도 못 짚었으면 이 말을 하지 않는다."

**대안** — `unplaced`에 문서 스칼라용 키를 더한다. 다만 `unplaced`는
`cross_check.to_notes(cross, unplaced=unplaced)`에서 **IE 필드 이름으로 조회**되므로
(`unplaced.get(c.field, 0)`), 두 가지 의미를 한 딕셔너리에 겹쳐 담게 된다. 권장하지 않는다.

**함께 필요한 것**: 깨끗한 문서에서는 이 문장이 **여전히 나오는지** 지키는 테스트.
안 그러면 이 문장이 조용히 사라져 반대 방향(과잉 침묵)으로 넘어간다.

> ⚠ A 수정으로 **오늘·어제 문서에서는** 이 모순이 더 이상 재현되지 않는다(전용면적이
> 이제 잡히므로). 하지만 구멍은 그대로다 — 주소를 못 찾는 문서(`1043`)에서 즉시 재발한다.
