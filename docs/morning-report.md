## 4. 내가 내린 결정과 그 이유

**자는 동안 모르게 정해진 것들입니다. 가장 중요한 항목입니다.**

### 결정 ① 매칭 기준을 'IE 결과'로 잡았다 (OCR이 본 것 전부가 아니라)
- **정해야 했던 것**: 사진에서 이름 5명이 보이는데 다 칠할 것인가?
- **선택지**: ⓐ OCR이 찾은 갑구 이름 전부(5명) / ⓑ IE의 `current_owners`만
- **고른 것: ⓑ.** 이 등기부는 소유권이 3번 넘어갔습니다
  (소유자A → 소유자B·소유자C → 소유자D·소유자E). 소유자B·소유자C은 **이미 지분을 전부 넘긴
  옛 소유자**입니다. 형광펜 문구가 "계약서의 임대인 이름이 이 이름과 같은지 확인하세요"
  인데 옛 소유자 이름과 같으면 **오히려 계약해도 된다고 착각시킵니다.**
- **부작용(정직하게)**: 지시서는 "이름 5건이 보일 것"으로 예상했지만, **화면에 보이는
  개수는 IE 응답에 달렸습니다.** 2명이면 2개, 5명이면 5개입니다.
- **되돌리려면**: `backend/app/services/highlight.py`의 `build_highlights`에서
  `owner_names`를 `extract.current_owners` 대신 `items`의 갑구 `NameHit` 전부로 (5줄)

### 결정 ② OCR 장별 호출을 순차로 했다
- **선택지**: ⓐ 장별로도 병렬 / ⓑ 순차
- **고른 것: ⓑ.** 실측 장당 1.6~3.1초인데 IE가 30초 이상 걸립니다. IE와 병렬이면
  OCR 전체(7초대)가 IE 뒤에 완전히 숨습니다. 더 병렬화해도 전체 시간은 안 줄고
  429(요청 제한) 위험만 커집니다.
- **되돌리려면**: `backend/app/services/ocr.py`의 `run_ocr` 루프를 `ThreadPoolExecutor`로

### 결정 ③ OCR이 말소로 보면 IE가 유효라 해도 칠하지 않는다
- **선택지**: ⓐ IE를 믿고 칠한다 / ⓑ 안 칠한다 / ⓒ 등급을 낮춘다
- **고른 것: ⓑ.** ⓒ는 금지 사항(IE↔OCR 교차검증으로 등급 변경 금지)이라 제외했습니다.
  ⓐ는 취소선 그어진 행에 형광펜을 칠하게 되어 **이미 없어진 빚을 현재 위험으로**
  오해시킵니다. **판정은 그대로**입니다 — 리포트는 여전히 그 근저당을 선순위채권으로
  계산합니다. 화면에 형광펜이 없을 뿐입니다.
- **되돌리려면**: `_match_money_entry`에서 `_active_rights_items` → 전체 items

### 결정 ④ 표시 문구를 백엔드에 뒀다
앱이 아니라 서버에서 `title`/`body`/`caution`을 만듭니다. 공동명의 인원수 같은 값이
서버에만 있고, 문구를 한 곳에서 고칠 수 있어서입니다. LLM은 개입하지 않습니다(고정 템플릿).
- **되돌리려면**: `highlight.py`의 `_OWNER_BODY`/`_MORTGAGE_BODY`/`_JEONSE_BODY`를
  앱으로 옮기면 됩니다.

### 결정 ⑤ 사진을 메모리에만 둔다
- **선택지**: ⓐ 갤러리 원본 경로를 다시 읽는다 / ⓑ 서버로 보낸 JPEG 경로를 기억한다
  / ⓒ 앱 저장소에 복사해 영구 보관
- **고른 것: ⓑ.** ⓐ는 **좌표가 전부 어긋납니다** — 좌표는 서버로 보낸 JPEG 픽셀 기준인데
  갤러리 원본은 해상도·EXIF 회전이 다릅니다(변환기가 quality 90으로 재인코딩합니다).
  ⓒ는 금지 사항(사진 영구 저장 금지)입니다.
- **부작용**: 앱을 껐다 켜면 사진이 사라집니다 → 이력에서 연 리포트에는 진입점이
  비활성화됩니다.
- **되돌리려면**: `frontend/lib/state/registry_photo_store.dart`를 파일 복사 +
  SharedPreferences 방식으로

### 결정 ⑥ 사진 한 장이라도 사라지면 전부 없는 것으로 친다
임시 폴더는 OS가 임의로 비웁니다. 3장 중 2번이 사라졌는데 1·3번만 보여주면
**page 인덱스가 밀려 엉뚱한 사진에 형광펜이 그려집니다.**
- **되돌리려면**: `registry_photo_store.dart`의 `pathsFor()`에서 존재 확인 루프 제거

### 결정 ⑦ 이미지 표시 크기를 직접 계산했다
`Image.file(fit: BoxFit.contain)`에 맡기면 **실제로 그려진 사각형을 알 수 없습니다.**
이미지가 레터박스(위아래 여백)로 들어가면 오버레이가 그만큼 밀립니다.
`_fitted()`로 contain 결과를 직접 구해 `SizedBox`로 고정하고 `BoxFit.fill`을 씁니다.
- **되돌리려면**: `registry_viewer_screen.dart`의 `_RegistryPageState.build`

### 결정 ⑧ 하단에 칩 목록을 넣었다 (지시서에 없던 추가)
등기부 글자는 화면 맞춤 배율에서 3~4px입니다. 형광펜만으로는 무엇을 짚었는지
알 수 없어서, 뱃지 번호 + 제목을 **글로** 적었습니다. 라운드 3에서 페르소나 2인 모두
"이게 없었으면 이 화면을 못 썼다"고 했습니다.

### 결정 ⑨ 터치 영역을 최소 48dp로 넓혔다
이름 bbox는 원본 44px / 878px = 5%입니다. 화면 폭 360dp면 18dp밖에 안 돼 못 누릅니다.
그리는 것은 원래 크기 그대로이고, 넓힌 것은 판정 영역뿐입니다.

### 결정 ⑩ (라운드 3 반영) 탭은 '가장 가까운' 표시를 연다
48dp로 넓힌 터치 영역은 표의 인접 행끼리 **반드시 겹칩니다.** 첫 매칭을 쓰면 항상
앞 번호가 이겨 **④를 눌러도 ①이 열립니다.** 시트 본문이 같아서 사용자는 틀린 걸
눈치조차 못 챕니다(공동명의에서 필연적으로 발생). `highlightAt()`이 탭 지점에서
가장 가까운 표시를 고르게 바꿨습니다.

### 결정 ⑪ (라운드 3 반영) 빨간 타원에 흰 halo를 둘렀다
디자인 리뷰어 실측: 우리 빨강(#D32F2F)과 등기부 인쇄 빨강(#FF0000)의 대비가
**1.24:1 — 사실상 같은 색**입니다. 그런데 **의미가 정반대**입니다.
등기부의 빨간 줄 = **말소(끝난 권리)**, 우리 빨강 = **살아있는 위험**.
사용자가 "이건 원래 종이에 있던 빨간 줄이네"로 읽으면 **살아있는 근저당을 놓칩니다.**
인쇄 잉크는 halo를 가질 수 없으므로, 흰 halo가 "앱이 얹은 것"이라는 형태 단서가 됩니다.
- **되돌리려면**: `HighlightPainter._paintCircle`

### 결정 ⑫ (라운드 3 반영) 표시가 0개여도 "무엇을 찾아봤는지"를 말한다
**리뷰어 3인이 동시에 지목한 최다 지적**입니다.
서연: *"지금 이 샘플에서는 신뢰도를 **내립니다**. 근데 '말소된 근저당 2건은 확인 후
제외했어요' 한 줄이 들어가는 순간 같은 화면이 **가장 강력한 신뢰 장치**로 뒤집혀요."*
`Report.checkedNotes`를 신설해 반영했습니다. 말소돼서 안 칠한 것과 **유효한데 위치를
못 찾아 못 칠한 것**을 구분해 적습니다(후자는 리포트 근거 카드로 안내).
- **되돌리려면**: `highlight.py`의 `_build_checked_notes()` + 뷰어의 `_CheckedNotes`

### 결정 ⑬ 쪽 누락이 감지되면 금액 표시만 보류한다 (이름은 유지)
말소 근거 행이 안 올린 페이지에 있으면 말소를 놓칩니다. 페이지 표식(`N/M`)으로
누락을 감지하면 금액 표시를 끕니다. **이름은 유지**하는 이유: 표시를 다 끄면 정상
사진에서도 아무것도 안 보이게 되는 부작용이 크고, 이름은 "말소 근거가 다른 장에 있다"는
실패 양식이 없습니다(IE의 `current_owners`가 직접 답합니다).
- **되돌리려면**: `ocr_layout.check_document()`의 `ok_to_highlight_money` 분기

### 결정 ⑭ `docs/data-contract.md`를 만들지 않았다
지시서는 그 파일에도 적으라고 했지만 **그 파일은 존재하지 않습니다.**
(CLAUDE.md 문서 맵에는 이름이 있으나 실제 파일은 `docs/api-contract.md` 하나뿐)
새 파일을 만들면 어느 쪽이 진짜인지 헷갈리므로 `api-contract.md` §9에만 적고
그 사실을 §9 끝에 명시했습니다.

## 5. 예상과 달랐던 것

### ① 표제부·매매목록 항목이 '말소'로 오탐됨
- **기대**: 항목 그룹화가 갑구·을구만 건드릴 것
- **실제**: `[매매목록 순위 2]`, `[표제부 순위 2]`가 말소근거행으로 잡혔다
- **원인**: 4.png 마지막 항목이 열린 채 1.png로 넘어가면서, 1.png 표지의
  `등기사항전부증명서(**말소**사항 포함)` 문구를 항목 안으로 삼켰다
- **대응**: ⑴ 표지·발급정보 줄은 어떤 항목에도 붙이지 않는다(`_DOC_PREAMBLE`)
  ⑵ 말소 판정을 갑구·을구에서만 한다(`RIGHTS_SECTIONS`) → 오탐 2건 사라짐

### ② 기존 백엔드 테스트가 61건이 아니라 86건
- **기대**: 지시서에 적힌 61건
- **실제**: `pytest -q` → **86 passed**
- **원인**: 지시서 작성 이후 테스트가 늘어난 것으로 보입니다(확인 불가)
- **대응**: 기준선을 86건으로 잡았습니다. 지금은 **125건 통과**(86 + 신규 39)

### ③ 말소 행이 갈라지는 것은 '줄 묶기 실패'가 아니었다
- **기대**: 줄 묶기 허용값(tol)을 키우면 해결될 것
- **실제**: 줄 묶기는 정상이었습니다. 표의 **등기목적 칸 안에서 글이 2줄로 접히고**
  그 사이에 접수·등기원인 칸 날짜가 끼어 있었습니다
- **원인**: 줄 단위로 이어붙이면 `1번근저당권설정등` + (날짜) + `기말소`로 끊깁니다
- **대응**: 등기목적 컬럼 x밴드 안의 word만 이어붙였습니다. tol을 키우는 방법은
  다른 항목까지 뭉개져 순위 구분이 무너지므로 버렸습니다

### ④ 이름 버그의 원인이 정규식 자체였다
- **기대**: `_clean_name`의 word 경계 스냅 로직을 고치면 될 것
- **실제**: 실제 word 배열은 `['…','제50495호','매매','소유자D','○○○○○○-○******']`로
  **'소유자D'이 이미 독립 word**였습니다. 문자 단위 정규식이 줄을 공백 없이 이어붙여
  매칭하다 `매매`+`소유자D`을 한 덩어리로 삼킨 것이었습니다
- **대응**: 문자 단위 → **word 단위**로 전면 교체. bbox 181px → 43px

### ⑤ 페이지 꼬리말에 쪽수 표식이 있었다 (좋은 쪽으로 예상과 달랐다)
라운드 4에서 "말소 근거 행이 다른 장에 있으면?"을 고민하다 꼬리말을 뒤져 보니
`1/5`, `5/5` 표식과 전 페이지 동일한 발급확인번호가 있었습니다. 이것으로 **쪽 누락 ·
사진 순서 어긋남 · 다른 등기부 섞임** 세 가지를 한 번에 방어할 수 있게 됐습니다.

## 6. 못 했거나 포기한 것

### 6-1. 실기기 육안 확인 — **안 했습니다**
`flutter build apk --debug`가 성공한 것까지입니다. 폰에 설치해 화면을 본 적이 없습니다.
좌표가 실제로 글자 위에 얹히는지는 아침에 확인해야 합니다.
**다시 하려면**: `docs/morning-check.md` 절차를 따르면 됩니다.

### 6-2. Information Extract 실호출 — **안 했습니다**
크레딧과 시간 때문입니다. 그래서 모르는 것이 3가지 있습니다.
- IE의 `current_owners`가 실제로 몇 명을 돌려주는지 → **형광펜 개수가 결정됩니다**
- IE의 `mortgages[].rank_number`가 실제로 채워지는지 → 비어 있으면 금액 매칭이
  **전부 실패**합니다(설계상 순위번호 없으면 좌표를 안 줍니다)
- IE 응답과 OCR 결과가 실제로 잘 맞물리는지
**다시 하려면**: 백엔드를 띄우고 앱에서 분석을 1회 실행하면 됩니다(크레딧 소모).

### 6-3. 유효 근저당 하이라이트 — **실데이터로 검증 못 했습니다**
이 등기부는 유효 근저당이 0건입니다. 금액 매칭 경로(`_match_money_entry`)는
**합성 테스트(손으로 만든 표 좌표)로만** 검증됐습니다.
**다시 하려면**: 유효 근저당이 있는 등기부 샘플이 필요합니다.

### 6-4. 폰 촬영본 — **검증 못 했습니다**
샘플 5장은 전부 인터넷등기소 PDF 캡처입니다. 그림자·기울기·구겨짐·조명 얼룩이
하나도 없습니다. 실제 사용자는 책상 위 종이를 폰으로 찍습니다. 그때
줄 묶기·컬럼 밴드가 얼마나 견디는지 **모릅니다.**
**이것이 이 기능의 채택 여부를 가르는 가장 큰 미지수입니다.**
**다시 하려면**: 등기부를 인쇄해 폰으로 찍고 `scripts/test_ocr_coords.py`를 실호출(크레딧 소모).

### 6-5. 칩을 눌렀을 때 해당 위치로 확대·이동 — **의도적으로 포기했습니다**
페르소나 2인이 모두 "이거 하나만 되면 이 화면의 가치가 확 올라간다"고 했습니다.
동의합니다. 하지만 `TransformationController`로 목표 사각형을 화면 중앙에 맞추는
애니메이션은 경계·최소배율과 얽혀 **잘못 만들면 화면이 튑니다.** 밤에 눈으로 검증할
수 없는 상태에서 넣기엔 위험이 컸습니다.
**다음 세션 1순위**입니다. 되돌릴 필요 없는 순수 추가 기능입니다.

### 6-6. 그 밖에 기록만 하고 넘어간 것
`docs/ocr-highlight-findings.md` §5.4에 표로 정리했습니다 — 시트에 확대 썸네일 /

## 8. 위험 신호 — 지금은 되지만 나중에 문제가 될 수 있는 것

| 신호 | 무엇이 위험한가 |
|---|---|
| **꼬리말이 잘린 사진에서는 쪽 누락을 알 수 없다** | `check_document()`가 "판별 불가"로 두고 진행합니다. 이 경우 **말소 누락 경로 ①이 여전히 열려 있습니다.** 우리 3·4.png가 정확히 이 상태입니다 |
| **컬럼 밴드가 표 헤더에 의존한다** | 헤더 줄(`순위번호 등기목적 …`)이 안 읽히면 순위번호를 못 잡고 항목이 만들어지지 않습니다. 사진이 기울거나 헤더가 잘리면 조용히 0건이 됩니다 |
| **레이아웃 임계값이 이 샘플 기준이다** | `_GAP_RATIO=1.8`, `_RANK_BAND_MARGIN=0.15`, `_NAME_GAP_RATIO=2.5`. 깨끗한 캡처 1건의 실측에서 나온 값입니다. 촬영본에서 어떻게 흔들릴지 모릅니다 (⚠ 이 값들은 **레이아웃 튜닝값**이며 위험 판정 임계값이 아닙니다 — risk-scoring 규칙의 "출처 없는 수치 금지" 대상 아님) |
| **`convertToJpeg`의 EXIF 기본값에 의존한다** | `keepExif: false`/`autoCorrectionAngle: true`를 명시했지만, 이건 라이브러리 기본값입니다. 라이브러리가 바뀌면 좌표가 통째로 어긋납니다. 서버에 경고 로그를 심어 뒀습니다 |
| **임시 폴더 사진이 언제든 사라질 수 있다** | OS가 비우면 진입점이 조용히 비활성화됩니다. 시연 중에 일어나면 곤란합니다 — 리허설 직전에 분석을 새로 돌리세요 |
| **pytest 9건이 `backend/out/`에 의존한다** | 그 폴더가 없으면 skip됩니다(실패는 아님). 실명이 있어 커밋할 수 없는 구조적 한계입니다. 재생성 방법은 테스트 skip 메시지에 적어 뒀습니다 |
| **`checkedNotes` 문구가 하드코딩 템플릿이다** | 조건 분기가 늘어나면 문구가 어긋날 수 있습니다. `_build_checked_notes()` 한 함수에 모아 뒀습니다 |
| **뷰어가 리포트를 다시 fetch한다** | `getReport(reportId)`로 서버에서 다시 읽습니다. 서버가 재시작되면 메모리 스토어가 비어 404가 됩니다(리포트 화면도 마찬가지라 새로 생긴 문제는 아닙니다) |

## 10. 내가 내려야 할 결정

### 결정 1. 형광펜을 '현재 소유자만' 칠할 것인가, '갑구 이름 전부'인가
- **선택지 A (현재 구현)**: IE의 `current_owners`만. 2~5개 표시
- **선택지 B**: 갑구에서 읽힌 이름 전부. 5개 표시(옛 소유자 포함)
- **추천: A 유지.** 옛 소유자를 칠하면 "이 사람이 임대인"이라고 착각시킵니다. 형광펜
  문구가 "계약서 이름과 같은지 확인하세요"인데, 옛 소유자와 일치하면 **오히려 계약해도
  된다고 믿게 만듭니다.** 미탐 방향의 오류입니다.
- **다만**: 시연에서 "형광펜이 5개 칠해지는 화면"이 더 인상적이라면 B가 유혹적일 수
  있습니다. 그때는 옛 소유자에 **다른 색·다른 문구**("과거 소유자입니다")를 줘야 합니다.

### 결정 2. 칩 탭 → 해당 위치로 확대·이동을 만들 것인가
- **추천: 만드세요.** 페르소나 2인이 모두 "이거 하나면 화면 가치가 확 올라간다"고
  했습니다. 지금은 무엇이 표시됐는지는 알아도 **종이의 어느 줄인지** 찾으려면 직접
  확대해야 합니다. 순수 추가 기능이라 되돌릴 위험이 없습니다.
- **비용**: 반나절. `TransformationController`로 목표 사각형을 중앙에 맞추는 애니메이션.
  실기기에서 눈으로 확인하며 만들어야 합니다(밤에 못 한 이유).

### 결정 3. 폰 촬영본으로 재검증할 것인가 (채택 여부의 핵심)
- **추천: 반드시 하세요.** 지금은 "깨끗한 PDF 캡처에서는 된다"까지만 증명됐습니다.
  등기부를 인쇄해 폰으로 찍고 `test_ocr_coords.py`를 실호출하면 30분이면 답이 나옵니다.
  결과가 나쁘면 **기능을 폐기할지 판단할 근거**가 되고, 좋으면 채택 근거가 됩니다.
- **비용**: 크레딧 몇 장 + 30분.

### 결정 4. 유효 근저당이 있는 등기부 샘플을 구할 것인가
- **추천: 구하세요.** 금액 매칭 경로가 **실데이터에서 한 번도 성공한 적이 없습니다**
  (합성 테스트만). 시연에서 "빚에 빨간 동그라미"를 보여줄 계획이라면 필수입니다.
- **대안**: 유효 근저당이 있는 등기부를 못 구하면, 시연을 **이름 대조 시나리오**로
  구성하는 것도 방법입니다(공동명의 4명 = 실제로 사고가 잦은 항목이라 설득력이 있습니다).

### 결정 5. 이 기능을 채택할 것인가 — decisions.md에 기록할 것인가
- **추천: 결정 3의 결과를 보고 판단하세요.** 지금은 `docs/ocr-highlight-findings.md`에
  "채택 미확정"으로만 남겨 뒀고 `decisions.md`·`plan.md`는 손대지 않았습니다.

  위험하다는 게 서연의 지적이었습니다.
- **추천: 올리세요. 단 별도 승인 절차로.** 이건 **판정 계층 변경**이라 이번 작업의
