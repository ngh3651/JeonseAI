## 00:35 [2] 예상 못 한 발견 — `check_document`의 실제 버그

`ocr_page_1.json`만 저장 시각이 다르다(23:06 vs 나머지 22:44). 조사해 보니:

- `ocr_page_1.json`: 페이지 표식 **없음**, 주소 줄 **없음**, 열람일시 **없음**,
  등기부 키워드(갑구·을구·근저당·순위번호…) **전부 0건**. 즉 **등기부가 아닌 다른 사진**이다.
- `ocr_page_2~5.json`: 표식 `2/5`, `3/5`, `4/5`, `5/5` — 같은 문서(주소 해시 동일).

즉 이 묶음은 **1쪽(표지+표제부)이 빠진 채, 무관한 사진 한 장이 그 자리를 채우고 있다.**

그런데 `check_document()`는 `ok_to_highlight_any=True, money=True, notice=None`을 돌려준다.
이유는 코드를 보면 명확하다:

```python
if markers:
    total = markers[0][1][1]      # 5
    if len(pages) < total:        # len(pages)=5 → 5 < 5 == False → 통과
```

**무관한 사진 1장이 `len(pages)`를 5로 채워 '쪽 누락' 방어를 무력화했다.**
표식이 읽힌 쪽은 4장뿐인데(2,3,4,5) 그 사실이 판정에 쓰이지 않는다.
`발급확인번호`가 이 문서에서는 아예 안 잡히고, 주소도 그 사진엔 없어 `len(addresses)>1`도
False라 두 번째 방어선도 통과한다.

이건 이 방어가 막으려던 **바로 그 시나리오**다 — 빠진 쪽에 말소 근거 행이 있으면
말소된 근저당에 형광펜이 간다. → **작업 F에서 함께 고친다**(§F가 사진 묶음 점검을
다루는 유일한 작업).

**부수 발견**: `_save_raw_ocr`는 `ocr_<파일stem>.json`으로 저장하는데 앱은 사진을 항상
`page_N.jpg`로 보낸다 → **분석할 때마다 이전 원응답이 덮어써진다.** IE 쪽은
`ie_<타임스탬프>.json`이라 남는데 OCR만 사라진다. 작업 E에서 같이 다룬다.

### 결과 ③ 18 vs 16 차이의 정체 — `provisional_seizures`

항목별 `rank_number` 분포를 세어 보니:

| 배열 | 순위번호 분포 (3개 파일 합산) |
|---|---|
| `seizures` | 2×3, 4×3, 7×3, 8×3, 9×3 |
| `provisional_seizures` | 2×3, 4×**1**, 7×3, 8×3, 9×**1** |

→ **IE가 압류와 가압류에 같은 순위번호(2,4,7,8,9)를 중복 배정한다.**
1회차만 4번·9번을 `provisional_seizures`에도 넣었고(=5건), 2·3회차는 빼서 3건이 됐다.

같은 순위번호를 OCR 등기목적으로 확인하면:
`가압류 = {2, 7, 8}` / `압류 = {4, 9}` (3번은 항목 경계가 붙어 혼재).
**2·3회차의 `provisional_seizures` = {2,7,8}은 OCR이 읽은 가압류 집합과 정확히 일치한다.**

→ 이건 이번 세션 최대 성과 후보다. **IE 단독으로는 압류/가압류를 안정적으로 못 가른다.
등기목적 텍스트를 읽는 두 번째 경로가 그 구분을 준다.** 작업 B(3경로)의 존재 이유가
가설이 아니라 실측으로 뒷받침됐다. → `docs/presentation-material.md`에 기록.
