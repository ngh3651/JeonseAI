## 1. 실행 계획 (작업 시작 시 기록)

### 미션 요약
위험 판정 리포트에 "유사 실제 판례" 섹션을 붙이는 RAG 기반 환경을 완성한다.
목표 상태: **판례 대량 데이터 + API 키만 꽂으면 수집→전처리→청킹→임베딩→벡터DB→검색→Solar 설명이 바로 도는 것.**

### 불변 원칙 (이번 작업의 실패 조건)
1. **판례 = 설명 전용.** 검색된 판례가 판정·점수·등급에 영향을 주는 코드 경로가 없어야 함 (rule-auditor 최종 감사).
2. **환각 금지.** LLM은 검색으로 실제 가져온 판례만 인용. 검색 실패·유사도 하한 미달 → 정직한 폴백. 인용에 사건번호·출처 필수.
3. **국내 스택.** LLM=Solar Pro, 임베딩=Upstage API 또는 로컬 오픈모델. 해외 API 금지.
4. 기존 규칙 엔진·E-1·E-2 산출물 훼손 금지. 프론트엔드 구현 금지(계약 문서까지만).

### 아키텍처 방향 (가설 — T1 리서치·judge-reviewer 채점 후 확정)
- 쿼리 원천이 **사용자 자연어가 아니라 규칙 엔진의 판정 JSON(구조화된 위험 사유)**이라는 특성상:
  - 위험 유형별 **분기 검색(Branch/Router)** + **메타데이터 필터**가 자연스럽고 구현 비용이 낮다.
  - 판정 사유→검색 질의 변환은 **결정적 템플릿**(위험 유형별 질의문)이 1차, HyDE(가상 판례 요지 생성)는
    법률 도메인 임베딩 갭을 메우는 후보 — 단 LLM 호출 추가 비용·환각 경로 증가와 저울질.
  - Self/Adaptive/Agentic RAG의 반복 판단 루프는 "쿼리가 이미 구조화되어 있다"는 우리 특성에서 이득이 작다(가설).
- 검색 품질: 순수 벡터 유사도만 믿지 않는다 — **하이브리드(BM25 키워드 + 벡터) + 위험 유형 메타데이터 필터 +
  판결요지 중심 청킹 + 유사도 하한 게이트**(미달 시 비노출) 조합.

### 리스크·우회책
- 법제처 API는 OC(등록 이메일 ID) 필요 → 키 없이 호출 막히면: 수집 스크립트는 완성만 해두고
  시드 판례(웹 검증)로 E2E 검증. **대기 금지 원칙.**
- Upstage 임베딩 실호출 실패(크레딧·키) → 결정적 오프라인 임베딩 백엔드(해시 기반)로 파이프라인 검증,
  실키 주입 시 재임베딩 스크립트 1회 실행이면 됨.
- Python 3.14로 chromadb/faiss 설치 실패 가능 → 경량 자체 벡터 저장소(수치 연산 + 파일 영속화)로 폴백,
  인터페이스 뒤에 숨겨 추후 교체 가능하게.

## 4. RAG 아키텍처 선정 결과 (judge-reviewer 채점 포함)

**채택: 분기(Branch) RAG + 하이브리드 검색** — 판정 → 태그 결정적 파생 → 태그별 결정적
질의 + 메타 필터 분기 검색 → RRF 융합 → 매칭 태그 수 정렬. LLM은 검색 질의조차 만들지
않고, 개입 지점은 "검색된 판례의 쉬운 설명" 한 곳뿐.

judge-reviewer 채점(대회 배점): 창의성 22/30 · 혁신성 15/20 · 추진성 21/30 · 성장성 15/20 =
**73/100, "채택안이 5안 중 최선 — 아키텍처 교체가 아니라 문서 마감·지표 정직화·화면 통합이
점수를 올린다"**. 탈락안 비교: Simple(설명 가능성 결여) · HyDE(환각 서사 자충수 — "가상 판례를
지어내 검색"은 심사 방어 불가) · Self-RAG(구조화된 쿼리에 루프 불필요) · Agentic(영상 시연
비결정성 리스크 최악). 채점이 짚은 시연 카드: **"AI가 판례를 못 찾으면, 못 찾았다고 말합니다"**
(게이트에 막혀 정직하게 비는 판례 섹션) — E-3 화면 통합 시 시연 대본 후보.

## 5. 검색 평가셋 성적 변화

평가셋: 위험 유형별 "이 판정이면 이 판례가 상위" 기대 쌍 10 시나리오
(`backend/data/precedents/eval_set.json`). 지표: Hit@K(상위4 안에 정답), P@1(1위 정답),
Recall(정답 집합 회수율), MRR. **filtered = 실서비스 경로(태그 필터+게이트) /
unfiltered = 필터 없는 순수 하이브리드 랭킹(민낯)**.

| 단계 | 백엔드 | filtered | unfiltered |
|---|---|---|---|
| 기준선 | hash | Hit@K 90% · P@1 100% · MRR 0.90 | Hit@K 100% · Recall 97% |
| 수리 ① 대항력 템플릿 누락 | hash | **Hit@K 100%** · MRR 1.00 | 동일 |
| Upstage 실임베딩 | upstage | Hit@K 100% · P@1 100% · Recall 93% · MRR 1.00 | Hit@K 100% · Recall 97% · MRR 0.95 |
| **최종** (감사 반영: 2024도15455 verified 강등) | upstage | Hit@K 90% · P@1 83% · Recall 83% · MRR 0.90 | Hit@K 100% · P@1 100% · Recall 97% · MRR 0.95 |

최종 행의 하락은 회귀가 아니라 **verified 게이트의 실동작**이다 — 공식 원문이 없는 전세가율
판례(2024도15455)를 rule-auditor 감사에 따라 검수 대기(`verified=false`)로 강등했고, filtered
경로(실서비스)는 그 시나리오에서 판례를 정직하게 비운다. 정민재 검수·원문 확보 → `true` 승격
시 100% 복귀(unfiltered가 검색 자체는 정상임을 보여준다).

### 대량 수집 스트레스 테스트 (n=7 → 26 문서, 62 → 373 청크)

"키만 꽂으면 대량 수집" 주장을 실증하기 위해 법제처 API로 대법원 판례 20건을 실수집
(`--query "임대차 보증금" --org 400201`)해 코퍼스를 3.7배로 늘리고 재측정했다:

| 모드 | n=7 (시드만) | n=26 (시드+대량 수집) | 해석 |
|---|---|---|---|
| filtered (실서비스) | Hit@K 90% · MRR 0.90 | **Hit@K 90% · MRR 0.90 (무변화)** | 게이트(미검수 차단)+태그 필터가 노이즈 6배에도 견고 |
| unfiltered (민낯) | Recall 97% · MRR 0.95 | Recall 85% · MRR 0.82 | 신규 수집분 중 **실제 관련 판례**(2024다326398 등 최근 임대차 판결)가 시드를 앞서는 경우 발생 |

unfiltered 하락의 실체를 확인한 결과 대부분 "쓰레기가 아니라 다른 관련 판례가 상위로"였다 —
사용자 관점에서는 무해하나, **평가셋의 정답 집합이 시드 7건에 고정돼 있어 생기는 측정 한계**다.
수집분이 검수(큐레이션)를 거쳐 승격되면 eval_set.json 기대 쌍도 함께 확장해야 한다(§7-5).
수집분 20건은 자동 태깅 + `verified=false`(사람 검수 전 노출 차단 — 감사 반영으로 ingest 기본값을
보수화)로 인덱스에 들어 있으며, 정민재 검수 워크플로의 실전 재료가 된다.

수리 ②(평가셋 외 발견): 문서 불완전 floor로 '확인 필요'가 된 카드(전세가율 60%·채권 0건)에
깡통전세·경매 판례가 붙는 과잉 매칭 → 태그 파생을 보수화(실측 기준 초과·실채권 존재 시만).
유사도 하한 0.45는 실측(정답 쌍 0.48~0.64)에서 캘리브레이션.

⚠ **정직성 주의(judge-reviewer 지적 수용)**: 위 100%는 **n=7 코퍼스의 포화 지표**다.
질의 템플릿과 시드를 같은 밤에 같은 손이 만들었다는 자기충족 한계가 있다. 발표에 단독 인용
금지 — 대량 수집 후 재측정이 전제이며, 그래서 unfiltered 수치를 항상 병기한다.

## 6. GPU 실행 계획 요약 ("GPU로 DB 형성이 가능한가" 검토 답변)

- **결론: 가능하고, 오히려 여유롭다.** RAG는 학습이 아니라 임베딩+저장이므로 GPU 필요 구간은
  **대량 임베딩 배치 1회뿐**이고, 코드상 실행 지점은 `LocalEmbeddingBackend` 하나로 격리돼 있다
  (`PRECEDENT_EMBEDDING_BACKEND=local` + 재적재 스크립트 1회).
- **모델**: `nlpai-lab/KURE-v1`(568M, 1024차원, 8K 컨텍스트, MIT, 고려대) — 한국어 검색 벤치
  최상위권(법률 포함 AutoRAGRetrieval에서 검증). 대조군 `dragonkue/snowflake-arctic-embed-l-v2.0-ko`
  (자체 벤치 법률 0.909). 확정 전 두 모델을 우리 평가셋으로 A/B 권장.
- **규모 추정**(fp16, 근거는 TEI/A100 실측 보고): 판례 10만 건 ≈ 청크 30만 ≈ 1.5억 토큰 →
  **A100에서 ~40분–1시간, RTX 4090급 2~6시간**. VRAM 8~12GB면 충분. 우리 현실 규모(수천~수만 건)는
  어느 단일 GPU든 수십 분 내. 512~1,024토큰 청킹 유지(8K 통짜 임베딩은 메모리 급증 — 금지).
- **주의**: sentence-transformers가 Python 3.14 미지원 — **배치는 Python 3.12~3.13 별도 venv**로.
  임베딩 후 `index/` 폴더 복사만으로 서비스 이전 완료(Chroma는 폴더가 곧 DB). 서비스 런타임은
  질의 1건 임베딩뿐이라 GPU 불필요(운영은 Upstage 백엔드 유지 권장).
