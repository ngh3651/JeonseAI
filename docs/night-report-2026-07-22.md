## 1. 실행 계획 (작업 시작 시 기록)

### 미션 요약
위험 판정 리포트에 "유사 실제 판례" 섹션을 붙이는 RAG 기반 환경을 완성한다.
목표 상태: **판례 대량 데이터 + API 키만 꽂으면 수집→전처리→청킹→임베딩→벡터DB→검색→Solar 설명이 바로 도는 것.**

### 불변 원칙 (이번 작업의 실패 조건)
1. **판례 = 설명 전용.** 검색된 판례가 판정·점수·등급에 영향을 주는 코드 경로가 없어야 함 (rule-auditor 최종 감사).
2. **환각 금지.** LLM은 검색으로 실제 가져온 판례만 인용. 검색 실패·유사도 하한 미달 → 정직한 폴백. 인용에 사건번호·출처 필수.
3. **국내 스택.** LLM=Solar Pro, 임베딩=Upstage API 또는 로컬 오픈모델. 해외 API 금지.
4. 기존 규칙 엔진·E-1·E-2 산출물 훼손 금지. 프론트엔드 구현 금지(계약 문서까지만).

### 사전 정찰 결과 (착수 시점)
- **네트워크**: law.go.kr 200 / PyPI 200 / api.upstage.ai 도달(401=키 필요, 정상). 외부 접근 가능.
- **환경**: Python 3.14.3 (.venv) — 최신 버전이라 chromadb·faiss 등 바이너리 의존성 호환 리스크 있음 → 설치 검증 후 벡터DB 결정.
- **시드 판례**: 미션이 언급한 "정민재 수집 대법원 판례 7건"은 저장소에 **아직 없음**
  (`backend/data/cases.json`은 `is_sample: true` 샘플 2건뿐, `docs/claude-chat/`도 README만).
  → 우회책: 웹 검증을 거친 실제 대법원 판례로 시드 7건을 직접 구성하고, 검증 상태를 데이터에 명시.
  정민재 실데이터 도착 시 같은 양식으로 교체·증분하면 됨.
- **기존 자산 재사용**: E-2의 Solar 클라이언트 패턴(`services/explanation.py`), 가드레일 구조
  (pydantic `extra="forbid"`, 금지어 필터, 폴백), 위험 패턴 파생(`services/patterns.py` — 4종 고정 어휘).

### 아키텍처 방향 (가설 — T1 리서치·judge-reviewer 채점 후 확정)
- 쿼리 원천이 **사용자 자연어가 아니라 규칙 엔진의 판정 JSON(구조화된 위험 사유)**이라는 특성상:
  - 위험 유형별 **분기 검색(Branch/Router)** + **메타데이터 필터**가 자연스럽고 구현 비용이 낮다.
  - 판정 사유→검색 질의 변환은 **결정적 템플릿**(위험 유형별 질의문)이 1차, HyDE(가상 판례 요지 생성)는
    법률 도메인 임베딩 갭을 메우는 후보 — 단 LLM 호출 추가 비용·환각 경로 증가와 저울질.
  - Self/Adaptive/Agentic RAG의 반복 판단 루프는 "쿼리가 이미 구조화되어 있다"는 우리 특성에서 이득이 작다(가설).
- 검색 품질: 순수 벡터 유사도만 믿지 않는다 — **하이브리드(BM25 키워드 + 벡터) + 위험 유형 메타데이터 필터 +
  판결요지 중심 청킹 + 유사도 하한 게이트**(미달 시 비노출) 조합.

### 리스크·우회책
- 법제처 API는 OC(등록 이메일 ID) 필요 → 키 없이 호출 막히면: 수집 스크립트는 완성만 해두고
  시드 판례(웹 검증)로 E2E 검증. **대기 금지 원칙.**
- Upstage 임베딩 실호출 실패(크레딧·키) → 결정적 오프라인 임베딩 백엔드(해시 기반)로 파이프라인 검증,
  실키 주입 시 재임베딩 스크립트 1회 실행이면 됨.
- Python 3.14로 chromadb/faiss 설치 실패 가능 → 경량 자체 벡터 저장소(수치 연산 + 파일 영속화)로 폴백,
  인터페이스 뒤에 숨겨 추후 교체 가능하게.
