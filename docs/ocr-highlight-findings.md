## 1. 왜 OCR을 추가하려 했나

**사용자가 손에 든 등기부 종이와 앱 화면을 대조할 수 있게 하려는 것이다.**
은행원이 색연필로 동그라미 치듯, 확인해야 할 항목의 위치를 사진 위에 짚어 준다.

지금 리포트는 "선순위채권 3,600만원"이라고 **말은 하지만**, 그게 종이의 어디에 적혀
있는지는 알려주지 못한다. 부동산 지식이 없는 사용자는 그 문장을 검증할 방법이 없다.

기술적 사정은 이렇다.

| | 좌표 | 구조화된 필드 |
|---|---|---|
| Information Extract (지금 쓰는 것) | ❌ 안 준다 | ✅ 준다 |
| Document OCR (이번에 추가) | ✅ 단어 단위로 준다 | ❌ 안 준다 |

그래서 **두 개를 함께 부르고 결과를 맞춰야** 한다.
판정은 지금처럼 IE + 규칙 엔진이 하고, OCR은 **좌표만** 만든다.

## 2. 검증으로 확인된 것 (수치 포함)

### 2.1 Document OCR API 사양 (실호출 검증 완료)
```
POST https://api.upstage.ai/v1/document-digitization
multipart: model=ocr, document=@<파일>
Auth: backend/.env 의 UPSTAGE_API_KEY
응답: pages[].words[].{text, confidence, boundingBox.vertices}
vertices = 전송 이미지 기준 픽셀 4점 (정규화 아님)
응답 시간: 장당 1.6~3.1초 (3~5장 기준 총 7초대)
```

### 2.2 금액이 쪼개지지 않는다
`금36,000,000원` 이 **word 1개**로 온다. 쪼개졌다면 여러 word의 bbox를 합쳐야 했는데
그럴 필요가 없다. 5장 전체에서 콤마 금액은 모두 "한 덩어리" 유형이었다.

### 2.3 표 컬럼이 x좌표로 깨끗하게 갈린다 — **이번 검증의 핵심 발견**
```
3.png 헤더: 순위번호@42-101 | 등기목적@145-226 | 접수@302-346 | 등기원인@405-487 | 권리자@616-752
칸 안 word 간격  7~16px
칸 사이 간격    44~177px
글자 높이 중앙값 ~16px
```
두 분포가 겹치지 않아 **간격 임계값(1.8 × 글자높이 ≈ 28.8px)으로 컬럼을 나눌 수 있다.**
해상도가 달라져도 글자 높이에 비례하므로 절대 픽셀 하드코딩을 피할 수 있다.

### 2.4 좌표 정확도 — 육안 확인 완료
`backend/out/marked_3.png`·`marked_4.png`에서 박스가 글자를 정확히 감싼다.
이름 word 폭 43~44px (수정 전 버그에서는 181px로 옆 칸까지 번졌다).

### 2.5 말소를 텍스트만으로 가려낼 수 있다 — **가장 중요한 확인**
OCR 응답에는 **선·스타일 정보가 전혀 없다**(응답 키 확인 완료: `strikethrough`/`style`/
`decoration` 등 없음). 즉 **취소선으로 말소를 판정할 수 없다.**

말소는 `"1번근저당권설정등기말소"` 라는 **별도 행**으로만 드러난다. 이 행의 `N번`을
파싱하는 것이 유일한 경로다.

`marked_4.png`를 눈으로 대조한 결과:

| 항목 | 원본에 빨간 취소선 | 우리 텍스트 판정 |
|---|---|---|
| 을구 순위1 근저당 (금36,000,000원) | ✅ 있음 | **말소** ✅ 일치 |
| 을구 순위2 근저당 (금75,600,000원) | ✅ 있음 | **말소** ✅ 일치 |
| 을구 순위3 `1번근저당권설정등기말소` | ❌ 없음 | **말소근거행**(유효한 기록) ✅ 일치 |
| 을구 순위4 `2번근저당권설정등기말소` | ❌ 없음 | **말소근거행** ✅ 일치 |

**선 정보 없이 텍스트만으로 말소를 정확히 가려낼 수 있음이 시각적으로 증명됐다.**

### 2.6 항목이 페이지를 걸쳐 이어진다
을구 순위1의 금액은 3.png, 근저당권자(하나은행)는 4.png에 있다
(`위치 3:L30-33,4:L2-4`). 항목을 페이지 경계에서 닫으면 안 된다.

### 2.7 페이지 꼬리말에 쪽수 표식과 발급확인번호가 있다 — 라운드 4에서 발견
```
1.png 마지막 줄: … 발급확인번호 ABCD-EFGH-0000 발행일 2026/06/30   /   1/5
5.png 마지막 줄: … 발급확인번호 ABCD-EFGH-0000 발행일 2026/06/30   /   5/5
```
- `N/M` → **쪽 누락·순서 어긋남**을 판별할 수 있다
- 발급확인번호가 전 페이지 동일 → **다른 등기부 섞임**을 판별할 수 있다
- (3·4.png는 캡처가 잘려 꼬리말이 없다 — 실제 촬영본에는 있을 것으로 본다)

### 2.8 개인/법인이 등록번호 형태로 구분된다
- 개인: `○○○○○○-○******` (뒤 7자리 **마스킹**)
- 법인: `110111-0015671` (뒤 7자리 **숫자**)

### 2.9 confidence는 이 샘플에서 품질 게이트로 쓸 수 없다
깨끗한 PDF 캡처라 값이 높게 나온다(대부분 0.95 이상). 촬영본 기준선이 없다.

## 3. 설계에 반영한 사실과 그 근거

| 설계 결정 | 근거 |
|---|---|
| **이미지를 병합하지 않고 장별 개별 호출** | 병합하면 좌표계가 합본 기준이 되어 원본 사진과 1:1로 안 맞는다 |
| **IE와 OCR을 병렬 호출** | IE 30초대 + OCR 7초대. 순차면 대기가 그대로 더해진다 |
| **OCR 실패가 분석을 실패시키지 않음** | 좌표는 있으면 좋은 것이지 판정의 입력이 아니다 |
| **순위번호는 헤더 word의 x밴드 안에서만 인정** | "줄 맨 앞 숫자" 규칙은 등기목적 칸에 접힌 분수의 분모(`2분의 / 1`)를 순위번호로 오인한다(3.png L19 실측) |
| **말소 패턴은 등기목적 컬럼 word만 이어붙여 찾음** | 줄 단위로 이으면 `…설정등` + (날짜) + `기말소`로 끊긴다(4.png L12-13 실측) |
| **이름은 등록번호 word 바로 앞 word에서** | 문자 단위 정규식은 `매매`+`소유자D`을 한 덩어리로 삼켜 bbox가 181px로 번진다 |
| **좌표는 0~1 정규화, 원본 크기는 Pillow로 직접** | 기기·회전·줌마다 표시 크기가 다르다. OCR 응답의 페이지 크기를 믿으면 1px 어긋남이 전체를 민다 |
| **말소된 항목에는 절대 좌표를 안 준다** | 사용자가 "이미 없어진 빚"을 현재 위험으로 오해하는 것이 이 기능 최악의 오류 |
| **부분 매칭 금지 (앵커 전부 일치)** | 같은 금액이 여러 곳에 나온다. 금액만으로 칠하면 말소분까지 칠한다 |
| **매칭 기준은 IE 결과** (OCR이 본 것 전부가 아니라) | 이 등기부는 소유권이 3번 넘어갔다. 옛 소유자를 칠하면 사용자가 그 사람을 임대인으로 오인한다 |
| **표시가 없어도 "무엇을 찾아봤는지"는 말한다** | 침묵은 "AI가 안 봤다"로 읽혀 리포트 신뢰까지 깎는다(리뷰 3인 공통 지적) |
| **빨간 타원에 흰 halo** | 우리 빨강과 등기부 인쇄 빨강(취소선)의 대비가 1.24:1로 사실상 같은 색인데 의미는 정반대다 |

## 4. 이번 검증의 한계 — **축소해서 읽지 말 것**

### 4.1 샘플이 깨끗한 PDF 캡처다. **폰 촬영본은 검증하지 않았다.**
`backend/test_samples/1~5.png`는 전부 인터넷등기소에서 받은 PDF를 캡처한 것이다.
- 그림자·기울기·구겨짐·손가락·조명 얼룩이 **하나도 없다**
- 초점이 완벽하고 글자가 평행하다
- 실제 사용자는 **책상 위 종이를 폰으로 찍는다.** 그때
  - 줄 묶기(y중심 클러스터링)가 기울기에 얼마나 견디는지 **모른다**
  - 컬럼 x밴드가 원근 왜곡에 얼마나 견디는지 **모른다**
  - confidence 임계값을 어디에 둬야 하는지 **모른다**
- **"깨끗한 이미지에서는 된다"까지만 증명된 상태다.**

### 4.2 유효 근저당이 0건이라 **근저당 하이라이트는 실행조차 되지 않았다.**
이 등기부는 을구 1·2번이 모두 말소됐다. 즉 라운드 1에서 만든 금액 매칭 경로
(`_match_money_entry`)는 **실제 데이터에서 한 번도 성공한 적이 없다.**
합성 테스트(손으로 만든 표 좌표)로만 검증했다.
→ 유효 근저당이 있는 등기부로 **반드시 다시 재야 한다.**

### 4.3 IE 응답을 실제로 받아보지 않았다.
이번 야간 작업에서 `/api/analyze`를 **실호출하지 않았다**(크레딧·시간). 그래서
- IE의 `current_owners`가 실제로 몇 명을 돌려주는지 **모른다** (2명일 수도 5명일 수도)
- IE의 `mortgages[].rank_number`가 실제로 채워지는지 **모른다** — 비어 있으면
  금액 매칭이 전부 실패한다(설계상 순위번호 없으면 좌표를 주지 않는다)
- 화면에 형광펜이 **몇 개** 보일지는 아침에 실제로 돌려봐야 안다

### 4.4 페이지 표식(`N/M`) 방어는 실데이터로 검증되지 않았다.
3·4.png에는 꼬리말이 없어 `check_document()`가 "판별 불가"로 지나간다.
표식이 있는 사진(1.png·5.png)만 올렸을 때의 동작은 합성 테스트로만 확인했다.

### 4.5 실기기에서 눈으로 본 적이 없다.
`flutter build apk --debug`가 성공했을 뿐, **폰에 설치해 화면을 본 적이 없다.**
좌표가 실제로 글자 위에 얹히는지는 아침에 확인해야 한다.

## 5. 라운드 3(페르소나·리뷰어)에서 나온 지적과 처리

서브에이전트 3인을 실제 호출했다(persona-jisoo · persona-newlywed · design-reviewer).

### 5.1 세 명이 동시에 지목한 것
> **"표시가 없는 것"과 "AI가 안 본 것"이 화면에서 구분되지 않는다.**

서연: *"지금 이 샘플에서는 신뢰도를 **내립니다**. 근데 '말소된 근저당 2건은 확인 후
제외했어요' 한 줄이 들어가는 순간 같은 화면이 **가장 강력한 신뢰 장치**로 뒤집혀요."*

→ **고침.** `Report.checkedNotes`로 "무엇을 찾아봤고 무엇을 왜 표시하지 않았는지"를
내려보내고 뷰어 하단에 붙였다. 말소돼서 안 칠한 것과 **유효한데 위치를 못 찾은 것**을
구분해 적는다(후자는 리포트 근거 카드로 안내).

### 5.2 디자인 리뷰어 실측 대비
| 조합 | 대비 | 조치 |
|---|---|---|
| 우리 빨강 vs 등기부 인쇄 빨강 | **1.24:1** | 흰 halo 추가 (형태로 구분) |
| 흰 뱃지 글자 on #B98900 | 3.16:1 (AA 미달) | `AppColors.caution`로 교체 → **4.92:1** |
| 형광 채움 vs 검은 인쇄 글자 | 17.9:1 | 유지 (반투명 선택이 옳았다) |

### 5.3 고친 것 (14건)
`checkedNotes` 신설 / 빨간 타원 흰 halo / **탭 최근접 선택**(첫 매칭이면 겹칠 때
④를 눌러도 ①이 열린다 — 공동명의에서 필연) / 뱃지 대비 AA 통과 / 줌 시 뱃지 역스케일 /
뱃지 위치·클램프·2패스 렌더 / 디버그 토글 `kDebugMode` / 헤더 개수 표기 /
칩 영역 높이 상한 / 하단 SafeArea / 크기 조회 실패 시 무한 스피너 → 안내 /
근저당 문구를 실행 가능한 행동으로 / 공동명의 문구를 법적 단정 → 권고형 / 시트 출처 한 줄.

### 5.4 기록만 하고 안 고친 것
| 지적 | 왜 안 고쳤나 |
|---|---|
| 칩 탭 → 해당 위치로 자동 확대·이동 | 값이 크다는 데 동의. 다만 `TransformationController` 애니메이션은 경계·최소배율과 얽혀 잘못 만들면 화면이 튄다. 밤에 검증 없이 넣기엔 위험. **다음 세션 1순위** |
| 시트에 해당 부분 확대 썸네일 | 위와 같은 이유 + 크롭 렌더 비용 검증 필요 |
| 공동명의 칩을 1개로 묶기 | 묶으면 뱃지 번호와 칩이 1:1이 아니게 되어 "②는 어디 갔지?"가 생긴다. 최근접 탭으로 오탭은 이미 해소 |
| 하이라이트 크롭 공유 | 공유 기능 자체가 아직 스텁 |
| 소유자 구성(공동명의 N명)을 근거 카드로 승격 | **판정 계층 변경** — 이번 작업의 금지 사항(규칙 엔진 변경 금지) |
| `_HighlightChip`을 `AppPill`로 흡수 | 공용 컴포넌트 변경은 다른 화면에 영향 |
| 뷰어 헤더에 등급 뱃지 | 등급 색과 마킹 색이 한 화면에 오면 다시 헷갈릴 수 있다 |

## 5-A. OCR이 IE의 말소 누락을 잡아낸 첫 실사례 (2026-07-27)

**이 기능을 채택할 근거 중 하나다.** 지금까지 OCR은 "판정에 개입하지 않는 표시 계층"이었는데,
이번에 **판정 입력(IE)의 오류를 드러내는 교차 검증 장치**로 처음 작동했다.

### 무엇이 어긋났나
같은 리포트의 두 화면이 다른 숫자를 말했다.

| 화면 | 표시 | 근거 경로 |
|---|---|---|
| 리포트 근거 카드 | 유효 채권최고액 등 합계 **27억 8,000만원 · 근저당 4건** (말소 제외) | IE → 규칙 엔진 |
| 뷰어 하이라이트 | 근저당 **3건 · 14억원** | OCR → 좌표 매칭 |

### 저장된 OCR 응답으로 확인한 을구 전체 (`out/ocr_page_1~5.json`, 크레딧 0원)

| 순위 | 등기목적 | 채권최고액 | OCR 판정 | 근거 |
|---|---|---|---|---|
| 1 | 근저당권설정 | **13억 8,000만원** | **말소** | page_4 L6-7 `1번근저당권설정등기말소` |
| 2 | 1번근저당권설정등기말소 | — | 말소 기록 행 | (유효한 기록) |
| 3 | 근저당권설정 | 5억원 | 유효 | |
| 4 | 근저당권설정 | 5억원 | 유효 | |
| 5 | 근저당권설정 | 4억원 | 유효 | |

- 금액이 붙은 근저당 행 **전체 4건 = 27억 8,000만원** ← **카드 수치와 정확히 일치**
- 그중 OCR이 유효로 본 **3건 = 14억원** ← **뷰어 하이라이트와 정확히 일치**
- 차액 **13억 8,000만원 = 말소된 을구 순위1의 채권최고액과 1원 단위까지 일치**

### 가압류는 섞이지 않았다
갑구의 가압류 청구금액(순위2 2억 5,000만원 · 순위7 1억 2,000만원 · 순위8 4억 5,000만원,
합 8억 2,000만원)은 합계에 들어가지 않는다. 계산으로도(14억+2.5억=16.5억 ≠ 27.8억,
14억+8.2억=22.2억 ≠ 27.8억) 코드로도(`_judge_senior_debt`는 `mortgages`·`jeonse_rights`만 더하고,
가압류는 `_judge_ownership`에서 별도로 센다) 확인된다.

### 결론 — 표시 버그가 아니다
카드의 건수와 합계는 **같은 `is_active` 필터를 통과한 같은 목록**에서 나온다
(`rule_engine.py` `active_mortgages` → 건수, 그 amounts 합 → 금액). 둘이 어긋날 구조가 아니다.
따라서 **IE 경로가 을구 순위1을 유효로 본 것**이 확정이다. 등기부 원본에는 순위1에 빨간
취소선이 그어져 있고, 그것을 말소한 별도 행(순위2)도 사진에 있다.

한 가지는 아직 못 가른다: IE가 `is_canceled: false`로 **틀리게** 답했는지, 아니면 값을
비워서(`null`) 보수적 편향 규칙("말소 여부를 모르면 유효로 간주" — `internal.py`)이 유효로
셌는지다. 둘 다 결과는 같지만 원인이 다르다. **그래서 IE 원응답도 `out/ie_<타임스탬프>.json`에
남기게 했다**(`extraction.py`의 `SAVE_IE_RAW`, `SAVE_OCR_RAW`와 같은 방식·같은 스위치).
다음 실행부터 이 질문에 크레딧 없이 답할 수 있다.

### 왜 이것이 채택 근거인가
- OCR은 **선·스타일 정보 없이 텍스트만으로** 말소를 가려냈고(§2.5), 그 판정이 IE보다 정확했다.
- 판정 계층은 그대로 두면서(규칙 엔진 무변경) **두 모델을 교차 확인해 불일치를 드러내는**
  구조를 이미 갖췄다는 뜻이다.
- 보수적 편향 관점에서도 방향이 맞다 — 어긋날 때 카드는 **더 큰 빚**(27.8억)을 말한다.
  즉 이 불일치가 위험을 숨기는 쪽으로 작동하지는 않았다.

⚠ **주의**: 이 사례는 "OCR이 항상 옳다"는 뜻이 아니다. 반대 방향(OCR이 말소로 오판해
유효한 빚을 안 칠하는 것)이 더 위험하고, 실제로 각주 오탐(§5.7)이 그 방향이었다.
지금 구조는 **하이라이트만 OCR을 따르고 판정은 IE·규칙 엔진을 따른다** — 이 경계는 유지한다.

## 6. 라운드 4(자기 비판)에서 찾아 막은 것

**"말소된 항목에 형광펜이 칠해지는 경로"를 스스로 공격해 3개 찾았다.**

| 경로 | 어떻게 생기나 | 대응 |
|---|---|---|
| ① 말소 근거 행이 **안 올린 페이지**에 있음 | 을구 순위1은 3.png, 그것을 말소한 행은 4.png. 3.png만 올리면 취소선 그어진 행에 빨간 타원을 친다 | 페이지 표식(`N/M`)으로 쪽 누락을 감지하면 **금액 표시 전체 보류** |
| ② 사진 순서가 뒤바뀌어 구역이 '미상'이 됨 | 4.png를 먼저 올리면 `【을 구】` 머리가 없어 구역을 모른다 → 말소 매칭이 (구역, 순위)로 갈려 실패 | '미상'을 어느 권리 구역과도 같게 봄 + 표식 순서가 어긋나면 **전부 표시 안 함** |
| ③ 말소 근거 행은 있는데 **대상 항목을 못 찾음** | "9번…말소"인데 9번이 사진에 없으면 "무언가 말소됐는데 무엇인지 모르는" 상태 | `cancel_bound`로 추적 → 미결이 하나라도 있으면 **금액 표시 전체 보류** |

그 밖에 찾은 것:
- **다른 등기부 섞임**: 발급확인번호(1순위)·상단 주소 줄(2순위)로 감지 → 전부 표시 안 함
- **EXIF 회전**: Pillow(저장 크기)와 Flutter(회전 적용)가 달라 좌표가 통째로 어긋날 수
  있다. 앱에서 `keepExif: false`를 명시하고, 서버는 방향 태그가 남아 있으면 경고 로그
- **JPEG 임시 파일 이름 충돌**: 같은 밀리초에 두 장이 변환되면 덮어써져 두 페이지가
  같은 사진을 가리켰다 → 장별 태그(`_p0`, `_p1`)

## 7. 미해결 사항

1. **꼬리말이 잘린 사진에서는 쪽 누락을 알 수 없다.**
   `check_document()`가 "판별 불가"로 두고 진행한다(확인 못 한다고 기능을 끄면 정상
   사진에서도 아무것도 안 보인다). 이 경우 경로 ①이 **여전히 열려 있다.**
   → 완화 아이디어: 사용자에게 "마지막 쪽까지 올렸는지" 한 번 확인받기(미구현)

2. **유효 근저당 매칭이 실데이터로 검증되지 않았다** (4.2 참조)

3. **폰 촬영본 미검증** (4.1 참조) — 이 기능의 채택 여부를 가르는 가장 큰 미지수

4. **IE의 `rank_number`가 실제로 채워지는지 모른다.** 비어 있으면 금액 매칭이 전부
   실패한다. 스키마상 있는 필드지만 IE가 항상 채운다는 보장은 없다.

5. **같은 이름이 갑구에 여러 번 나올 때** 가장 아래(최신) 등기를 쓴다. 이 규칙이
   모든 등기부에서 옳은지는 확인되지 않았다(이 샘플에서는 각 이름이 1번씩만 등장).

6. **칩 탭 → 위치 이동**이 없어, 칩으로 무엇이 표시됐는지는 알아도 **종이의 어느 줄인지**
   찾으려면 사용자가 직접 확대해야 한다(5.4 참조).

**시안에 없지만 이번에 바뀐 것 (되돌리기 쉬움):**
- **앱바 제목이 매물 별칭 → 화면 이름**(`내가 올린 사진에서 보기`)으로 바뀌었다.
  별칭을 두자는 앞선 결정(5.x 서연 리뷰: "캡처해 배우자에게 보낼 때 맥락이 없으면 못 보낸다")과
  시안이 충돌한다. 시안을 따랐고, **되돌리려면 `_ViewerAppBar`의 title 한 줄**이다.
- **접었다 펴는 "이 등기부에서 찾아본 것" 목록이 사라졌다.** 시안의 문장 감축 방향이라,
  목록 끝 **회색 한 줄**(= 리포트엔 있는데 사진에 표시하지 못한 것)만 남겼다.
  "침묵이 신뢰를 깎는다"(5.1)의 핵심은 그 한 줄이 담당한다 — 근저당 4건 중 1건이 말소라
  화면 표시가 3개일 때, 개수가 안 맞는 이유를 그 줄이 댄다.
  **말소 전용이 아니라 범용 슬롯**이다(위치 못 찾음·표시 보류도 같은 자리에 나온다).
  전체 목록을 되살리려면 `_CheckedNotes` 위젯을 복원하면 된다.

### 9.2 좌표계 — 시안과 무엇이 다른가 (가장 중요)

시안은 `종이 네 꼭짓점 검출 → 원근 보정(deskew) → 같은 폭 리샘플` 뒤의 좌표계를 전제한다.
**그 단계는 이 앱에 존재하지 않는다.** 실제 파이프라인은 이렇다:

1. 앱이 사진을 **quality 90으로 재인코딩**하고 EXIF 회전을 픽셀에 반영해(EXIF는 제거) 서버로 보낸다
   (`registry_upload_service.convertToJpeg` — `autoCorrectionAngle: true, keepExif: false`)
2. 백엔드는 **그 JPEG 픽셀 기준**의 0~1 정규화 좌표를 돌려준다 (`highlight._normalize`)
3. 앱은 **그 변환 JPEG를 로컬에 보관**해 두고(`RegistryPhotoStore`) 그대로 화면에 그린다
4. 화면 표시 크기는 쪽 종횡비로 미리 계산하므로 `BoxFit.fill` = `contain`이고,
   `정규화값 × 표시 크기`가 곧 그릴 자리다 (`highlightRect`)

→ **좌표 변환을 새로 만들지 않았다.** 갤러리 원본을 다시 읽지도 않는다(해상도·회전이 달라
전부 어긋난다). 시안이 말한 "보정 후 좌표계"는 이 파이프라인에서 **2번의 좌표가 이미 그 역할**을 한다.

부수 효과: 쪽마다 촬영 거리가 다르면 시안이 걱정한 대로 종이 크기가 제각각으로 보인다.
같은 폭으로 맞추고 높이만 종횡비로 다르게 두는 것으로 대응했고(세로 스크롤은 성립한다),
**원근 왜곡(기울어진 촬영) 자체는 보정하지 않는다** — 그건 정규화 단계가 생겨야 풀린다.

### 9.3 `oneLiner`는 백엔드에 없었다

`backend/app/schemas/contract.py`의 `Highlight`가 주는 것은
`id / page / kind / badge / box / title / body / caution / source` 뿐이다.
카드 2행의 "한 줄 요약"에 쓸 문구가 없어서 **지어내지 않았다.**

`body` 첫 문장에서 파생시킨다. 문구의 원본은 백엔드다.

### 9.5 형광펜 박스는 종류마다 모양이 다르다 (`highlight.py` 코드 확인, 2026-07-27)

**이름은 단어 단위, 금액 항목은 앵커 합집합(줄 전체 폭). 순위번호가 '선순위'의 근거라
박스에 포함돼야 하며, 금액만 칠하면 몇 번째 순위인지 사용자가 다시 찾아야 한다.**

근거:
- **이름** — `ocr_layout.extract_names()`가 등록번호 word 바로 앞 **word 하나**의 bbox를
  그대로 쓴다(`NameHit.box = src.box`). 문자 단위 정규식으로 잡으면 `매매`+`소유자D`이 한
  덩어리가 되어 bbox가 옆 칸까지 번진다(실측 181px → word 단위 43px). `_match_owner`가
  이 box를 그대로 넘기고 `_normalize(pad_ratio=0.08)`만 붙는다.
- **금액** — `_match_money_entry`가 `boxes = [item.rank_box] + [w.box for w in money_words]`의
  min/max **합집합 사각형**을 만든다. 순위번호와 **같은 줄에 한정**되므로 세로는 한 줄 높이,
  가로는 최좌측(순위번호) ~ 최우측(금액)이라 사실상 줄 전체 폭이 된다.
- 정확히는 **순위번호 + 금액 두 앵커의 합집합**이다. **등기목적(`근저당권설정`/`전세권설정`)은
  검증 앵커일 뿐 박스에 기여하지 않는다**(`keyword not in item.purpose`는 통과/실패 판정에만
  쓰인다). 다만 표에서 두 앵커 사이에 있어 결과 사각형 안에 들어온다.
- `_normalize`의 여백은 **박스 자기 크기 대비 비율**이다(`pad_x = (x1-x0) * pad_ratio`).
  같은 5%라도 폭 900px 금액 박스는 좌우 45px씩, 8%인 43px 이름 word는 3.4px씩 붙는다 —
  두 표시의 "두께 감각"이 다른 데는 이 비례 여백도 한몫한다.

**[보류] 표시 종류가 늘면 줄무늬가 될 수 있다.**
압류·가압류는 갑구 행이라 같은 방식이면 **역시 줄 전체 폭**이 된다. 가로 띠가 여러 개 쌓이면
가독성이 떨어질 수 있다. 지금은 표시 4개라 문제없고, **선택 항목만 진하게** 하는 대비와
카드 캐러셀이 완충한다. 실제로 종류를 추가하는 시점에 화면을 보고 재검토한다.

### 9.7 2단계에서 코드 쪽으로 드러난 것

- **`late final AnimationController` 는 dispose에서 터진다.** `late final _draw = AnimationController(...)`로
  두면 처음 **읽을 때** 만들어지는데, 로딩 중에 사용자가 뒤로 나가면 그 '처음 읽기'가
  `dispose()`가 되어 이미 떨어져 나간 위젯에서 Ticker를 만들려다 죽는다.
  → initState에서 만든다. (레이아웃 측정 테스트를 쓰다가 잡혔다)
- **`report_screen.dart`가 build() 안에서 `getReport()`를 부르고 있었다.** StatelessWidget이라
  증상이 없었지만 진입 카드에 이미지가 들어오면 재빌드가 늘어 뷰어에서 겪은 문제
  (로딩 분기로 되돌아감 · 매 프레임 요청)가 그대로 재현될 자리였다. → StatefulWidget +
  initState의 `late final Future`로 고쳤다.

### 9.9 진입 카드 부제 → **등기부 열람일** (표시 전용, 백엔드 필드 추가)

등기부는 **열람 시점의 스냅샷**이다. 그 뒤에 잡힌 근저당은 이 서류에 없고, 계약 직전

나는데 화면 어디에도 그 사실이 없었다.

확인 결과 그 값은 앱까지 오지 않고 있었다:
- IE 스키마(`registry_schema.py`) — 항목별 `receipt_date`만 있고 **문서 열람일시는 없다**
- OCR 레이아웃(`ocr_layout.py`) — 꼬리말에서 쪽수 표식·발급확인번호는 읽지만 **열람일시는 안 읽었다**

- 계약(`contract.py`) — 해당 필드 없음

테스트로도 못 박았다(`test_열람일시는_판정에_쓰이지_않는다` — 열람일시가 있든 없든 좌표·안내가 동일).

분석일을 넣으면 오히려 "오늘 서류"라고 믿게 만들어 아무것도 안 쓰느니만 못하다.

### 9.10 [알려진 한계 — 미해결] 마스코트가 흰 배경에서 잘 안 보인다
