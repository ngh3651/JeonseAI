## 1. RAG 아키텍처 재검증

### 1.1 어젯밤 비교한 5안 · judge-reviewer 채점표 · 탈락 사유 (원본 기록)

비교 5안: **① 분기(Branch) RAG + 하이브리드(채택) ② Simple RAG ③ HyDE ④ Self-RAG/Adaptive ⑤ Agentic RAG**

judge-reviewer 채점 (축별 10점 척도):

| 안 | 창의성 | 혁신성 | 추진성 | 성장성 | 탈락 사유 (요약) |
|---|---|---|---|---|---|
| **채택: 분기+하이브리드** | **7** | **8** | **7** | **7** | — ("유일하게 우리 문제의 특수성에서 출발한 설계") |
| Simple RAG | 4 | 3 | 6 | 4 | 판정 통짜 문자열 1회 검색 — 복합 위험에서 한 유형이 상위 독점, "왜 이 판례인가"에 답 불가(설명 가능성 원칙 위배) |
| HyDE | 5 | 4 | 4 | 5 | LLM이 가상 판례 요지를 생성해 검색 — "지어낸 판례 문장으로 검색"이 환각 금지 서사와 정면 충돌(심사 방어 불가), 질의 재현성 상실 |
| Self-RAG/Adaptive | 5 | 5 | 2 | 5 | 재검색 자가 판단 루프 — 쿼리가 이미 구조화돼 이득 불명확, 2인 체제 구현·디버깅 비용 과대 |
| Agentic RAG | 5 | 5 | 1 | 4 | 비결정적 루프 — 영상 시연에서 지연·불확실성 리스크 최악 |

채택안의 대회 배점 환산: 창의성 22/30 · 혁신성 15/20 · 추진성 21/30 · 성장성 15/20 = **73/100**
(감점은 아키텍처가 아니라 당시 문서 미마감·n=7 포화 지표·화면 미통합 — 첫 둘은 야간에 해소).

### 1.2 5안에 없던 기법 재평가 (우리 제약: 쿼리=판정 JSON · 환각 금지 · 보수 편향 · 2인 · 영상 시연)

*(리서치 종합 — 상세 근거·출처는 §1.3)*

| 기법 | 재평가 (2~3줄) | 판정 |
|---|---|---|
| Self-RAG | 생성 중 LLM이 스스로 검색 필요성·인용 적합성을 판단(reflection 토큰). 우리는 검색 필요성이 판정 태그로 이미 결정돼 있고, 인용 적합성은 결정적 게이트가 담당 — LLM 자가 판단으로 바꾸면 가드레일이 확률화된다. | 탈락 유지 |
| Corrective RAG (CRAG) | 검색 결과 품질을 평가기가 채점해 나쁘면 보정(웹 검색 등 대체 소스). **"나쁘면 노출 안 함"이라는 우리 3중 게이트가 이미 CRAG의 보수적 특수형** — 대체 소스 보정은 "다른 판례라도 보여주기" 방향이라 보수 편향과 반대. 평가기 아이디어만 리랭커(2c)로 흡수 가능. | 탈락 (게이트가 상위 호환) |
| Adaptive RAG | 질의 난이도별 검색 전략 라우팅. 우리 라우팅은 위험 태그로 이미 결정적으로 존재(분기 검색이 곧 Adaptive의 결정론 버전). LLM 라우터를 끼울 자리가 없다. | 탈락 (이미 결정론으로 보유) |
| Graph RAG | 판례 인용 그래프·법령 관계 그래프 기반 확장 검색. 법률 도메인 적합성은 높으나(참조판례 필드 보유) 그래프 구축·유지 비용이 2인 체제에 크고, 현 코퍼스(26건)에선 무의미. **대량 수집 후 '참조판례 1-hop 확장'만 저비용 차용 후보**. | 부분 차용 후보 (지금은 보류) |
| Agentic RAG | 챗봇 한정이면 리스크가 줄지만 리포트 경로에는 여전히 부적합. → 2e에서 별도 평가. | 리포트 경로 탈락 유지 |
| Speculative RAG | 소형 모델이 여러 초안 생성 → 대형 모델이 검증·선택. 지연 단축용 기법인데 우리 병목은 생성 지연이 아니라 검색 신뢰. 모델 2종 운용 비용만 늘어난다. | 탈락 |
| Simple RAG + memory | 대화 이력 메모리로 검색 보강. 리포트는 단발 판정이라 메모리가 무의미, 챗봇(2e)에서만 의미. | 리포트 경로 탈락 |

### 1.3 법률 도메인 최신 기법·연구·업계 사례 (자유 조사)

웹 조사 요약 (출처는 각 항목):

- **법률 RAG 환각 실증 (Stanford RegLab/HAI, J. Empirical Legal Studies 2025)**: 상용 법률 AI
  사전등록 실측 — Lexis+ AI 17%, Westlaw AI 33% 환각률. 교훈: **RAG는 환각을 줄일 뿐 없애지
  못하며, "진짜 판례를 잘못 요약·오적용하는 2차 환각"이 남는다** → 검색 게이트 외에
  "생성문 대 원문" 검증 계층이 필요. (law.stanford.edu Legal_RAG_Hallucinations)
- **법률 IR 정설 확인**: BM25는 판례 검색의 강한 베이스라인("Yes, BM25 is a Strong Baseline
  for Legal Case Retrieval", COLIEE 2021 2위)이고, COLIEE 상위팀은 일관되게 **BM25 1차 +
  신경망 리랭킹 2차의 다단 구조** — 우리 BM25+벡터 RRF 채택은 학계 정설과 일치.
- **업계 공개 레시피**: Harvey — 문장 단위 인용 + 메타데이터 필터 + 리랭킹(클레임 환각 ~0.2%
  주장) / Casetext CoCounsel — "신뢰 DB에서만 답하거나 **답하지 않는다**" / 로앤컴퍼니
  슈퍼로이어 — Advanced RAG + **답변 전 근거 재확인 '팩트체커' 계층** / Lexis — 인용 실존
  검증(Shepard's 대조)에도 17% 환각(실존 검증만으로는 부족하다는 반면교사). 국내 인텔리콘은
  법률-판례 그래프 검색(COLIEE 2016·17 우승) — 대규모 판례망 전제.
- **최신 검증 연구**: HalluGraph(2025) — 유사도 게이트는 당사자·금액·조항의 **엔티티 치환을
  통과시킨다** → 엔티티 단위 대조 필요성 제기. Microsoft Legal GraphRAG — LLM 그래프 추출
  대신 **판례의 기존 인용 관계**를 그래프로 쓰는 실용주의(수십만 건 규모 전제).
- **Anthropic Contextual Retrieval**: 청크에 맥락 문장 부착 시 검색 실패율 최대 67% 감소
  보고 — 2b 후보의 근거.

### 1.4 결론 — 교체 여부

**교체 근거 없음 — 현행(분기+하이브리드+3중 게이트) 유지.** 근거는 구조적이다:

1. Self/Adaptive/CRAG/Agentic이 해결하는 문제는 대부분 **"사용자 자연어 질의의 불확실성"**
   (검색 필요 판단·복잡도 라우팅·나쁜 검색의 동적 보정)인데, 우리 쿼리는 판정 JSON에서
   결정적으로 나와 그 불확실성이 애초에 없다 — 이득 축이 존재하지 않는다.
2. CRAG의 대체 소스 보정·Agentic의 자율 루프는 환각 금지·영상 시연 결정성과 정면충돌,
   Self-RAG·Speculative RAG는 별도 모델 학습·운용이 필요해 2인·일정과 충돌.
3. 업계 실증이 보여주는 격차(Stanford 17~33% vs Harvey ~0.2%)의 원인은 아키텍처의 화려함이
   아니라 **검증 계층의 엄격함**(문장 단위 인용·답하지 않을 권리·근거 재확인) — 우리 게이트
   방향의 타당성을 확인해 준다.

**대신 조사에서 새 보강 후보가 발굴됐다**: **생성문 검증(4번째 게이트)** — LLM이 만든 판례
설명이 검색된 원문에 실제로 근거하는지 결정적으로 대조(사건번호 화이트리스트는 이미 구현,
추가로 금액·핵심 엔티티·인용 스팬 대조). Stanford가 지적한 "2차 환각"을 막는 유일한 계층이고
Harvey·슈퍼로이어·Lexis가 공통 채택한 방향이다. → §2 추천 순서에 후보 f로 편입.

## 2. AI 핵심 활용 확장 후보 5개 평가

평가 축: 구현 비용(2인 기준 인일) / 심사 효과(AI 활용·정확도·창의성·GPU 어필) / 판정 불변 원칙 / E-3 일정 영향.

### 2a. 인덱싱 시 LLM 자동 태깅·구조화 (+ 정민재 검수 게이트)

- **구현 비용**: 하(1~2일). ingest 경로에 LLM 태깅 단계 추가 + 검수 시트 생성. 프롬프트·검증은
  하네스의 tagging 역할로 이미 초안 존재(허용 태그 화이트리스트 + extra 금지).
- **심사 효과**: 중상 — "수집→AI 구조화→사람 검수→승격" 파이프라인은 AI 활용도·데이터 품질
  서사가 좋다. 현행 키워드 자동 태깅(rule-auditor가 과잉 태깅 소지 지적)의 정밀도 문제를 직접
  해결한다. GPU 어필은 없음(API 호출).
- **판정 불변**: **위반 없음** — 태그는 검색 필터 전용이며, 미검수분은 게이트가 노출 차단.
  LLM 태깅 결과도 "미검수" 상태로 들어가 검수 후 승격되므로 이중 안전.
- **E-3 영향**: 없음(인덱싱 오프라인 단계). 오히려 정민재 검수 부담을 줄여 E-3 데이터 준비를
  가속. **주의**: 허용 태그 밖 출력 폐기 + 키워드 태깅과 불일치 시 검수 큐 우선 표기 설계 필요.

### 2b. 컨텍스추얼 임베딩 (청크에 LLM 생성 맥락 문장 부착)

- **구현 비용**: 하~중(1~2일). 청킹 단계에서 문서 전문을 주고 "이 청크의 맥락 1~2문장" 생성 →
  청크 앞에 부착 후 임베딩. Anthropic Contextual Retrieval 방식 — 검색 실패율 유의미 감소 보고.
- **심사 효과**: 중 — 검색 정확도 개선 + "임베딩 전처리에도 LLM 활용" 서사. 단 효과 입증은
  평가셋이 커진 뒤에야 가능(현 n=7 포화 상태에서는 개선 여지 자체가 안 보임).
- **판정 불변**: 위반 없음(인덱스 품질 계층). 환각 리스크도 낮음 — 맥락 문장은 검색용이며
  사용자에게 노출되지 않음(노출 문구는 여전히 큐레이션·요지 원문).
- **E-3 영향**: 없음(오프라인). 비용: 코퍼스 전체 × LLM 1회 — 대량 수집 후 GPU 임베딩 배치와
  같은 시점에 묶어 실행 권장. **평가셋 확장 후 A/B로 채택 결정**이 순서다.

### 2c. 한국어 크로스인코더 리랭커 GPU 재정렬

*(모델 후보 조사는 §2c-보강 — 리서치 결과)*

- **구현 비용**: 중(2~3일). retrieval.py의 RRF 뒤에 리랭킹 단계(이미 확장 지점으로 설계됨) +
  GPU 서빙(또는 CPU 소형). 평가셋 전/후 비교 필수.
- **심사 효과**: 상 — 검색 정확도 직접 개선 + **GPU 활용 실적**(임베딩 배치 외 추론 워크로드
  추가) + "하이브리드→리랭킹 2단 검색" 기술 서사. 대량 코퍼스에서 효과가 큰 기법이라
  수집 확대와 시너지.
- **판정 불변**: 위반 없음(검색 순위 계층). 유사도 하한 게이트는 리랭커 점수가 아니라
  기존 벡터 점수 기준 유지(게이트 의미 변화 없음) 설계를 전제.
- **E-3 영향**: 낮음 — 검색 내부 단계라 계약·화면 무변경. 단 GPU 없으면 지연이 늘 수 있어
  시연 전 실측 필요.

  KURE-v1도 bge-m3 기반이라 동일 쟁점 — 함께 질의할 것.)

### 2d. A5 심화: 판정 JSON × 판례 원문 비교 추론 (같은 점/다른 점/결과/교훈)

- **구현 비용**: 중(2~3일). explainer 확장 — 스키마(`same_points/different_points/case_outcome/lesson`,
  extra="forbid") + 폴백 + 프롬프트. 하네스 case_compare 역할로 프롬프트·검증 초안 이미 존재.
- **심사 효과**: **최상** — "등기부 판정과 실제 판결문을 AI가 비교 추론"은 우리 플래그십
  차별화(등기부×판례 매칭)를 한 단계 심화하며, 판례 화면의 카드 정보량이 시연 임팩트로 직결.
  같은 점만이 아니라 **다른 점**을 보여주는 것은 과잉 일반화 방지(보수 편향)와도 정합.
- **판정 불변**: 위반 없음 설계 가능 — 입력은 판정 JSON+검색된 판례 원문뿐, 출력 스키마에
  등급·점수 필드 없음, 금지어·case_id 대조 동일 적용. **단 "교훈(lesson)"이 행동 지시 문장이라
  nextAction 결정적 유지 원칙과의 경계 설계 필요**(판정 요약 재진술 금지, "확인하세요" 계열로
  제한하는 검증 추가).
- **E-3 영향**: 중 — 계약(카드 스키마)에 필드가 추가되므로 E-3 계약 갱신과 한 몸으로 가야 함.
  api-contract-cases-v2-proposal.md에 additive로 얹기 좋은 시점.

### 2e. 챗봇 화면 한정 Agentic/Adaptive 검색

- **구현 비용**: 상(4일+). 챗봇은 현재 glossary 조회 전용(범위 밖 거절이 가드레일)인데,
  판례 검색 도구를 주는 순간 자유 질의 → 검색 → 생성 경로가 열려 검증 면적이 크게 늘어난다.
- **심사 효과**: 중 — "Agentic" 키워드 어필은 있으나 심사 체크포인트(신뢰성·윤리)와 긴장 관계.
  영상 시연에서 자유 입력 데모는 리허설 통제도 어렵다.
- **판정 불변**: 구조적으로는 유지 가능(챗봇은 판정을 만들지 않음)이나, **"이 집 계약해도
  돼요?"류 질문에 판례를 곁들인 답이 사실상 조언·판정으로 읽힐 위험** — 현행 챗봇의 "범위 밖
  거절" 가드레일을 완화하는 방향 자체가 리스크.
- **E-3 영향**: 없음(별개 화면)이지만 E-5(챗봇 실연동)와 묶어야 하며, 지금 착수하면 E-3 집중을
  해친다.

### 추천 순서

§1 조사에서 발굴된 **후보 f — 생성문 검증(4번째 게이트)**를 포함해 순위를 매긴다:

> **f. 생성문 검증**: LLM 판례 설명이 검색된 원문에 실제 근거하는지 결정적 대조 — 사건번호
> 화이트리스트(구현 완료)에 더해 금액·기관명 등 엔티티 대조, 원문에 없는 수치 검출 시 폴백.
> 비용 하(1일), 판정 불변 위반 없음, E-3 영향 없음. Stanford "2차 환각" 연구·Harvey·슈퍼로이어
> 팩트체커가 공통 근거 — **심사 체크포인트(신뢰성·윤리)에 정확히 꽂히는 저비용 최고 수익**.

## 3. 국내 LLM 3종 역할별 비교 — Solar Pro vs SKT A.X vs LG EXAONE

### 3.1 현재 클라이언트의 교체 가능성 진단

**결론: 환경변수 교체만으로는 갈아탈 수 없다 (코드 수정 필요).**

- `app/services/explanation.py`: `SOLAR_BASE_URL`·`SOLAR_MODEL`·`REASONING_EFFORT`가 **모듈
  상수**(환경변수 미참조). 키만 `UPSTAGE_API_KEY` 환경변수. 판례 `explainer.py`는 이 상수들을
  import — 단일 지점이긴 하다.
- Solar 전용 파라미터 `reasoning_effort`가 요청 본문에 하드코딩 — 타 프로바이더가 미지 필드를
  거부하면 호출 실패 소지.

**추상화 설계안 (승인 시 구현, ~50줄 + 호출부 2곳)**:

```
app/services/llm_client.py (신규)
  ROLE_CONFIG = {                # 역할별 프로바이더 매핑 — 전부 환경변수 오버라이드 가능
    "explanation": LlmConfig(base_url=env("LLM_EXPLANATION_BASE_URL", SOLAR_기본값), ...),
    "precedent":   ...,          # (향후) "tagging", "case_compare", "chatbot"
  }
  def chat(role, messages, *, response_json=True) -> str
    # 프로바이더별 extra 파라미터(reasoning_effort 등)는 config에 격리
```

- 원칙: **역할마다 다른 모델을 꽂을 수 있는 구조**(미션 전제)가 기본. 기본값은 전부 현행
  Solar — 설정 없으면 동작 변화 0. 폴백·금지어·pydantic 검증은 역할 소유(현행 유지).
- 테스트: `_call_solar` 목 지점이 `llm_client.chat` 목으로 이동 — 기존 테스트 구조 유지 가능.

### 3.2 비교 설계 (4축 × 역할별)

- **대상 역할**: explanation(E-2 설명) · precedent(판례 설명) · tagging(2a 후보) ·
  case_compare(2d 후보). 챗봇은 현행 LLM 미사용이라 제외(도입 결정 시 추가).
- **입력 통제**: 동일 픽스처 판정(mortgage_heavy — 위험 매물, 설명 난도 최고) + 실제 검색
  결과를 3종에 동일 투입. 프롬프트는 **제품 프롬프트 그대로**(하네스가 import).
- **축별 측정**:
  - ① 한국어 품질: 자동화 불가 — 하네스가 출력 샘플을 채점 시트(.md)로 뽑고 **사람이 1~5점**
    (비전문가 이해 용이성·해요체 준수·용어 풀이). 페르소나 2인 서브에이전트 채점을 보조로 활용 가능.
  - ② 스키마 준수율: 제품과 동일한 pydantic(extra="forbid") 검증 통과율 + 금지어 검출률
    (= 실서비스에서의 폴백 발생률 대리 지표).
  - ③ 지연: 반복 호출 중앙값.
  - ④ 비용·안정성: usage 토큰 실측 + HTTP 오류·재시도 횟수, 단가는 시트에 수기(가격표 조사값).
- **판정 기준(사전 등록)**: 역할별 승자 = ②≥현행 Solar 수준(스키마 통과 미달이면 품질 무관
  탈락 — 폴백률이 곧 사용자 경험) → ① 우세 → ③④ 타이브레이크. 교체는 역할 단위로만.

### 3.3 하네스 준비 상태와 실측에 필요한 것

`backend/scripts/compare_llm_backends.py` 작성 완료 — `--list`로 검증(호출 0), 4개 역할 준비.

| 프로바이더 | 필요 환경변수 (backend/.env) | 상태 |
|---|---|---|
| Solar | `UPSTAGE_API_KEY` (기존) | ✅ 준비됨 |
| SKT A.X | `AX_BASE_URL` `AX_MODEL` `AX_API_KEY` | ⛔ 3개 모두 필요 — 경로 조사 §3.4 |
| LG EXAONE | `EXAONE_BASE_URL` `EXAONE_MODEL` `EXAONE_API_KEY` | ⛔ 키는 채팅으로 수령(주의 §3.5), base/model 확정값 §3.4 |

실행(키 주입 후): `python scripts/compare_llm_backends.py --run --repeat 3`
→ `data/llm_bench/run-<시각>.json + .md`(품질 수기 채점 열 포함).

### 3.4 A.X·EXAONE 접근 경로 조사 (웹 조사 확정치)

**SKT A.X — 무료 게스트 API가 존재 (순수 국내 경로)**:
- base_url `https://guest-api.sktax.chat/v1` · 모델 `ax4`(A.X 4.0 72B) · OpenAI SDK 완전 호환.
  게스트 키는 SKT-AI/A.X-4.0 GitHub 저장소 apis/README.md에 **공개**되어 있음(가입 불필요) —
  `.env`의 `AX_API_KEY`에 넣으면 하네스가 활성화된다.
- 유의: rate limit·제공 기간·`response_format` 지원이 미문서화 — 실측 1회차에서 JSON 모드
  동작부터 확인하도록 하네스가 스키마 통과율을 측정한다. A.X 4.0은 **Qwen2.5 기반 재학습**이라
  "국내 모델" 순수성 해석 여지 있음(from-scratch인 A.X 3.1·A.X-K1은 자체 서빙만 가능).
- 라인업 참고: 최신 플래그십 A.X-K1(519B MoE, Apache 2.0, 2025-12 공개)은 공개 API 미확인.

**LG EXAONE — FriendliAI serverless의 K-EXAONE이 사실상 유일한 API 경로**:
- base_url `https://api.friendli.ai/serverless/v1` · 모델 `LGAI-EXAONE/K-EXAONE-236B-A23B`
  (236B MoE, 활성 23B — 현재 serverless에 EXAONE 4.x는 없음). OpenAI 호환 확정,
  `flp_` 키 프리픽스는 FriendliAI 체계 확인 — **수령한 키와 일치**.
- 기능: `response_format`의 json_object·**json_schema 서버 강제** + `reasoning_effort` 지원 —
  3종 중 구조화 출력이 가장 견고한 경로(단 tools와 response_format 동시 사용 불가).
  가격 $0.2/$0.8 per 1M(무료 기간 2026-01-28 종료 — 유료).
- 라이선스: **K-EXAONE은 상업 허용**(EXAONE 4.x는 비상업 한정 — 비상업 대회 참가는 명시 허용).
- **⚠ 규정 쟁점**: FriendliAI는 한국 창업(전병곤)·한국 법인 실재 + **미국 본사** 이중 구조.
  "해외 API 금지"가 ⑴ 모델 국적 기준이면 무풍, ⑵ 서빙 사업자 기준이면 회색지대 —
  **주최 측 유권해석 필요**(리랭커·KURE의 중국계 베이스 쟁점과 함께 한 번에 질의 권장).
- 대안 경로(GPU 직접 서빙): EXAONE-4.0.1-32B를 대회 GPU에 vLLM으로 — BF16 ~64GB(80GB 1장),
  FP8 ~32GB, Q4 ~20GB(24GB 카드 가능). **장점**: 해외 서빙사 쟁점 소멸 + GPU 활용 실적
  (임베딩 배치·리랭커에 이어 세 번째 GPU 워크로드 — "생성까지 자체 서빙" 서사) + 비용 0.
  **단점**: 비상업 라이선스(대회는 허용이나 수익모델 발표와 긴장), 32B는 K-EXAONE 대비 성능
  열위, 서빙 운영 부담(2인 체제), 시연 중 장애 리스크는 API 대비 높음. → **비교 실측은 API로
  먼저, 직접 서빙은 채택 확정 후 GPU 일정에 편입**이 합리적 순서.

**실측 시작에 필요한 것 (backend/.env에 추가)**:
```
AX_API_KEY=<SKT 게스트 키 — github.com/SKT-AI/A.X-4.0 apis/README.md 공개값>
EXAONE_API_KEY=<flp_... — 수령분, §3.5 주의 참조>
```
(base_url·모델명은 하네스에 위 확정값이 기본 내장 — 키만 넣으면 됨.)

  **정식 채점은 사람 몫** — 시트(run-*.md)의 ①열에 기입.
- **잠정 판단**: 사전 등록 기준(②동률→①→③④)상 **현행 Solar 유지가 우세**하고,
  EXAONE은 ⑴ 지연에 둔감한 오프라인 역할(태깅 배치·비교 추론 사전 생성) ⑵ 대회 GPU
  직접 서빙(4.0.1-32B) 시나리오에서 채택 가치. 최종 결정은 ① 수기 채점 후.

### 3.6 키 취급 주의

EXAONE용 키(`flp_` 접두 — FriendliAI 토큰 체계로 추정, §3.4에서 확인)가 **채팅에 평문
노출**됐다. CLAUDE.local.md의 Upstage 키 노출 메모와 동일 상황 — `.env`에만 저장하고,
찜찜하면 발급처에서 재발급 권장. 이 보고서·하네스·저장소 어디에도 키 값은 기록하지 않았다.

## 4. 판례 지속 업데이트 전략 (DB 프레시니스)

> 대원칙(미션): 완전 자동화보다 **업데이트의 자유로움** — 사건번호 기준 idempotent
> upsert/delete로 언제든 추가·교체·삭제 가능. 설계만 하고 구현은 보류.

### 4.1 현재 구조의 출발점 (야간 구축분)

이미 갖춘 것: 판례일련번호 기준 raw 파일 스킵(재수집 멱등) · 전체 재적재(rebuild) 방식이라
적재 자체는 항상 일관 · 임베딩 서명 기록+불일치 차단 · 신규 수집분 verified=False 기본(게이트
차단) · 큐레이션 조인. **빠진 것**: 증분 수집 커서, 사건번호 단위 교체/삭제 의미론, 재임베딩
정책의 명문화, 원커맨드.

### 4.2 설계

**상태 파일** `data/precedents/state.json` (자동 관리):
```json
{
  "last_incremental_at": "2026-07-29",
  "query_profiles": "collect_profiles.json 참조",
  "embedding_history": [ {"signature": "upstage:embedding-passage", "ingested_at": "..."} ]
}
```

**수집 프로필** `data/precedents/collect_profiles.json` (팀 편집 가능):
검색어·법원·기간 조합 목록(예: "임대차 보증금"×대법원, "임차권등기"×전체, "신탁 임대차"×전체).
증분 수집은 프로필별 `lawSearch(sort=ddes, prncYd=<커서>~<오늘>)`로 최신순 조회 →
이미 있는 판례일련번호를 만나면 조기 종료. 커서는 성공 시에만 전진.

**Idempotent 의미론 (사건번호 기준)**:
- **추가/교체(upsert)**: `--nb <사건번호> --force` → 해당 raw 파일 재수집·덮어쓰기.
  같은 사건번호가 일련번호 여럿으로 들어오면(출처 중복) 정규화된 사건번호 파트 대조로
  중복 판정 → 최신 수집본만 유지, 나머지는 제외 목록으로.
- **삭제(delete)**: raw 파일을 지우는 대신 `data/precedents/removals.json`에 사건번호 기재 →
  ingest가 제외. (원본 보존 + git 이력으로 "왜 뺐는지" 추적 — 팀이 메모 필드에 사유 기입.)
  물리 삭제는 `--purge`로만.
- 시드 큐레이션(seed_cases.json)은 지금처럼 사건번호로 조인 — 검수·문구는 여기서만 수정.

**검수 플로우 연결** (기존 게이트 재사용, 신규 장치 불필요):
신규 유입 → 자동 태깅 + `verified=False` 적재 → **게이트가 자동 노출 차단**(야간 구축 그대로)
→ 검수 큐 시트(미검수 문서 목록 + 자동 태그 + 요지 발췌)를 갱신 스크립트가 출력 → 정민재가
seed_cases.json에 항목 추가(verified=true) → 재적재 시 승격. 검수 시 자동 태그 재검토 포함
(rule-auditor 권고 반영, README 명문화 완료).

**임베딩 버전 메타와 재임베딩 정책**:
- meta.json의 `signature`가 단일 진실 — 질의·인덱스 불일치는 이미 하드 에러.
- **전체 재임베딩 트리거 기준**: ⑴ 백엔드/모델 교체(서명 변화 — 자동 감지) ⑵ 청킹 규칙 변경
  ⑶ 컨텍스추얼 임베딩(2b) 도입. → 이 셋은 무조건 full rebuild(현행 방식 그대로).
- **증분 임베딩(최적화, 선택)**: 문서 추가·교체만 있을 때 청크 내용 해시를 대조해 신규·변경
  청크만 임베딩. 소량 갱신 시 비용 절감용이며, 서명이 같을 때만 허용. (Chroma upsert 지원)

**원커맨드** `scripts/update_precedents.py` (설계 — 미구현):
```
python scripts/update_precedents.py                  # 증분 수집→중복 제거→적재→평가→검수 큐 출력
  --full          # 전체 재수집·재적재
  --nb <사건번호> [--force]   # 특정 판례 upsert
  --remove <사건번호> --reason "..."  # removals.json 기재
  --reembed       # 서명 무관 강제 전체 재임베딩
종료 시 요약: 신규 N · 교체 N · 제외 N · 미검수 대기 N · 평가 성적 변화 (전/후)
```

**스케줄 자동화 (설계만, 구현 보류)**: 주 1회 `update_precedents.py` 실행 후보 —
Windows 작업 스케줄러(개발기) 또는 GitHub Actions(레포 커밋 겸용). 단 대원칙상 자동 주기보다
"팀이 원할 때 한 줄"이 우선이고, 자동화는 대회 이후 운영 단계 과제로 둔다.

### 4.3 precedent-rag.md 반영안 (승인 시 적용)

- §2 실행 방법에 "지속 업데이트" 절 추가: 원커맨드 사용법 + 검수 큐 → seed_cases.json 승격
  절차 + removals.json 의미론.
- §4 확장 지점에 "증분 수집 커서·재임베딩 트리거 기준" 항목 추가(위 4.2 요약).
- §5 가드레일 표에 "신규 유입 기본 미검수 → 게이트 차단" 행 추가(이미 구현된 사실의 명문화).

  시만). ⑸ 원커맨드 `update_precedents.py`(수집→중복 제거→적재→평가→검수 큐 요약).
  cron 자동화는 설계만(대회 이후 과제).

- **바꾼 이유**: 질의 없이 방침으로 확정(PM 결정, 2026-07-22) — 인정 여부가 애매한 축을

  FriendliAI가 주최 측 안내 경로(flp_ 키 체계 일치)이므로 서빙사 국적 쟁점도 소멸 —
  질의 ①(외산 베이스)·②(FriendliAI 경유) 모두 폐기.
- **최종 결정**: **베이스(사전학습)부터 국내 개발인 모델만 사용한다.** 이에 따라:
  ⑴ GPU 대량 임베딩 1순위였던 KURE-v1(bge-m3 기반) **배제** — [2026-07-22 임베딩·벡터DB
  결정]의 로컬 모델 선정 부분을 이 항목이 대체(append-only 갱신). 재편안은 §6.
  ⑵ 리랭커 후보 dragonkue/bge-reranker-v2-m3-ko 등 bge 계열 **전부 배제** — 초안 B의
  후보 c를 §6의 대체안으로 재편. ⑶ LLM은 Solar Pro·EXAONE(·A.X 계열 중 from-scratch인
  A.X 3.1/K1만) — 전부 국내 자체 개발이라 무풍.
- **출처**: PM 방침 확정(2026-07-22) + 주최 측 EXAONE 키 공식 제공 사실. 재편 조사:
  docs/rag-expansion-review-2026-07-22.md §6.

## 6. 방침 재편 조사 — 순수 국내 제약 하의 임베딩·리랭커·GPU 스토리

### 6.1 GPU 대량 임베딩 재편

**KURE-v1 계보 확정 → 배제**: 공식 GitHub·모델 카드에 "BAAI/bge-m3 기반 파인튜닝" 명시
(github.com/nlpai-lab/KURE). 같은 랩 KoE5(multilingual-e5 기반)도 배제.

**순수 국내 오픈 임베딩 전수 조사 결과 — 실전급은 1개**:

| 후보 | 계보 판정 | 성능(한국어 검색 nDCG@10) | 비고 |
|---|---|---|---|
| **kakaocorp/kanana-nano-2.1b-embedding** | ✅ 순수 국내 — 기술보고서(arXiv 2502.18934)에 "from scratch 2.7조 토큰" 명시, 자체 8B에서 증류 | **65.0** (같은 벤치 근사: KURE 69.5 · bge-m3 68.7 · KLUE 계열 48.7) | **유일한 실전급.** CC-BY-NC(비상업 — 대회 시연 무방, 상용화 시 재검토), 512토큰 청킹 권장, sentence-transformers 호환, 2.1B로 GPU 배치 적합 |
| KLUE RoBERTa 계열 (ko-sroberta-multitask 등) | ✅ 순수 국내 (KLUE 컨소시엄 자체 사전학습) | 0.487 — 큰 폭 열세 | 최후 폴백만 |
| snunlp/KR-SBERT | ✅ 순수 국내 (서울대 KR-BERT) | 검색 벤치 검증 부재 | 부적합 |
| 네이버 CLOVA 임베딩(dolphin) | 자체 개발이나 **API 전용**·계보 비공개 (v2는 bge-m3라 배제) | — | GPU 배치 요건 미충족 |
| LG LGAI-Embedding-Preview | ❌ Mistral-7B 기반 명시 | — | 배제 (EXAONE 전용 임베딩은 미공개) |

**Upstage 임베딩**: 오픈 웨이트 공개 이력 없음 — **API 전용 확정**(GPU 로컬 배치 불가).
가격은 신형 Embed 2 기준 **$0.02/1M** → 판례 10만 건(1.5억 토큰) ≈ **$3(약 4천 원)** —
비용은 무시 가능. ⚠ 확인 필요 2건: ⑴ 구 Embed(solar-embedding-1-large)는 **2026-08-31
종료 예정** — 현재 코드가 쓰는 `embedding-query/-passage`가 Embed 2 계열인지 콘솔에서 모델
ID 매핑 확인(오늘 실호출은 정상 동작) ⑵ 배치 rate limit(RPM/TPM) 수치.

**재편안 (권고: 투트랙)**:
- **서비스 경로(질의 임베딩·소량 적재) = Upstage API 유지** — 이미 실검증, 국내 벤더, 비용 무시 가능.
- **GPU 대량 배치·"순수 국내 오픈" 스토리 = kanana-nano-2.1b-embedding** — 평가셋 A/B
  (Upstage vs kanana)로 하한선 재캘리브레이션 후 채택 확정. KURE 대비 ~4.5pt 열세는
  BM25 하이브리드가 보완(우리 구조의 강점).
- 순수 국내 오픈이 기대 이하로 나오면: **임베딩은 Upstage API 배치(Embed 2, $3)로 확정하고
  GPU는 §6.3의 다른 구간에 투입** — 어느 쪽이든 파이프라인은 백엔드 교체 1회(서명 자동 감지).
- 반영 필요(승인 후 1줄): `embedding.py`의 `PRECEDENT_LOCAL_MODEL` 기본값
  `nlpai-lab/KURE-v1` → `kakaocorp/kanana-nano-2.1b-embedding` + precedent-rag.md §3 갱신.

### 6.2 리랭커(c) 재편

**순수 국내 오픈 크로스인코더는 부재 확정** — ko-reranker(bge-reranker-large 기반)·dragonkue·
sigridjineth·upskyy 전부 bge 계보로 배제. klue 기반 커뮤니티 업로드는 문서·벤치 없는 미검증.
네이버 CLOVA 리랭커는 API 전용 + 기반 모델 미명시.

**대체안 평가** (판정 불변 · 심사 효과 기준):

| 대체안 | 판정 불변 | 심사 효과 | 평가 |
|---|---|---|---|
| **㈎ LLM listwise 재정렬 (Solar 1순위, EXAONE 대안)** | ✅ 게이트 통과 후보의 **노출 순서에만** 관여(게이트·판정 무접촉). temperature 0 + 리포트 단위 캐시로 시연 결정성 확보 | **상** — "국내 LLM이 판례 후보를 재정렬"로 AI 활용 확대 + RankGPT/RankZephyr(7B급으로 크로스인코더 상회) 연구 근거 제시 가능 | **채택 후보 1순위.** 후보 10~20건 listwise ≈ 질의당 수천 토큰 — 비용·지연 감당 가능. 평가셋 확장 후 A/B로 확정 |
| ㈏ 하이브리드 가중 튜닝 (RRF 가중·후보 폭) | ✅ 완전 결정적 | 하 — 튜닝일 뿐 새 AI 활용 없음 | 기본으로 항상 수행(비용 0). 단 순위 품질 상한이 임베딩에 묶임 |
| ㈐ CLOVA 리랭커 API | ✅ | 중 | 신규 벤더 추가 + 기반 모델 비공개 — 방침 검증 불가라 배제 |

**재편 결정(권고)**: c(외산 크로스인코더) 폐기 → **㈏는 즉시(평가셋 루프의 일부), ㈎는 대량
수집 후 A/B로 조건부 채택**. ㈎ 채택 시 decisions.md 기록(AI 활용 확대 결정) + 재정렬 LLM은
지연 무관한 오프라인 사전 생성(분석 시점) 우선 검토.

### 6.3 GPU 활용 실적 재구성 (순수 국내 조합만)

재편 후에도 GPU 스토리는 오히려 두꺼워진다:

| GPU 워크로드 | 모델(전부 순수 국내) | 시점 | 어필 |
|---|---|---|---|
| ① 판례 대량 임베딩 배치 | kanana-nano-2.1b-embedding | 대량 수집 후 1회 | "판례 수만 건을 대회 GPU에서 자체 임베딩" |
| ② EXAONE 직접 서빙 | EXAONE-4.0.1-32B (vLLM, 80GB 1장 / FP8 32GB) | 오프라인 역할: 태깅 배치(2a)·비교 추론 사전 생성(2d)·LLM 재정렬(㈎) 실험 | "생성 워크로드까지 GPU 자체 서빙" — 라이선스도 비상업 대회 명시 허용 |
| ③ (선택) 임베딩 A/B 평가 | kanana vs Upstage 산출 비교 | ①과 동시 | "GPU에서 모델 선정 실험을 직접 수행" 서사 |

서비스 실시간 경로는 현행 유지(Upstage·FriendliAI API) — GPU는 전부 오프라인 배치라
시연 안정성과 충돌하지 않는다.
